## 3. Clean Room 100% — Mandatory Research Boundary
SMEsPlus is a NEW / CLEAN ROOM 100% implementation.

Allowed research inputs:
1. SMEsPlus-owned requirements, decisions, frozen evidence and approved business rules.
2. Official public vendor/product documentation.
3. Public standards and specifications.
4. Open-source software whose license and provenance are reviewed.
5. Clean-room benchmark fixtures written from SMEsPlus requirements.
6. Permitted black-box behavioral learning at the level authorized by project governance.

Forbidden research/implementation inputs:
1. Copying proprietary ERP source code, private schema, private ORM definitions, proprietary workflow implementation, or non-public documentation.
2. Decompilation, reverse engineering intended to reproduce protected implementation, or importing proprietary implementation artifacts into prompts/fixtures.
3. Asking an AI agent to imitate or reproduce a named proprietary implementation.
4. Accepting AI-generated code with unknown or unreviewed provenance merely because it was generated by AI.
5. Cross-contaminating clean-room benchmark fixtures with prohibited implementation material.

## 4. Clean Room Evidence Required for Development-Capable Tools
Before any generated code can be accepted downstream, evidence must include where applicable:
- Prompt ID and prompt hash.
- Input-source/provenance manifest.
- Repository/base commit and isolated branch/worktree.
- Tool/model/version and execution mode.
- Diff or generated artifact manifest.
- Dependency/license/SBOM evidence.
- Unit/integration/E2E/security evidence as applicable.
- Independent review of architecture, license/provenance and behavior.
- Gate decision lineage.

If prohibited source material is detected, the affected benchmark/output is `INVALID / QUARANTINE`; it cannot be scored as positive evidence.

## 5. Selection Philosophy
The project is an ERP SaaS for Thai SMEs. Selection is therefore based on:
`Mission Fit + Constraint Fit + Runtime Evidence + Governance Fit + Clean-Room Safety + Sustainable TCO`.

Paid build-time tools are acceptable when productivity/quality/risk ROI is demonstrated. Runtime/core tools with tenant/company/user/server/request/storage cost multipliers require stricter economics. Open/free licensing is preferred where operationally sound, but Free is not an automatic winner.

## 6. No Premature Tool Freeze
Research may recommend `KEEP`, `SUPPLEMENT`, `REPLACE`, `REJECT` or `HOLD` by mission. No tool becomes canonical solely from a vendor claim, prior usage, feature count, popularity or one benchmark result.
