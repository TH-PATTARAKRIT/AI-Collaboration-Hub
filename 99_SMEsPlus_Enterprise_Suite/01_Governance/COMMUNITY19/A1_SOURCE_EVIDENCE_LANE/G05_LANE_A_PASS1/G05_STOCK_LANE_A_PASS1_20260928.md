WHY: it is the system's single source of truth for "where is this product, how much of it, and how does it get from A to B." Category Supply Chain/Inventory, `application: True` (installs as a standalone top-level app), license LGPL-3. (`__manifest__.py`)
2. Declared dependencies (dependency relationships only, not group membership): `product` — this same pilot's other G03 anchor module — plus `barcodes_gs1_nomenclature` and `digest`. (`__manifest__.py`)
3. Lifecycle hooks: `pre_init_hook`, `post_init_hook` (`_assign_default_mail_template_picking_id`), and `uninstall_hook` are all registered — i.e. this module runs custom Python at install/uninstall time beyond ordinary XML data loading, a pattern not seen in the smaller G03 anchors (`product`, `uom`, `analytic`) fetched earlier in this pilot. RISK: A1 should treat these hooks as executable migration-adjacent logic requiring their own review if/when this module is formally opened, since their bodies were not fetched in this PASS-1 (out of scope; `models/__init__.py` only re-exports them). (`__manifest__.py`)
4. `data` installs security first, then digest/mail-template/barcode-pattern/sequence/traceability seed data, then 15 report definition files, then ~30 view files (menu, wizards' views, then a long ordered list of model views), ending with `views/uom_uom_views.xml` — a direct cross-reference into this pilot's confirmed `uom` anchor (extended, not merely depended on, at the view layer). A separate `demo` key installs 5 demo files. Assets span 5 buckets: report-only SCSS, eager backend JS/XML/SCSS (with the forecast-graph widget explicitly deferred to a `_lazy` bucket), a frontend traceability-report SCSS, and both a Tour-test and a unit-test bucket. ### 2.2 Data — models, inheritance, key fields, identity/uniqueness
5. `stock.location` is a materialized-path hierarchy (`_parent_store`) with a required `usage` selection (`supplier`/`view`/`internal`/`customer`/`inventory`/`production`/`transit`, default `internal`) — each value's help text documents a specific semantic role (e.g. `view` "Can't directly contain products," `inventory` is "the counterpart for inventory operations done to correct stock levels"). A `replenish_location` boolean flags at most one location per parent/child chain as the resupply point for pull rules (enforced by `_check_replenish_location`, which searches for a conflicting ancestor/descendant). `stock.route` (in the same file) is a named, sequenced, optionally product/category/warehouse/packaging-selectable path composed of `stock.rule` records. (`models/stock_location.py`)
6. `stock.quant` is the on-hand-quantity ledger: `(product_id, location_id, lot_id, package_id, owner_id)`-scoped quantity rows. `check_product_id` blocks creating a quant for a non-`is_storable` product ("consumables or services"); `check_location_id` blocks quants at a `usage == 'view'` location; `check_lot_id` blocks a lot being linked to a different product than the quant's own; `check_quantity` (called, not itself a DB constraint trigger, per its `@api.constrains`-free signature — it is invoked explicitly elsewhere) additionally enforces that a `tracking == 'serial'` lot never sums to more than 1 unit across non-inventory locations, using the product's own UoM-aware `compare()` (this pilot's `uom` anchor's own API, cross-referenced here). (`models/stock_quant.py`)
7. `stock.move` (the atomic movement record): a required `state` selection (`draft → waiting → confirmed → partially_available → assigned → done` / `cancel`, each value's help text documenting the two competing meanings of "waiting" — "waiting another move" vs. "waiting for product availability"). `product_id` is domain-restricted to `type == 'consu'` (this Odoo version's collapsed goods/service/combo typing, confirmed in `product`'s own Lane A Pass-1 file) — i.e. `stock.move` itself does not further require `is_storable`; that distinction is enforced elsewhere (finding 6's quant-level check, and `stock.move`'s own procurement/reservation logic, not fully traced in this pass). `procure_method` (`make_to_stock`/`make_to_order`) and a linked `rule_id` (`stock.rule`, `ondelete='restrict'`) connect a move back to the procurement rule that created it. `move_orig_ids`/`move_dest_ids` (both M2M to `stock.move` itself) chain moves across a multi-step route. (`models/stock_move.py`)
8. `stock.move.line` is the concrete execution unit of a move (a specific lot/quantity actually picked/put away): `_check_lot_product` blocks a lot mismatched to the line's product; `_check_positive_quantity` forbids negative quantities. (`models/stock_move_line.py`)
9. `stock.picking` groups moves into one user-facing transfer document; its own `state` (`draft/waiting/confirmed/assigned/done/cancel`) is **computed** (`compute='_compute_state'`, `store=True`) from the underlying moves' states rather than being independently settable — its help text documents a `move_type` (`direct`/`one`, "as soon as possible" vs. "when all products are ready") that changes what "Ready"/"Waiting" mean in aggregate across the picking's moves. `stock.picking.type` (same file) is the configuration record (a warehouse's "Receipts"/"Delivery"/"Internal Transfers"/etc. operation types) that pickings are created from. (`models/stock_picking.py`)
10. `stock.rule` models a single push/pull step: `action` (`pull`/`push`/`pull_push`), `procure_method` (`make_to_stock`/`make_to_order`/`mts_else_mto`, the third option's help text explicitly documents it as "take from stock, if unavailable, trigger another rule" — a fallback chain, not a simple either/or), `location_src_id`/`location_dest_id`, `picking_type_id`, `delay` (lead time). A companion `Procurement` `NamedTuple` and `ProcurementException` class define the low-level procurement-request contract used to invoke rules programmatically. (`models/stock_rule.py`)
11. `stock.warehouse.orderpoint` (min/max reordering rule): `_check_min_max_qty` enforces `product_min_qty <= product_max_qty`; `_compute_warehouse_id` falls back from the orderpoint's own location to searching by company if the location has no warehouse, and warns (`_warehouse_redirect_warning`) if neither resolves — i.e. an orderpoint with an unreachable warehouse is tolerated at the data level but flagged. `action_replenish`/`action_replenish_auto` are the entry points that turn a shortfall into an actual procurement request. (`models/stock_orderpoint.py`)
12. `stock.warehouse` is the top-level configuration object whose writes are expected to programmatically (re)generate the warehouse's own routes/rules/picking-types (confirmed by the size and structure of this file — 1164 lines — though the generation logic itself was read only at a header/method-signature level in this pass, not traced in full; see Evidence Gaps). (`models/stock_warehouse.py`)
13. `stock.lot`: `_check_lot_name_product` -family constraint on `(name, product_id, company_id)` guards lot-name uniqueness scope (exact uniqueness semantics not fully traced — flagged for A1). `stock.package` is a materialized-path hierarchy of physical containers (pallet/box nesting), computing both a "current" and a "destination" complete name (the latter anticipating an in-progress move's package relocation). `stock.package.type`/`stock.storage.category`(`.capacity`) define reusable dimension/weight templates and per-category capacity limits used by putaway logic. `product.removal` (in `product_strategy.py`) is a pluggable removal-strategy registry (e.g. FIFO/LIFO — concrete strategy implementations not present in this module's own files, confirmed only by the registry's existence) and `stock.putaway.rule` maps a source location/package-type/category to a destination location. (`models/stock_lot.py`, `stock_package.py`, `stock_package_type.py`, `stock_storage_category.py`, `product_strategy.py`)
14. `product` extension (`models/product.py`): adds `is_storable` (Boolean, "Track Inventory," computed default `False`, forced `False` whenever `type != 'consu'` — i.e. only goods can ever be storable, never `service`/`combo`) and `tracking` (`none`/`lot`/`serial`, required, forced to `none` whenever `is_storable` is falsy) directly onto `product.template` — confirming and completing the "no separate storable-type" observation flagged as an open question in `product`'s own Lane A Pass-1 file (finding 6 there): this Odoo version keeps `type` as goods/service/combo only, and layers "is this goods item actually stock-tracked" as a **separate, dependent-module-added** boolean rather than a `type` value. `qty_available`/`virtual_available`/`incoming_qty`/`outgoing_qty` are all computed-and-searchable (custom `search=` methods, not simple stored fields) — i.e. filtering products by on-hand quantity in a list/search view triggers a computed SQL-level search method rather than an indexed column scan. (`models/product.py`)

### 2.3 Business rules / states / lifecycle / exceptions
15. Reservation/availability is the module's central business concern: `stock.move.state` distinguishes `partially_available` from `assigned` (fully reserved), and `stock.picking.state` is itself derived from the aggregate of its moves' states, modulated by `move_type` (direct vs. all-at-once). The actual reservation algorithm (which quants get assigned to which move, respecting removal strategy and package/lot preference) lives inside `stock_move.py`'s larger body and was not traced in full detail in this pass (flagged in Evidence Gaps) — A1 doing a deep dive on availability should read `stock_move.py` end-to-end rather than relying solely on this PASS-1's field/selection-level summary.
16. Push/pull procurement (`stock.rule`) is the mechanism by which routes are actually executed: a `pull` rule reacts to a downstream shortage by creating an upstream move; a `push` rule reacts to a move's completion by automatically creating a follow-on move; `pull_push` does both. `procure_method`'s three-way fallback (finding 10) means a single route step's behavior is configurable per rule, not fixed by the route as a whole.
17. Scrap (`stock.scrap`) is a deliberate, auditable write-off path — a distinct model from ordinary `stock.move`, with its own `@api.ondelete` guard (found in the grep pass; specific condition not read in depth here) and a separate `stock.scrap.reason.tag` taxonomy for categorizing why stock was scrapped.
18. Storage-category capacity (`stock.storage.category.capacity`) and putaway rules (`stock.putaway.rule`) together implement location-selection logic (e.g. "this category of product can only go in a location with spare weight/volume capacity, and should be routed here") — the actual capacity-checking algorithm was not traced in this pass (only the models' existence and field-level shape); flagged for A1.
19. Multi-step warehouse configuration: `stock.warehouse`'s size and the presence of auto-computed route/rule fields (per its own field list, not exhaustively traced) indicate that changing a warehouse's step-count settings (e.g. one-step vs. multi-step receipt/delivery) is expected to regenerate its associated `stock.route`/`stock.rule`/`stock.picking.type` records programmatically — a significant "configuration write triggers structural regeneration" pattern A1 should verify in depth (not verified here beyond the file's size/shape).
20. `res.company._default_confirmation_mail_template` falls back to `False` (rather than raising) if the seeded `stock.mail_template_data_delivery_confirmation` external ID cannot be resolved — a defensive default, confirming this module tolerates its own seed data being partially uninstalled/renamed without hard-failing company creation. (`models/res_company.py`)
