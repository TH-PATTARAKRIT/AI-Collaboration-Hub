## 2. Findings by A1 completion-card section

### 2.1 Manifest / dependencies / purpose
1. WHAT: `purchase` ("Purchase") is the base module for requesting quotations (RFQs), issuing purchase orders, and reconciling them against vendor bills. WHY: it is the system's single source of truth for "what did we order from this vendor, at what price, and has it been billed correctly." Category Supply Chain/Purchase, `application: True`, license LGPL-3. (`__manifest__.py`)
2. Declared dependency (dependency relationship only, not group membership): **`account` only** — notably, `purchase` does **not** depend on `stock` (this pilot's G05 anchor); the goods-receipt/inventory side of purchasing is confirmed to live in a separate, dependent module (`purchase_stock`, per the module-naming convention already seen in `stock`'s and `mrp`'s own manifests) rather than in this module itself. This is a directly confirmed, source-based fact relevant to A1/A2's cross-group analysis, not an inference from naming alone. (`__manifest__.py`)
3. `data` installs security, then digest data, then an `account.move` view extension, then purchase seed data, cron data, and a report file — the ordering shows `views/account_move_views.xml` loading **before** `data/purchase_data.xml`, ahead of most of the module's own views. Assets: a large eager `web.assets_backend` bundle (components, product-catalog integration, a "toaster button" widget, views, onboarding-tour JS), a frontend bundle (portal interactions + SCSS), and a Tour-test bundle. A separate `demo` key installs 1 demo file. (`__manifest__.py`)

### 2.2 Data — models, inheritance, key fields, identity/uniqueness
4. `purchase.order` `_inherit`s four mixins at once: `portal.mixin` (customer-portal access), `product.catalog.mixin` (this pilot's `product` anchor's own extension point — confirmed exercised here, same as `stock`'s exercise of it), `mail.thread`+`mail.activity.mixin`, and `account.document.import.mixin` (implying OCR/EDI-style document import support). Required `state` selection: `draft` ("RFQ") → `sent` ("RFQ Sent") → `to approve` → `purchase` ("Purchase Order") / `cancel` — a 5-state machine distinct in shape from `stock.picking`'s or `mrp.production`'s own state machines (no separate "waiting"/"assigned" availability axis here; readiness is purely approval-driven). A `locked` boolean (independent of `state`) additionally gates editability once confirmed, itself driven by a company-level `po_lock` setting (`lock_confirmed_po`, a `related` field). (`models/purchase_order.py`)
5. Double-validation approval (`res.company` extension): `po_double_validation` (`one_step`/`two_step`, default `one_step`) plus `po_double_validation_amount` (Monetary, default 5000) implement an amount-based approval threshold — `purchase.order._approval_allowed()` returns true if the company is `one_step`, or if `two_step` but the order's total (currency-converted) is under the threshold, or if the current user holds `purchase.group_purchase_manager` regardless of amount. `button_confirm()` calls `_approval_allowed()` and either auto-approves (`button_approve()`, setting `state='purchase'` and `date_approve`) or parks the order at `state='to approve'` pending a manager's explicit approval. This is a complete, clean, source-confirmed approval-threshold business rule. (`models/purchase_order.py`, `res_company.py`)
6. Cancellation/deletion guards: `button_cancel()` blocks cancelling a locked PO (must unlock first) and blocks cancelling a PO whose bills are not themselves cancelled/draft; `_unlink_if_cancelled` (`@api.ondelete`) blocks deleting any PO not in `state == 'cancel'`. `_check_order_line_company_id` (`@api.constrains` on `company_id`/`order_line`) blocks a PO from containing products belonging to a company the PO's own company cannot access (`_accessible_branches()`), raising a `ValidationError` naming the offending products. (`models/purchase_order.py`)
7. Vendor-bill reconciliation is implemented as a **dedicated read-only SQL view model**, `purchase.bill.line.match` (`_auto = False`, i.e. Odoo creates a SQL VIEW rather than a table for this model) — joining `purchase.order.line` against `account.move.line` per product/company/partner, exposing `qty_invoiced`/`qty_to_invoice`/billed-vs-purchased untaxed amounts. This is a materially different implementation pattern from any model seen in this pilot's other 5 anchors (`product`, `uom`, `analytic`, `stock`, `mrp`), all of which are ordinary stored tables — flagged as a notable architecture choice for A1. (`models/purchase_bill_line_match.py`)
8. `account.move` extension (`account_invoice.py`): `purchase_id`/`purchase_vendor_bill_id` support "auto-complete a vendor bill from a prior PO or bill," `is_purchase_matched` is an explicit boolean summarizing whether every bill line is linked to a PO line ("0: PO not required or partially linked. 1: All lines linked" per its own docstring) — i.e. 3-way-match status is surfaced as a single computed flag on the bill itself, not only via the separate `purchase.bill.line.match` view. A module-level `TOLERANCE = 0.02` constant is used when searching for a matching PO by total amount — a deliberate fuzzy-match allowance, not an exact-total requirement. (`models/account_invoice.py`)
9. `account.tax` extension: adds `purchase_order_line_ids` (M2M, `readonly=True`, i.e. populated only by PO-line logic, not directly editable) and extends `_compute_is_used` so a tax used on any PO line is flagged "in use" (preventing, elsewhere in `account`, deletion/deactivation of an in-use tax) — a small but meaningful cross-module integrity link protecting tax configuration from being broken by in-use PO data. (`models/account_tax.py`)
10. `account.analytic.applicability` extension: adds a `purchase_order` value to the `business_domain` selection (`selection_add`, `ondelete={'purchase_order': 'cascade'}`) — this is `purchase`'s confirmed integration point into this pilot's G03 `analytic` anchor's applicability-scoring mechanism (see `analytic`'s own Lane A Pass-1 file, finding 10): a PO line's analytic-plan mandatoriness can now be scored specifically for the `purchase_order` business domain rather than only the generic `'general'` value that `analytic` itself ships with. (`models/analytic_applicability.py`)
11. `bill.to.po.wizard`: creates a new PO (or appends to an existing one) directly from selected vendor-bill lines, **and then immediately calls `button_confirm()` on that PO** — i.e. this wizard bypasses the normal RFQ→confirm user flow and always attempts confirmation right away (subject to the same `_approval_allowed()` logic from finding 5, so a two-step-validation company would still park it at `to approve` rather than silently approving it). RISK: A1 should confirm this auto-confirm behavior is the intended design (creating a PO retroactively from a bill implies the purchase already happened) rather than an oversight, since it differs from every other PO-creation path in this module. (`wizard/bill_to_po_wizard.py`)

### 2.3 Business rules / states / lifecycle / exceptions
12. Confirmation-time validation (`button_confirm`): `_confirmation_error_message()` blocks confirming a PO with an order line that is missing a product (excluding display-type and down-payment lines); `order_line._validate_analytic_distribution()` is invoked before approval logic runs; `_add_supplier_to_product()` runs on every confirm (implying every confirmed PO updates the product's own vendor-pricing records — the two-way "confirming a PO teaches the product who its vendors are" pattern, not merely reading `product.supplierinfo`). (`models/purchase_order.py`)
13. Quotation printing (`print_quotation`) side-effects the order's own state: printing a draft quotation silently transitions it to `sent` — i.e. "has this RFQ been sent" is tracked as a side effect of a print/report action, not an explicit user action of its own. (`models/purchase_order.py`)
14. Portal/customer-facing surface: `controllers/portal.py` exposes 5 routes — `/my/rfq` and `/my/purchase` (both `auth="user"`, i.e. logged-in portal users only), `/my/purchase/<id>` (`auth="public"` — token/portal-access-gated rather than login-gated, consistent with Odoo's standard portal-record-access pattern), a JSON-RPC `/my/purchase/<id>/update` route (also `auth="public"`) letting the **vendor themself** update the scheduled date on PO lines from the portal (`get_update_url` in `purchase_order.py` builds this URL), and an EDI-download route. RISK: A1 should confirm the `auth="public"` routes rely on Odoo's standard portal-token access check (not verified independently in this pass — the underlying `portal.mixin` access-check implementation lives in a different module) rather than any custom, weaker check in this controller. (`controllers/portal.py`, `models/purchase_order.py`)

Two further independent feature-toggle groups exist: `group_warning_purchase` ("A warning can be set on a product or a customer (Purchase)") and `group_send_reminder` ("Send an automatic reminder email to confirm delivery" — note this help text references "delivery," a `stock`-family concept, even though `purchase` itself does not depend on `stock`; this group's practical effect likely only activates once a `stock`-integrating module like `purchase_stock` is also installed — an observation, not independently verified in this pass). A `base.group_user` record is also referenced/extended in this file (not independently traced beyond its presence). (`security/purchase_security.xml`)
16. Multi-company: `ir.rule`s were found for Purchase Order, Purchase Order Line, "Portal Purchase Orders," "Purchase User Account Move Line," "Purchase User Account Move," "Portal Purchase Order Lines," "Purchases & Bills Union," and "Purchase Order Report" (8 distinct rule names identified via grep on rule `<field name="name">` values; exact `domain_force` content and full company-scoping pattern per rule were not individually re-verified in this pass — flagged as a depth gap for A1, mirroring the same gap recorded for `mrp`).
