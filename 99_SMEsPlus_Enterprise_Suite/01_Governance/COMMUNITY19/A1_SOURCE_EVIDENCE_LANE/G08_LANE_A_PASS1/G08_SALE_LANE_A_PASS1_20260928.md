## 2. Findings by A1 completion-card section

### 2.1 Manifest / dependencies / purpose
1. WHAT: `sale` ("Sales") is the base module for quoting customers, confirming sales orders, and generating customer invoices from them. WHY: it is the system's single source of truth for "what did we quote/sell to this customer, at what price, and has it been invoiced." Category Sales/Sales, `application` key absent from the manifest itself (the app entry is registered by the `sales_team` dependency), license LGPL-3. (`__manifest__.py`)
2. Declared dependencies (dependency relationships only, not group membership): `sales_team`, `account_payment` (manifest comment: "-> account, payment, portal"), `utm`. Notably `sale` does **not** depend on `stock` (this pilot's G05 anchor) or `crm` (this pilot's G09 anchor) — goods-delivery integration (`sale_stock`) and CRM-opportunity-to-quotation integration (`sale_crm`, seen by name in the PR#71 candidate bank list for this group) are confirmed to live in separate, dependent modules, consistent with the `purchase`/`purchase_stock` boundary already recorded in this pilot's G07 Pass-1 file. (`__manifest__.py`)
3. `data` installs security first, then report views, then cron/sequence/mail-template/tour data, then wizard views, then `views/sale_order_views.xml` explicitly "before their references" per an inline comment, then remaining views, then `views/sale_menus.xml` last "because referencing actions defined in previous files" — an explicit, self-documented load-order dependency chain. A large `web.assets_backend` bundle (product-catalog/combo/quantity/product-list widgets, onboarding tour) and a `web.assets_frontend` bundle (portal interactions + SCSS) are declared; a separate `demo` key installs 2 demo files. (`__manifest__.py`)

### 2.2 Data — models, inheritance, key fields, identity/uniqueness
4. `sale.order` `_inherit`s six mixins at once: `portal.mixin`, `product.catalog.mixin` (the same G03 `product` extension point already exercised by `stock`, `mrp`, and `purchase` per this pilot's other Pass-1 files), `mail.thread`, `mail.activity.mixin`, `utm.mixin`, and `account.document.import.mixin` (the same OCR/EDI-import mixin `purchase.order` also inherits). `state` selection: `draft` ("Quotation") → `sent` ("Quotation Sent") → `sale` ("Sales Order") / `cancel` — a 4-state machine, one state shorter than `purchase.order`'s 5-state machine (no separate "to approve" step in base `sale`; a `locked` boolean, independently settable, still exists here as it does on `purchase.order`). A model-level SQL `Constraint` (`_date_order_conditional_required`) enforces that a confirmed order must carry `date_order` — a data-integrity rule expressed at the database level, not only in Python. (`models/sale_order.py`)
5. `sale.order.line` `_inherit`s `analytic.mixin` only (a materially lighter mixin set than `sale.order`'s own, and than `purchase.order.line`, which this pilot's G07 evidence did not record any `_inherit` list for). (`models/sale_order_line.py`)
6. Auto-approval logic exists (`_should_be_locked`/company `sale.group_auto_done_setting` feature-flag check) but there is no separate manager-approval-threshold mechanism analogous to `purchase.order`'s `_approval_allowed()`/`po_double_validation` — `action_confirm()` on `sale.order` moves straight from `draft`/`sent` to `sale` once its own precondition (`_confirmation_error_message()`, see finding 8) passes, then optionally auto-locks. This is a materially simpler confirmation-authority model than `purchase`'s two-step-validation pattern — flagged as a cross-group design-comparison observation for A1, not a defect. (`models/sale_order.py`)

### 2.3 Business rules / states / lifecycle / exceptions
7. `action_confirm()` runs `_confirmation_error_message()` per order (blocking confirmation of orders not in `draft`/`sent`, or with a line missing a product outside display-type/down-payment lines — the same missing-product guard pattern as `purchase.order.button_confirm()`), runs `order_line._validate_analytic_distribution()`, writes `state='sale'` + refreshed `date_order` via `_prepare_confirmation_values()`, calls the extension hook `_action_confirm()` (empty in this base module, meant to be overridden — e.g. by `sale_stock` to trigger delivery creation), then conditionally auto-locks. (`models/sale_order.py`)
8. Order-confirmation email sending has an explicit async/sync branch: if the `sale.async_emails` ICP is set and a company enables it, the mail template is stashed on `pending_email_template_id` and a cron (`sale.send_pending_emails_cron`) is triggered instead of sending inline — i.e. confirmation-email delivery timing is itself a configurable business rule, not a fixed synchronous side effect. (`models/sale_order.py`, `models/ir_config_parameter.py` pointer)
9. `_prepare_invoice()`/`_create_invoices()` exist as the SO→invoice generation path (signature-level identification only in this pass; full invoicing-line-selection logic not traced in depth — flagged as a depth gap for A1, the equivalent of the `purchase.bill.line.match` reconciliation-depth gap recorded for `purchase`). (`models/sale_order.py`)

### 2.4 Security
10. `security/res_groups.xml` defines 4 independent feature-toggle `res.groups` records (no privilege-tier group pair like `purchase`'s user/manager split is defined in this file itself — `sale`'s user/manager groups are provided by its `sales_team` dependency, not re-declared here): `group_auto_done_setting` ("Lock Confirmed Sales"), `group_discount_per_so_line`, `group_warning_sale`, `group_proforma_sales`. (`security/res_groups.xml`)
11. `security/ir_rules.xml` names 24 distinct multi-company/personal-vs-all record rules spanning SO, SO line, SO/invoice analysis, portal SO/SO-line, personal-vs-all Orders/Order-Lines/Invoices/Invoice-Lines, payment-transaction/token access, invoice send-and-print (single/batch, personal/all), the advance-payment-invoice wizard, and 2 "Manager can manage sale order plan(s)" rules — a "Personal X / All X" pairing pattern recurring across nearly every rule name, implying a consistent salesperson-scoped-vs-manager-scoped record-visibility design across the whole module (exact `domain_force` content not individually re-verified in this pass — depth gap, mirroring the same gap recorded for `purchase`'s `ir.rule`s). (`security/ir_rules.xml`)
12. ACL (`security/ir.model.access.csv`) was fetched and hash-verified but not read in depth beyond confirming its presence — no row-level pattern is asserted here; flagged as a depth gap for A1, mirroring `purchase`. (`security/ir.model.access.csv`)

### 2.5 UI / customer-portal surfaces
13. `controllers/portal.py` exposes 8 routes: `/my/quotes` and `/my/orders` (list views, `auth="user"`), `/my/orders/<id>` (`auth="public"`, token/portal-access-gated — the same pattern as `purchase.controllers.portal`'s equivalent route), a JSON-RPC accept route and an HTTP POST decline route (both `auth="public"`) letting the **customer themself** accept or decline a quotation from the portal, a document-download route, an EDI-download route (paralleling `purchase`'s own EDI-download route), and a JSON-RPC payment-transaction route. This is a materially richer customer-facing surface than `purchase`'s 5-route controller (`purchase` has no customer accept/decline-equivalent action; only a scheduled-date-update route) — reflecting the sell-side vs buy-side asymmetry between the two anchors, an observation for A1's cross-group UX comparison, not independently verified for security-boundary correctness (same portal-mixin caveat as `purchase`'s Pass-1 finding 14). (`controllers/portal.py`)
14. `controllers/combo_configurator.py` and `controllers/product_configurator.py` were fetched and hash-verified but not read in depth in this pass — both are JSON-RPC controllers supporting complex product/combo selection UX, named consistently with the "combo_configurator_dialog"/"product_configurator_dialog" asset bundles in the manifest; flagged as an evidence gap. (`controllers/combo_configurator.py`, `controllers/product_configurator.py`)
