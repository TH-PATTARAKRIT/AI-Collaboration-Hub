### 2.1 Phone remove path creates an archived entry for the acting user's own number (PC-PHON-30, SF-PHON-01-R1(b))

Re-derivation at `phone_validation/models/phone_blacklist.py`@d94486f6, `models/models.py`@dccf9fbf, `models/mail_thread_phone.py`@01ca256f, `odoo/orm/domains.py`@63724c20, `odoo/orm/fields_textual.py`@8653b820:

1. The public remove formats its input on the acting user's record with raising **off**, so an unformattable input becomes a no-value, and that value is passed unchanged to the internal remove.
2. The number field declares its **own** search method. For the set operators that method replaces each term with the term formatted on the acting user's record, keeping the raw term only if formatting yields nothing. A no-value term therefore resolves to the acting user's own number before any lookup runs. **This is explicit in the module itself, not an ORM inference.**
3. Refutation attempt — *is the no-value term dropped before the search method runs?* No. The null-drop optimization for set conditions applies only when the field declares no falsy value, and character fields declare the empty string as theirs. The search method is honoured for any field that declares one and is addressed by its own name. Both pointers reproduce at the anchor. Attempt failed.
4. The "missing" list is computed by testing the **submitted** values for membership in the **found stored** numbers. A no-value can never equal a stored number, so it is **always** missing — even in the branch where the acting user's entry was just found and archived. There is no emptiness guard anywhere on this path.
5. Missing values go to create with the inactive flag. Create formats on the acting user with raising on, giving the user's number, then searches existing entries with the active filter off.
   - Entry exists: it is in the keep-inactive set, so it is **not** reactivated, and it is excluded from creation. No duplicate.
   - **No entry exists: an archived entry for the acting user's number is created.** Refutation attempt — *does the creation filter exclude it, or does a uniqueness constraint stop it?* No: the filter excludes only numbers already found, and the number is by hypothesis not stored. Attempt failed.
6. Refutation attempt — *does the elevated mixin reset helper change the subject?* No. Elevation changes the superuser flag, not the acting user, so steps 2–5 still resolve to the acting user.
7. Acting user with no number: the formatter returns a no-value even with raising on, and the failure arrives from the required-field / not-null check, not from validation. This reproduces the A2 wording (c) exactly.

**Verdict: NOT REFUTED.** PC-PHON-30 **PASS** upheld, and SF-PHON-01-R1(b) is confirmed end to end at source, including the absent-entry branch.

**Strengthening observation (new, LOW, route REC).** A2 §1.1 item 8 records that when the acting user's entry already exists and a message is supplied, that entry receives both a tracking log message and a posted note, because create returns the existing record. A3 R1 reproduces this: the internal remove sets the log message on the found records and archives them, then calls create for the still-"missing" no-value, whose return is the same existing record, and posts a note on it. One removal therefore writes two audit entries onto the wrong subject's entry. The observation is source-confirmed but carries **no REC item and no proof link** — see residual R-PHON-1.

## 4. Adjudication of the non-source classifications (task 3)

### 4.1 Is `PROVIDER CLAIM — NOT SOURCE-PROVABLE` the correct disposition, against GAP or UNKNOWN_PENDING_PROOF?

The label is applied to two items: REC-UNSP-BR5(b) ("as its API terms require") and REC-UNSP-G5 (whether the provider's hosts actually redirect, which decides the exploitability of C09).

**Adjudication: the disposition is CORRECT, and it is correctly applied as a qualifier on top of the class GAP rather than as a replacement class.**

Reasoning:

1. **Against UNKNOWN_PENDING_PROOF.** UPP asserts that a proof exists to be executed and that the item will close when it is. Neither item has such a route in this programme. BR-5(b) is an assertion about a third party's contractual terms; no reading of the anchor and no observation of this module can establish it, and the only basis in evidence is an in-code comment. G5 is an assertion about a live third party's HTTP behaviour, and contact with that provider is **prohibited** for this work. Labelling either UPP would put a permanently-open item into the queue of pending, obtainable proofs — the precise failure mode in which an unclosable claim is later read as "not yet checked" and then, on a mock result, as checked. The REC and the Proof both block that: REC records that no case can settle (b), and Proof §5.1 forbids citing any mock result as closing (b) or G5. Consistent and correct.
2. **Against bare GAP.** GAP is the right *class* — an A1 item that is unverified or incomplete — but GAP alone loses the reason, which is that no evidence route exists inside the authorized scope. A consumer seeing a bare GAP would reasonably plan proof work for it. The qualifier carries that information, and REC states the consumption rule explicitly ("MASTER must not consume part (b) as fact"). Keeping GAP as the class while adding the qualifier preserves the classification vocabulary and the tally, and adds the scope fact. This is the strongest available disposition.
3. **The split of BR-5 is what makes it safe.** Part (a), the mechanics, remains reconciled, classed and runtime-linked. Only the unprovable clause is quarantined. Had the whole business rule been marked PROVIDER CLAIM, the provable narrowing ("not every download") would have been lost.

**Residual (LOW, route REC).** The single label covers two materially different situations and does not distinguish them:

- **BR-5(b)** is not establishable by source **or** by any observation of this system; it would require the provider's own terms document, which is an out-of-band, non-technical artifact. It is unclosable by this programme's evidence types altogether.
- **G5** is an empirical fact about a running third-party service. It is not source-provable, and it is outside the **authorized** observation scope here, but it is not unknowable in principle: an authorized provider-side observation, if ever commissioned, would settle it and the item would then become UPP.

A3 R1 recommends a sub-tag distinguishing "no evidence type can settle this" from "an evidence type exists but is outside authorized scope", rather than any class change. This is a precision defect, not a misclassification.

### 4.2 Is PC-ONBD-05 correctly recorded FAIL on the verbatim wording while PC-ONBD-05R PASSes, and does that double-count?

**Adjudication: the pair is CORRECT and does NOT double-count a finding. One LOW tally residual is routed to PROOF.**

Reasoning:

1. **Two distinct predicates, one substance.** PC-ONBD-05's predeclared predicate scans *all* module `.py` files and fails on *any* elevation call. PC-ONBD-05R's predicate scans the *runtime-code* set. These are different falsifiable statements, both executed against the same re-derived facts, and A3 R1 reproduced both (section 2.4). The underlying substance is a **single** finding — zero elevation constructs in runtime code, five in test-harness code — and neither result contradicts it.
2. **The FAIL is a predicate-integrity record, not a second substantive finding.** Its function is to record that the parent case met its own fail condition and that the parent's post-hoc narrowing was the defect A3 raised. The Proof states this inline and again in §7 ("Runtime code has zero elevation (PC-ONBD-05R PASS). The literal PC-ONBD-05 FAIL is recorded"), so nothing reads the FAIL as evidence of elevation in runtime code, nor the PASS as clearing the rule-2 defect.
3. **Both remedies, not a substitution.** The original offered the owner stage a choice: record FAIL against the literal predicate, **or** add a tagged post-declaration case limited to runtime code. Taking both is strictly more conservative than either, and it is what allows the substantive question and the process question to be answered separately. Declaring PC-ONBD-05R in the predeclaration file **before** the fetch, and stating there that it is "declared now; not a post-hoc narrowing", forecloses the obvious objection that 05R is 05's narrowing under a new name.
4. **Where the risk actually sits — the tally, not the finding.** The addendum's static tally counts nine executed cases, including both rows, and §8 also adds the parent correction. A reader consuming only the numbers sees one FAIL and cannot tell that it is a non-independent re-execution of an already-counted predicate. The comparable case in the same addendum is treated differently: **PC-PRIV-12 was labelled SUPPLEMENTARY and excluded from the tallies used for MASTER consumption**, while PC-ONBD-05 — equally a re-execution rather than an independent case — is included. That inconsistency, not double-counting, is the defect.

**Residual R-ONBD-1 (LOW, route PROOF):** tag PC-ONBD-05 in the tally as a predicate-integrity re-execution, on the same footing as the PC-PRIV-12 SUPPLEMENTARY exclusion, so that the static totals consumed by MASTER carry one row per independent proposition.
