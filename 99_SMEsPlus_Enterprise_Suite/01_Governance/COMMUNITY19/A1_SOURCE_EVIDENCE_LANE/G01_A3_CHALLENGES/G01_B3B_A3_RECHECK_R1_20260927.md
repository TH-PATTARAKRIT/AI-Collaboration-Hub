**Addendum position** (A2 R1 §6.3, REC R1 §6.2, Proof R1 §4): A3's CH-1b narrowing ("cross-company within the user's membership") holds for the interactive non-superuser trigger but not for the root queue-job trigger, because that environment is in superuser mode and the read probe always passes.

**A3 R1 re-derivation.** The status-push loop probes read access on the parent record in `self.env`, i.e. the triggering environment (`mail_message.py` L1364). The probe helper returns true unconditionally when the environment is in superuser mode (`models.py` L4123-4128 — the superuser test short-circuits before any rule evaluation, so no company set is ever read). An environment constructed for the superuser id is forced into superuser mode regardless of the flag passed (`environments.py` L64-67). The queue cron record names the root user (`ir_cron_data.xml` L9), the root reference is user id 1 (`base_data.sql` L134-135), the superuser id is 1 (`utils.py` L19), and the cron runner builds its environment with the job's user id and no explicit flag (`ir_cron.py` L482). Therefore on the queue-job path the gate does not evaluate companies at all, and the company narrowing that follows from the empty-context semantics (`environments.py` L266-283) cannot bound it. Exposure on that path is bounded only by what serialisation under each recipient's user reads, and the with-user helper does drop superuser mode (`models.py` L5993-6001).

**RULING: the addendum is RIGHT; the original A3 challenge (CH-1b as applied to REC-MAIL-11 / REC-MAIL-38) was overbroad and is not sustained for path (b).** REC R1's split into (a) interactive and (b) root queue-job is the correct reconciliation, and both paths must be carried separately downstream. Two bounded observations added, neither changing the ruling: (i) the with-user helper preserves superuser mode when the recipient's own user is the superuser, so if an author partner's main user were the root user, serialisation would also run elevated — a narrow extra leg for PC-MAIL-05R; (ii) the seeded root user row is inactive, which makes (i) unlikely but not excluded by the source read. Neither is evidence of disclosure; runtime still decides (PC-MAIL-05R outcomes (i)-(iii)).

### 5(b) `http_routing` R06 — decline to extend to unmatched paths

**Addendum position** (Proof R1 §3): R06 is not extended because the canonical-slug redirect runs in pre-dispatch for a matched endpoint only, so an unmatched path has no reachable behaviour to test.

**A3 R1 re-derivation.** The parent PC-HROU-R06 tests the slug-canonicalisation redirect on a multilang route carrying a record argument (old slug after rename, bare id, POST). That redirect is implemented in the pre-dispatch hook, guarded by the frontend-multilang flag, and it rebuilds the URL from the matched rule and its resolved arguments (`ir_http.py` L483-513). Pre-dispatch is only ever reached with a rule and args, i.e. after a successful match. On an unmatched path the match step raises not-found after forcing the frontend flags true (L476-480) and control passes to the frontend error handler (L570 onward); no rule and no record arguments exist, so no slug can be rebuilt or compared.

**RULING: the addendum is RIGHT; A3's original recommendation to extend R06 to unmatched paths rested on a premise that the source does not support, and the decline is correctly documented as DISPUTED-in-part rather than silently dropped.** The legitimate residual behind that recommendation — off-host redirect targets on unmatched paths — is the R05 concern, and it *is* extended (PC-HROU-R05b). Supporting static observation (strengthens R05b's expected result, does not replace the runtime test): the unmatched-path redirects use the framework redirect helpers whose local flag defaults to true and which strip scheme and network location and re-anchor the path (`http.py` L2100-2114); the slash-merge redirect passes the local flag explicitly (`ir_http.py` L394-396).
