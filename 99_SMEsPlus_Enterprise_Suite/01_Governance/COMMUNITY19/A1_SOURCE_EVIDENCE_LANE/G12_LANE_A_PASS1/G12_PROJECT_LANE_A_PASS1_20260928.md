### 2.1 Manifest / dependencies / purpose
1. WHAT: `project` ("Project") is the base module for organizing and planning projects composed of tasks. WHY: it is the system's single source of truth for "what work is planned, who is doing it, and how far along is it" for internal and portal-shared collaborators. Category Services/Project, `application: True`, `post_init_hook`/`uninstall_hook` (module-level setup/teardown logic, not traced in depth), license LGPL-3. (`__manifest__.py`)
2. Declared dependencies (dependency relationships only, not group membership): `analytic` (this pilot's own G03 anchor — directly confirmed, not inferred, since `project.project` inherits `analytic.plan.fields.mixin`, finding 4), `base_setup`, `mail`, `portal`, `rating`, `resource` (this pilot's G01 anchor family), `web`, `web_tour`, `digest`. Notably `project` does **not** depend on `sale`, `hr_timesheet`, or `purchase` — timesheet integration (`hr_timesheet`/`sale_timesheet`), sale-order-to-project integration (`sale_project`), and purchase-to-project integration are all confirmed to live in separate, dependent modules, directly corroborating the roster note already recorded in `LANE_A_CONTROL/GMVQ_EVIDENCE_SOURCE_REGISTRY.tsv` for G12 ("`hr_timesheet`, `sale_project`, `sale_timesheet` are named as important Project/Service bridge targets but membership is... not credited"). This Pass-1 evidence does not change that non-credit; it independently confirms, from the manifest itself, why those three names are bridge candidates rather than dependencies of the anchor module. (`__manifest__.py`)
3. `data` installs security, then digest data, a burndown-chart report view, an analytic-account view, a rating view, project-update views/templates, project-stage views, a share-wizard view, then task-type/project/task/role/tag/milestone/partner/settings/mail-activity views, then the project-sharing (external-collaborator) view/template surface, another report view, cron/mail-subtype/mail-template/project data, a tour, 3 more wizard views, and `views/project_menus.xml` last. Assets: a large `web.assets_backend` bundle with 9 explicit `remove`+relocate-to-`web.assets_backend_lazy` entries (task activity/graph/pivot/analysis views, burndown chart, project-activity view, dark-mode SCSS) — the same deliberate lazy-load performance pattern already seen in `crm`'s manifest, applied here more extensively; a separate `project.webclient` asset bundle re-includes a large slice of the core `web` framework's own assets plus `html_editor`/`mail`/`bus`/`web_tour`/`portal` assets, specifically to support the standalone external project-sharing webclient. (`__manifest__.py`)

### 2.2 Data — models, inheritance, key fields, identity/uniqueness
4. `project.project` `_inherit`s six mixins: `portal.mixin`, `mail.alias.mixin` (a project-specific incoming-mail alias, a mixin none of this pilot's other 7 confirmed anchors inherit), `rating.parent.mixin`, `mail.activity.mixin`, `mail.tracking.duration.mixin` (`_track_duration_field = 'stage_id'`), and **`analytic.plan.fields.mixin`** — this last mixin is `project`'s own direct, confirmed exercise of this pilot's G03 `analytic` anchor's extension point (the same class of cross-anchor mixin-reuse finding already recorded for `product.catalog.mixin` across `stock`/`mrp`/`purchase`/`sale`, and for `account.analytic.applicability.selection_add` in `purchase`). (`models/project_project.py`)
5. Task counts (`task_count`/`open_task_count`/`closed_task_count`) are computed via a single private helper `__compute_task_count()` parameterized by field name and an additional domain, rather than three separate ad hoc compute methods — `open_task_count` filters on `project.task.OPEN_STATES` and excludes template subtasks; `closed_task_count` filters on the module-level `CLOSED_STATES` constant (finding 7). This is a code-reuse pattern worth noting for A1's implementation-quality observations, not a business rule per se. (`models/project_project.py`)
6. **`project.task` maintains two independent lifecycle axes on the same record**: `stage_id` (a per-project-configurable Kanban stage, `project.task.type`, `group_expand`-driven) and a separate `state` Selection field — `01_in_progress` / `02_changes_requested` / `03_approved` / `1_done` / `1_canceled` (via the `CLOSED_STATES` dict, unpacked into the selection) / `04_waiting_normal` — this `state` field is itself `compute='_compute_state'`, `store=True`, `readonly=False` (i.e. computed-but-user-overridable, the same "computed-but-overridable" pattern already recorded for `crm.lead`'s contact fields). This is a materially different design from every other anchor examined in this pilot: `stock.picking`/`mrp.production`/`purchase.order`/`sale.order` each use a single `state` field as both the Kanban-grouping and the lifecycle-authority field, whereas `project.task` deliberately separates "which Kanban column is this in" (`stage_id`, free-form per project) from "what is its approval/closure status" (`state`, a fixed cross-project vocabulary) — flagged as a significant cross-anchor architecture-comparison finding for A1. (`models/project_task.py`)
7. `personal_stage_id` (`project.task.stage.personal`, `compute_sudo=False`) provides a **third**, per-viewing-user personal Kanban placement for a task shared across multiple assignees — independent of both `stage_id` (project-level) and `state` (approval-status) — i.e. the same task can simultaneously show a different Kanban column to each of its assignees while sharing one project-level stage and one approval state. This is a materially more complex per-user-view data model than seen in any other confirmed anchor in this pilot. (`models/project_task.py`, `models/project_task_stage_personal.py`)
8. Constraint methods identified via `grep`: `@api.constrains('company_id', 'partner_id')`, `@api.constrains('child_ids', 'project_id')`, `@api.constrains('depend_on_ids')` (task-dependency-graph integrity — presumably cycle prevention, not independently re-derived in this pass), `@api.constrains('parent_id')` (subtask-parent integrity) on `project.task`; `@api.constrains('stage_id')` and `@api.constrains(lambda self: self._get_plan_fnames())` (a dynamic analytic-plan-field constraint, consistent with the `analytic.plan.fields.mixin` inheritance in finding 4) on `project.project`. Exact constraint-body logic was not independently re-derived for any of these 6 — signature/decorator identification only, a depth gap flagged explicitly (mirroring the discipline already used for `purchase_order_line.py`'s constraints in this pilot). (`models/project_task.py`, `models/project_project.py`)

### 2.3 Business rules / states / lifecycle / exceptions

Method bodies were identified by signature only in this pass — depth gap. (`models/project_project.py`)
10. Dependency/subtask actions on `project.task` (`action_dependent_tasks`, `action_open_subtasks`, `action_unlink_recurrence`, `action_recurring_tasks`) and project-sharing-specific counterparts (`action_project_sharing_open_task`, `action_project_sharing_open_subtasks`, `action_project_sharing_open_blocking`, `action_project_sharing_recurring_tasks`) exist as **parallel, separately-named action pairs** — one action per feature for the internal backend view and a second, differently-scoped action for the external project-sharing (portal-collaborator) view. This "duplicate action per surface" pattern is a notable implementation convention distinguishing `project`'s security-boundary design from every other anchor examined (none of which expose a comparable dual internal/external action surface at this granularity). Method bodies were identified by signature only — depth gap. (`models/project_task.py`)

### 2.4 Security
11. `security/project_security.xml` defines 6 groups: a `res.groups.privilege` ("Project") with a `group_project_user`/`group_project_manager` pair (the same "User"/"Administrator" privilege-tier naming pattern already recorded for `stock`, `mrp`, and `purchase` in this pilot), plus 4 independent feature-toggle groups (`group_project_stages`, `group_project_recurring_tasks`, `group_project_task_dependencies`, `group_project_milestone`). Named `ir.rule`s (31 counted via `grep` on `<field name="name">` values) include multi-company rules for both `project.project` and `project.task.type`, "project manager: see all"/"employees: following required for follower-only projects" pairs for both projects and tasks, and a "project manager: see all tasks linked to a project or its own tasks" rule — the highest `ir.rule` count of any of this pilot's 8 confirmed anchors so far (`purchase` 8, `sale` 24, `crm` 8, `project` 31), consistent with `project`'s dual internal/portal/project-sharing-collaborator access model (findings 6, 7, 10) requiring the most granular record-visibility scoping. Exact `domain_force` content not individually re-verified — depth gap, mirroring every other confirmed anchor's own Pass-1 file. (`security/project_security.xml`)

Neither file's row content was read in depth in this pass beyond confirming presence; flagged as a depth gap. (`security/ir.model.access.csv`, `security/ir.model.access.xml`)

### 2.5 UI / customer-portal / project-sharing surfaces
13. `controllers/portal.py` exposes 9 routes across 2 distinct customer/collaborator-facing surfaces: a standard portal surface (`/my/projects`, `/my/projects/<id>` — `auth="public"`, the same token-gated pattern as `purchase`/`sale`'s own portal-detail routes —, `/my/tasks`, `/my/tasks/<id>`) and a separate, more privileged **project-sharing** surface (`/my/projects/<id>/project_sharing` and its `<path:subpath>` variant, `auth='user'`; `/my/projects/<id>/task/<id>`, `auth='public'`; `/my/projects/<id>/task/<id>/subtasks` and `/recurrent_tasks`, both `auth="user"`) plus a dedicated `POST` image-upload route (`/project_sharing/attachment/add_image`, `auth='user'`) for the project-sharing chatter. This two-tier portal/project-sharing surface (backed by `project.collaborator`, finding on `models/project_collaborator.py`) is a materially richer and more privileged customer-facing access model than the read/accept-oriented portal surfaces seen in `purchase`/`sale` — external project-sharing collaborators can apparently create content (attachments, per the upload route), not merely view/accept/decline documents. RISK: A1 should independently verify the `project.collaborator`/portal-mixin access-check boundary for these `auth='user'`/`auth='public'` routes, since the write-capable upload route in particular represents a larger attack surface than any route seen in this pilot's other 7 anchors. (`controllers/portal.py`, `models/project_collaborator.py`)
14. `controllers/project_sharing_chatter.py` (imported directly into `project_task.py` per its own `__init__.py`'s import list — not merely a generic controller import) implements the chatter-access logic specifically for the project-sharing surface; fetched and hash-verified but not read in depth in this pass — flagged as a depth gap given its direct relevance to finding 13's RISK note. (`controllers/project_sharing_chatter.py`)
