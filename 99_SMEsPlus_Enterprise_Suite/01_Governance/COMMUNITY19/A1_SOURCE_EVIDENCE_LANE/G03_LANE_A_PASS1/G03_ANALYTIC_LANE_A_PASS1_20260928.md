## 2. Findings by A1 completion-card section

### 2.1 Manifest / dependencies / purpose
1. WHAT: `analytic` ("Analytic Accounting") defines a parallel, configurable-dimension cost/revenue tracking layer ("analytic accounts"/"analytic plans") that is linked to, but independent from, the general ledger. WHY: lets an organization slice costs/revenues by project, department, or any other user-defined dimension without touching the chart of accounts. Category Accounting/Accounting, license LGPL-3. (`__manifest__.py`)
2. Declared dependencies (dependency relationships only, not group membership): `base`, `mail` (the account model inherits `mail.thread`), `uom` (analytic lines carry a `product_uom_id`). (`__manifest__.py`)
3. `data` installs security, then 4 view files, then `data/analytic_data.xml`; a separate `demo` key installs `data/analytic_account_demo.xml` (not fetched). Assets split three ways: eager backend components/services/views, a `web.assets_backend_lazy` bucket specifically for the graph/pivot view renderers (deliberately deferred/lazy-loaded), and a `web.assets_unit_tests` bucket. (`__manifest__.py`)

### 2.2 Data — models, inheritance, key fields, identity/uniqueness
4. `account.analytic.plan` is a self-referential hierarchy (`_parent_store`) of named "dimensions" (e.g. "Project", "Department"). Each **root** plan gets its own **dynamically created database column** on any model using the mixin (`_sync_plan_column`/`_strict_column_name`: `account_id` for the special "Project" root plan, `x_plan{id}_id` for every other root plan) — i.e. the set of analytic dimensions is not fixed at install time; it is extended at runtime by creating new `ir.model.fields` rows (`ttype='many2one'`) and, for root plans, a real Postgres column + index. Non-root (child) plans instead get a computed, non-stored "hierarchy" field for group-by only. RISK: this is significant runtime schema mutation triggered by ordinary record CRUD (`write()`/`unlink()` on `account.analytic.plan`), not by a module upgrade — A1 should confirm what access is required to create/reparent a plan (see finding 13) given the DDL this triggers. (`models/analytic_plan.py`)
5. `account.analytic.account` `_inherit`s `mail.thread` (chatter/tracking). Key fields: `name` (required, translated, tracked), `code`, `active` (default True, tracked), `plan_id` (required Many2one to `account.analytic.plan`), `root_plan_id` (related, stored), `partner_id` (tracked, `check_company=True`), computed `balance`/`debit`/`credit` (aggregated from `account.analytic.line`, converted to company currency, optionally date-bounded via `from_date`/`to_date` context keys). A `_check_company_consistency` constraint blocks changing an account's `company_id` once it has analytic lines outside that company's hierarchy. (`models/analytic_account.py`)
6. `analytic.mixin` (an `AbstractModel`, meant to be inherited by any business-document line model — e.g. invoice lines, PO lines, etc.) adds a single JSON field `analytic_distribution` (`{"account_id[,account_id...]": percentage, ...}`, i.e. one row can be split across a *combination* of accounts from different plans, each combination summing to a percentage) plus a computed `distribution_analytic_account_ids` (M2M, searchable) and a Postgres GIN index (added in `init()`) over the JSON keys for search performance. `analytic.plan.fields.mixin` (a separate abstract model, used specifically by `account.analytic.line`) instead exposes the dynamically-created per-plan columns directly plus a magic `auto_account_id` computed/inverse field that resolves to whichever plan column is active given an `analytic_plan_id` context key. (`models/analytic_mixin.py`, `analytic_line.py`)
7. `account.analytic.line`: required `name`/`date`/`amount` (Monetary), `unit_amount` (Float quantity), `product_uom_id` (→ `uom.uom`, this module's cross-anchor dependency inside G03's own named-anchor set), `partner_id`, `user_id`, `company_id` (required, readonly, defaulted), a single-value `category` selection currently offering only `('other', 'Other')` (extension point for dependent modules to add e.g. 'invoice'/'timesheet'), and a constraint (`_check_account_id`) requiring at least one of the dynamic plan columns to be set. (`models/analytic_line.py`)
8. `account.analytic.distribution.model`: `_inherit`s `analytic.mixin`; stores reusable "if partner X / category Y / company Z, apply this distribution" default rules, matched by `_get_applicable_models`/`_create_domain` (each condition matches the stored value or `False`/wildcard) and merged (`_get_distribution`) in a way that later, more-specific matches only fill in the plans not already covered by an earlier, higher-priority match (`_merge_distribution`'s `'__update__'` mechanism). (`models/analytic_distribution_model.py`)
9. `ir.config_parameter` extension: the system parameter `analytic.project_plan` (which root plan is "the" project plan, referenced throughout as `_get_all_plans()`'s privileged first element) cannot be set to anything other than a valid, non-subplan `account.analytic.plan` id — enforced by raising `UserError` in `write()`, with a full column-resync side effect on both the old and (implicitly, via `_sync_all_plan_column`) new plan whenever it changes. `account.analytic.plan.__get_all_plans` itself raises `UserError` if this parameter has never been set to an existing plan — i.e. this module's dynamic-column machinery hard-depends on that one system parameter being correctly seeded. (`models/ir_config_parameter.py`, `models/analytic_plan.py`)

### 2.3 Business rules / states / lifecycle / exceptions
10. Applicability scoring: each plan (root only) has a `default_applicability` (optional/mandatory/unavailable, company-dependent) overridable per business-domain/company by `account.analytic.applicability` rows, resolved by a simple additive scoring function (`_get_applicability`/`_get_score`, base score 0.5, +1/-1 for a matching/non-matching `business_domain`) — the current fetch set exposes only one `business_domain` selection value (`'general'`/"Miscellaneous"), so the full scoring mechanism's practical effect (multiple competing domains) is not exercised within this module alone; other modules are expected to extend the selection. (`models/analytic_plan.py`, comment on the scoring weights: "Adapt each criterion's weight if new ones are added.")
11. Mandatory-distribution validation: `_validate_distribution` (only invoked when a caller explicitly sets `context.get('validate_analytic')`) sums the distributed percentage per *root plan* and raises `ValidationError` if any plan marked `applicability == 'mandatory'` does not sum to exactly 100% (within the `Percentage Analytic` decimal precision) — this is opt-in per caller, not enforced unconditionally on every write to `analytic_distribution`. (`models/analytic_mixin.py`)
12. Changing an account's plan, or reparenting/deleting a plan, triggers a data-migration side effect: `_update_accounts_in_analytic_lines` moves existing `account_analytic_line` rows from the old dynamic column to the new one via a raw SQL `UPDATE`, but first blocks the operation with a `RedirectWarning` (offering a link to inspect the affected lines) if the move would overwrite non-null data in the destination column — i.e. data-loss prevention is enforced at the account/plan level, but once past that guard the actual move is an unguarded bulk SQL statement, not a per-record business validation. (`models/analytic_account.py`, `analytic_plan.py`)
13. `account.analytic.distribution.model._check_company_accounts` (a raw-SQL `@api.constrains`) blocks saving a distribution-model row that references a company-specific analytic account from a model that is itself company-agnostic or assigned to a different company — preventing a shared/default distribution template from silently pulling in another company's analytic account. (`models/analytic_distribution_model.py`)
14. Cache invalidation discipline: `get_relevant_plans` (an expensive, request-scoped-cached query over plans) is explicitly popped from cache on every `create`/`write` to `account.analytic.plan` or `account.analytic.applicability`, and on `ir.config_parameter` writes to `analytic.project_plan` — an omission here would be a stale-plan-list defect class; A1/A2 should treat any future change to these models as needing to preserve this invalidation. (`models/analytic_plan.py`, `analytic_distribution_model.py`... via `ir_config_parameter.py`)

### 2.4 Security
15. One group: `group_analytic_accounting` ("Analytic Accounting"), exposed as a settings checkbox (`res_config_settings.py`) implying it. All 5 ACL rows (covering `account.analytic.account`, `.line`, `.plan`, `.applicability`, `.distribution.model`) grant full CRUD to this single group and nothing to any other group — i.e. this module has no read-only/manager split of its own; any finer-grained access control is expected to be layered on by dependent modules or record rules. (`security/ir.model.access.csv`, `models/res_config_settings.py`)
16. Multi-company: 4 `ir.rule` record rules (account, line, applicability, distribution model) all scope to the current user's companies; three of the four (account/applicability/distribution model) additionally allow records with no company set (`company_id = False`) to remain visible across companies via `parent_of`, while the line rule (`account.analytic.line`) requires the line's own company to be `in company_ids` with no such "no-company" exception. (`security/analytic_security.xml`)
