## 2. Findings by A1 completion-card section

### 2.1 Manifest / dependencies / purpose
1. WHAT: `product` ("Products & Pricelists") is the base master-data module for sellable goods/services, product variants (via attributes), vendor pricing, and multi-rule pricelists. WHY: it is the single source of truth for "what can be sold/bought, in which unit, at what base and rule-adjusted price." Category Sales/Sales, license LGPL-3. (`__manifest__.py`)
2. Declared dependencies (dependency relationship only, not group membership): `base`, `mail` (chatter/activity mixins on several models), `uom` — this same G03 pilot's other confirmed anchor module. (`__manifest__.py`)
3. `data` installs seed data, then security, then wizards' views, then ~14 view files (with an explicit ordering note that `product_views.xml` must load after `product_tag_views.xml`), then 5 report files. A separate `demo` key installs 5 demo files (attributes, category, products, documents, supplierinfo) not fetched here. Assets: eager JS/SCSS for the product form/catalog/name-and-description widgets, a separate report-only SCSS bundle, and a unit-test bundle. (`__manifest__.py`)

### 2.2 Data — models, inheritance, key fields, identity/uniqueness
4. `product.template` `_inherit`s `mail.thread`, `mail.activity.mixin`, `image.mixin`. `type` is a required selection (`consu`/`service`/`combo`, default `consu`) — note this Odoo version has collapsed the historical "storable vs. consumable" distinction into a single `consu` goods type (inventory tracking is expected to live in a dependent module, e.g. `stock`). `list_price` (Sales Price, tracked) and `standard_price` (Cost, computed/inverse, gated by `groups="base.group_user"`) are the two price anchors; `uom_id` defaults to the seeded `uom.product_uom_unit` external ID (a direct cross-reference into this pilot's `uom` anchor module) via an `ormcache`d default-getter, and is itself required. `categ_id` groups into `product.category`. `combo_ids` (M2M to `product.combo`) only applies when `type == 'combo'`. (`models/product_template.py`)
5. `product.product` `_inherits` `product.template` (`product_tmpl_id`, delegation inheritance — every template field is directly readable/writable on a variant) and additionally `_inherit`s `mail.thread`/`mail.activity.mixin` in its own right. `combination_indices` (computed, stored, indexed) is a canonicalized string key of the variant's `product_template_attribute_value_ids`, and a `UniqueIndex` (`_combination_unique`) enforces uniqueness of `(product_tmpl_id, combination_indices)` among **active** variants only — i.e. the same attribute-value combination can exist twice if one copy is archived. `barcode` is unique-checked in Python (`_check_barcode_uniqueness`, `@api.constrains`), not by a DB constraint, and is explicitly cross-checked against `product.uom` (packaging) barcodes too, company-scoped. (`models/product_product.py`)
6. Variant configuration chain: `product.attribute` (has a `create_variant` selection — `always`/`dynamic`/`no_variant` — governing whether/when adding this attribute actually spawns new `product.product` rows) → `product.attribute.value` (one concrete value) → `product.template.attribute.line` (which attribute+which subset of its values are configured on one template) → `product.template.attribute.value` (materialized line×value row, carrying `price_extra` and `exclude_for`) → `product.product.product_template_attribute_value_ids` (which materialized values compose one variant). `product.attribute.custom.value` holds a free-text answer when a value is marked `is_custom`. `product.template.attribute.exclusion` records "if this template.attribute.value is chosen, these other template.attribute.values become invalid," used to prune combinations. (`models/product_attribute*.py`, `product_template_attribute_*.py`)
7. `product.combo` (a reusable, named "choose one of these options" group) and `product.combo.item` (one option inside it, with its own `extra_price`, referencing a non-combo `product.product` via `domain=[('type', '!=', 'combo')]`) exist to let a `type == 'combo'` template be sold as a bundle of independently-priced choices; `product.combo.base_price` is computed as the **minimum** currency-converted `lst_price` across its items, described in its own help text as a proration anchor so the combo's own price stays independent of which option the customer later picks. (`models/product_combo.py`, `product_combo_item.py`)
8. `product.pricelist` (`_inherit`s `mail.thread`+`mail.activity.mixin`) holds an ordered `item_ids` (`product.pricelist.item`, domain-filtered to only active-product/active-template rules) and exposes `_get_product_price`/`_get_products_price`/`_get_product_price_rule`/`_get_product_rule`, all thin wrappers around the core `_compute_price_rule(products, quantity, currency=, uom=, date=, compute_price=)`, which converts the requested quantity into the product's own UoM before matching rules (since `min_quantity` and related pricelist fields are expressed in that UoM). (`models/product_pricelist.py`)
9. `product.pricelist.item`: `applied_on` (`3_global`/`2_product_category`/`1_product`/`0_product_variant`, most-specific-first ordering built into `_order`) scopes a rule; `base` (`list_price`/`standard_price`/`pricelist`) selects the base price source, with `base_pricelist_id` required when `base == 'pricelist'`; `compute_price` (`percentage`/`formula`/`fixed`) selects which of `fixed_price` / `percent_price` / (`price_discount`+`price_round`+`price_surcharge`+`price_min_margin`/`price_max_margin`) applies; `price_markup` is a computed/inverse mirror of `price_discount` specifically for the `standard_price` (cost) base, so the UI can show "markup over cost" instead of "discount off cost" without a separate stored field. (`models/product_pricelist_item.py`)
10. `product.supplierinfo`: vendor-specific price/lead-time/min-qty per `(partner_id, product_id-or-product_tmpl_id)`, `_order`ed so the cheapest-then-highest-min-qty row sorts first (a "best vendor for this quantity" heuristic implied by ordering, not enforced by a dedicated selection method in this module). `product_uom_id`/`product_tmpl_id`/`product_id` are all `precompute`d, stored, user-overridable computed fields that default from whichever of variant/template is set. (`models/product_supplierinfo.py`)
11. `product.document` `_inherits` `ir.attachment` (delegation), adding only `active`/`sequence`; deleting a `product.document` cascades to delete its underlying `ir.attachment`. `ir.attachment.create()` is extended (in a separate file, `models/ir_attachment.py`) to auto-create a matching `product.document` whenever an attachment lands in a product's/template's chatter (unless a context flag opts out) — the two files together implement a bidirectional attachment↔document sync. (`models/product_document.py`, `ir_attachment.py`)
12. `product.uom`: a product-specific "packaging" record — a `uom.uom` reference plus a required, uniquely-constrained `barcode` — extending `uom.uom` (in this module) with a `product_uom_ids` One2many so a base unit of measure can enumerate every packaging barcode defined against it. Its own barcode-uniqueness constraint additionally cross-checks against `product.product` barcodes (see finding 5), and vice versa — the two constraints are mutually reinforcing, not just parallel. (`models/product_uom.py`, `uom_uom.py`)
13. `product.tag`: uniquely-named (`_name_uniq` constraint), attachable to templates and/or variants, with a `visible_to_customers` flag and a computed union `product_ids` covering both attachment paths. (`models/product_tag.py`)

### 2.3 Business rules / states / lifecycle / exceptions
14. Combo integrity: a `type == 'combo'` template must have at least one `combo_ids` entry (`_check_combo_ids_not_empty`); if such a template is also sellable (`sale_ok`), every product inside every one of its combos must itself be sellable (`_check_sale_combo_ids`) — i.e. a sellable combo cannot silently expose an unsellable option. Symmetrically, `product.combo` itself requires ≥1 item and forbids duplicate products within one combo (`_check_combo_item_ids_not_empty`/`_check_combo_item_ids_no_duplicates`), and `product.combo.item` forbids nesting a combo inside a combo (`_check_product_id_no_combo`, both by field domain and by an explicit constraint). (`models/product_template.py`, `product_combo.py`, `product_combo_item.py`)
15. Variant lifecycle is driven by attribute-line CRUD, not directly by user action on `product.product`: creating/writing/unlinking a `product.template.attribute.line` calls `_update_product_template_attribute_values()`, which reconciles `product.template.attribute.value` rows against the line's current `value_ids` (creating new ones, archiving/unlinking removed ones, reactivating previously-archived ones) and then triggers `product_tmpl_id._create_variant_ids()` — the actual `product.product` rows are generated from the resulting combination space. Attribute deletion/archiving is guarded: a `product.attribute`, `product.attribute.value`, or `product.template.attribute.value` that is already used on a product raises `UserError` on delete (via `@api.ondelete`), or, where safe (an archived/inactive path exists), silently archives instead of raising. (`models/product_template_attribute_line.py`, `product_attribute.py`, `product_attribute_value.py`, `product_template_attribute_value.py`)
16. Attribute-type change guard: `product.attribute.create_variant` cannot be changed on `write()` once the attribute is used on any product (`UserError`, explicit note in the field's own help text: recomputing existing variants after such a change "might take too long" and would change products "without the user knowing about it") — this is a deliberate, documented business rule protecting data integrity over convenience. (`models/product_attribute.py`)
17. Pricelist recursion guard: `product.pricelist.item._check_pricelist_recursion` performs a depth-first search over `base == 'pricelist'` chains (rule A bases its price on pricelist B, which has a rule based on pricelist A, …) and raises `ValidationError` naming the full cycle path if one exists — this is a real graph-cycle-detection algorithm implemented in this module, not a simple self-reference check. A separate constraint (`_check_margin`) requires `price_min_margin <= price_max_margin`, and `_check_date_range` requires `date_start < date_end` when both are set. (`models/product_pricelist_item.py`)
18. Pricing computation order (formula path, `_compute_price`): base price → apply discount or markup (sign convention differs depending on whether `base == 'standard_price'`) → round to `price_round` → add `price_surcharge` → clamp with `price_min_margin`/`price_max_margin` relative to the pre-adjustment base — the ordering (round *before* surcharge) is explicit in the field's own help text ("Rounding is applied after the discount and before the surcharge") and is a business-meaningful sequencing choice A1 should treat as authoritative. (`models/product_pricelist_item.py`)
19. Multi-company pricelist creation: `res.company` auto-creates (or reactivates a previously-archived) default pricelist for every company, but only when `product.group_product_pricelist` is enabled; `write()` on a company's `currency_id` defers this auto-creation (via a context flag) until after the currency change is committed, specifically to avoid creating a pricelist with the pre-change currency. Disabling multi-currency/archiving a currency conversely archives every pricelist in that currency (`res_currency.py`). Enabling the pricelist group also re-runs the per-company creation/reactivation pass (`res_config_settings.set_values`). (`models/res_company.py`, `res_currency.py`, `res_config_settings.py`)
20. Partner-pricelist resolution (`res.partner`): `property_product_pricelist` is a computed, non-`company_dependent`-declared field that nonetheless *behaves* like one via `_get_partner_pricelist_multi` (delegated to `product.pricelist`, not read here), with its inverse (`_inverse_product_pricelist`) writing to a real `company_dependent` shadow field (`specific_property_product_pricelist`) only when the chosen value differs from the country-based default — i.e. an explicit "don't store what a computed default would already give you" optimization, documented in the field's own inline comment about a two-level `ir.config_parameter` fallback (per-company, then global) it participates in. (`models/res_partner.py`)

### 2.4 Security
21. `security/product_security.xml` defines a `res.groups.privilege` ("Products") plus three groups: `group_product_pricelist` ("Basic Pricelists"), `group_product_variant` ("Manage Product Variants"), and `group_product_manager` ("Create") — the manager group is implied by `base.group_system` and pre-assigned to `base.user_root`; `base.user_admin` is separately, explicitly granted it. (`security/product_security.xml`)
22. 24. Controller-side: `catalog.py`'s two JSON-RPC routes both require `auth='user'` and delegate straight into `order.with_company(order.company_id)._get_product_catalog_order_line_info`/`_update_order_line_info` on a **caller-supplied `res_model`** — i.e. this controller trusts the calling model to enforce its own record-level access via ORM `browse()`/method dispatch rather than checking anything about `res_model` itself; RISK: A1 should confirm every model that implements `product.catalog.mixin` correctly gates `_get_product_catalog_order_line_info`/`_update_order_line_info` by the order record's own read/write access, since this controller performs no independent authorization check of its own beyond `auth='user'`. `product_document.py`'s upload route restricts `res_model` to exactly `('product.product', 'product.template')` (`is_model_valid`) and separately checks `record.has_access('write')` before accepting an upload — a stronger, explicit check than the catalog controller's. `pricelist_report.py`'s export route is `auth='user'`, `readonly=True`, with no model/record access check of its own (it operates on a client-supplied JSON export spec, not a browsed record). (`controllers/catalog.py`, `product_document.py`, `pricelist_report.py`)
