## 2. Findings by A1 completion-card section

### 2.1 Manifest / dependencies / purpose
1. WHAT: `mrp` ("Manufacturing") is the base module for producing goods from components: Bills of Materials (recipes/kits), Manufacturing Orders, work orders/routings, work centers, and reverse manufacturing (unbuild). WHY: it is the system's single source of truth for "how is this product built, from what, and where." Category Supply Chain/Manufacturing, `application: True`, license LGPL-3. (`__manifest__.py`)
2. Declared dependencies (dependency relationships only, not group membership): `product` and `stock` — both this same pilot's other confirmed anchors (G03 and G05 respectively) — plus `resource` (work-center scheduling/calendar). (`__manifest__.py`)
3. Lifecycle hooks: `pre_init_hook` (`_pre_init_mrp`), `post_init_hook` (`_create_warehouse_data`), `uninstall_hook` — the same "custom Python at install/uninstall" pattern already observed in `stock` (this pilot's G05 anchor); bodies not fetched here (out of scope). `data` installs security, then digest/mail-template/mrp/mail-subtype seed data, then 7 wizard view files, then ~13 model view files (with an inline comment noting `wizard/stock_replenishment_info.xml` must load after `views/mrp_workcenter_views.xml`), then 9 report files. A separate `demo` key installs 1 demo file. Assets: eager JS/XML/SCSS bundle plus a Tour-test and unit-test bucket. (`__manifest__.py`)

### 2.2 Data — models, inheritance, key fields, identity/uniqueness
4. `mrp.bom`: `type` is a required selection (`normal` "Manufacture this product" / `phantom` "Kit," default `normal`) — a `phantom` BoM is Odoo's mechanism for "this is just a bundle of components, not a separately-manufactured item" (its components are exploded directly into whatever order references the kit, rather than creating a separate MO — confirmed only by the field's own naming/help text, not traced through to the exploding logic in this pass). `product_tmpl_id` is domain-restricted to `type == 'consu'` (this pilot's collapsed goods/service/combo product typing, cross-referenced from `product`'s own Lane A Pass-1 file); an optional `product_id` narrows a template-level BoM to one specific variant. `bom_line_ids` (components) and `byproduct_ids` (secondary outputs) are separate One2many sets on the same BoM. (`models/mrp_bom.py`)
5. `mrp.production` (the Manufacturing Order): required `state` selection (`draft → confirmed → progress → to_close → done` / `cancel`, help text explicitly distinguishing "In Progress" as "the production has started (on the MO **or** on the WO)" — i.e. a work-order-level start can move the parent MO into progress even before the MO's own top-level action is invoked) plus a separately computed `reservation_state` (`confirmed`/`assigned`/`waiting`, described as "Manufacturing readiness... as per bill of material configuration") and `components_availability_state` — three distinct, independently computed status axes layered on one record (state machine, material readiness, and a third component-availability signal not further traced in this pass). `move_raw_ids` (components consumed, domain-excluded from `inventory`-usage destination locations) and `move_finished_ids` (products/byproducts produced) are both computed, stored, user-overridable One2many sets onto `stock.move` — i.e. `mrp.production` does not itself hold quantities; it drives and reconciles against `stock.move`/`stock.move.line` records in this pilot's G05 anchor module. `mrp.production.group` (same file) is a lightweight grouping record for MOs split from a single order. (`models/mrp_production.py`)
6. `mrp.workorder`: `state` (`blocked`/`ready`/`progress`/`done`/`cancel`, computed, stored, default `ready`) is distinct from the MO's own `state`; a large block of `related=` fields (`product_id`, `product_tracking`, `production_availability`, `production_state`, `production_bom_id`, `qty_production`, `company_id`) explicitly mirrors parent-MO data onto the workorder purely "for views and domains," per inline comments — i.e. these are read-only projections, not independently meaningful business data on the workorder itself. `qty_producing`/`qty_produced`/`qty_remaining`/`qty_ready` track four distinct quantity concepts per workorder (currently-being-produced, already-done, still-to-do, and ready-to-start) rather than a single progress counter. `blocked_by_workorder_ids` (with its own `@api.constrains`) implies a dependency graph between workorders of the same MO — full graph-validation logic not traced in this pass. (`models/mrp_workorder.py`)
7. `mrp.workcenter` (+ `mrp.workcenter.tag`, `.productivity.loss.type`, `.productivity.loss`, `.productivity`, `.capacity`): a workcenter is both a schedulable resource (implying integration with the `resource` module dependency) and a productivity-tracking unit — `mrp.workcenter.productivity` rows log actual time spent per workorder against a `mrp.workcenter.productivity.loss`/`.loss.type` taxonomy (OEE-style loss categorization: e.g. planned downtime vs. unplanned vs. performance loss — categories themselves not enumerated in this pass). `mrp.workcenter.capacity` associates a per-product-or-category capacity/cycle-time override onto a workcenter. `alternative_workcenter_ids` (with its own `@api.constrains`) lets one workcenter designate substitutes for load-balancing — validation logic not traced in this pass. (`models/mrp_workcenter.py`)
8. `mrp.routing.workcenter`: the BoM-level operation-step template (which workcenter, in what sequence, with what expected duration) that `mrp.workorder` rows are instantiated from per MO — this file's own internal structure (fields/constraints) was not traced in this pass beyond class/model-name identification (only 216 lines; flagged as an evidence gap, not a confirmed absence of business rules). (`models/mrp_routing.py`)
9. `mrp.unbuild`: a required `state` selection (values not individually enumerated in this pass — grep only located the field, not its options) representing a reverse-manufacturing order that consumes a finished product and produces its components back — the inverse operation of `mrp.production`. (`models/mrp_unbuild.py`)
10. `product` extension (`models/product.py`, 489 lines, not read in depth beyond class-name identification and the wider PASS-1 scope note): adds BoM-related computed fields to `product.product`/`product.template` (e.g. BoM count, "is this product used as a component in any BoM" — exact field names not enumerated in this pass; flagged as an evidence gap). `product.document` extension adds `attached_on_mrp` (`hidden`/`bom`, default computed from a context flag) — a document attached to a product can additionally be surfaced specifically on its Bill of Materials view. (`models/product.py`, `product_document.py`)
11. `stock.rule` extension (`models/stock_rule.py`): adds `manufacture`/`manufacture_step`-family values to the `action` selection (`selection_add=[...]`, exact added values not individually enumerated in this pass — grep confirmed the extension point, not its full value list) and adds `_get_matching_bom` (resolve which BoM a procurement should use), `_get_stock_move_values`, `_get_date_planned`, `_get_lead_days` — i.e. a manufacture-route procurement is implemented as a `stock.rule` action, consistent with `stock`'s own push/pull rule architecture (this pilot's G05 anchor) rather than a separate procurement mechanism. (`models/stock_rule.py`)
12. `res.company` extension: `_create_unbuild_sequence`/`create_missing_unbuild_sequences` ensure every company has its own `mrp.unbuild`-coded `ir.sequence` (prefix `UB/`), with a backfill method (`create_missing_unbuild_sequences`) for companies that predate this module's installation — `_create_per_company_sequences` is overridden to call this automatically for newly created companies. (`models/res_company.py`)
