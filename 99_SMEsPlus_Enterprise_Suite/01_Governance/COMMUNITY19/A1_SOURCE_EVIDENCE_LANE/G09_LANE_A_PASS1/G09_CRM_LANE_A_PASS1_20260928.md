## 2. Findings by A1 completion-card section

### 2.1 Manifest / dependencies / purpose
1. WHAT: `crm` ("CRM") is the pipeline module for tracking leads and closing opportunities. WHY: it is the system's single source of truth for "who is a prospective/active deal, at what stage, with what probability of closing." Category Sales/CRM, `application: True`, license LGPL-3. (`__manifest__.py`)
2. Declared dependencies (dependency relationships only, not group membership): `base_setup`, `sales_team` (the same base dependency `sale` itself declares — both anchors share this common foundation module, per this pilot's G08 companion evidence), `mail`, `calendar`, `resource` (this pilot's G01 anchor family), `utm`, `web_tour`, `contacts`, `digest`, `phone_validation` — notably **not** `sale` itself; the reverse integration (creating a quotation from an opportunity) is confirmed to live in a separate, dependent module (`sale_crm`, seen by name in the PR#71 candidate bank list for this group and in the G08 candidate list as `G08_SALE_CRM`), the same non-dependence pattern already recorded for `purchase`↔`stock` and `sale`↔`stock`/`crm`. (`__manifest__.py`)
3. `data` installs security first, then lead-merge/prediction/lost-reason/stage/team/digest/action/cron/subtype/recurring-plan data, then a tour, then all 5 wizard views, then 12 view files (calendar, recurring plan, lost reason, stage, lead, team member, digest, mail activity plan/type, settings, partner, utm campaign), then 2 report view files, then team views, then menu views, then helper templates last. `demo` installs 5 demo files. Assets: a large `web.assets_backend` bundle with 2 explicit `remove`+relocate-to-`web.assets_backend_lazy` entries for the forecast graph/pivot views (a deliberate lazy-load performance pattern), plus test/unit-test bundles. (`__manifest__.py`)

### 2.2 Data — models, inheritance, key fields, identity/uniqueness
4. `crm.lead` `_inherit`s six mixins: `mail.thread.cc`, `mail.thread.blacklist`, `mail.thread.phone`, `mail.activity.mixin`, `utm.mixin`, `format.address.mixin`, and `mail.tracking.duration.mixin` (`_track_duration_field = 'stage_id'`) — a materially different, communication/tracking-heavy mixin set compared to `sale.order`'s or `purchase.order`'s portal/catalog-oriented mixin sets; no `portal.mixin` is inherited here, meaning `crm.lead` (unlike `sale.order`/`purchase.order`) has no built-in customer-portal access surface of its own. A single `type` Selection field (`lead`/`opportunity`, default computed from the `crm.group_use_lead` feature group) distinguishes an unqualified lead from an active opportunity on the **same model/table** — a materially different design from `sale`/`purchase`, which use a single model per document type rather than a type-flag on one shared model. (`models/crm_lead.py`)
5. **`crm.lead` has no `state` Selection field at all** — a materially different lifecycle-modeling choice from every other anchor in this pilot (`stock.picking`, `mrp.production`, `purchase.order`, `sale.order` all use an explicit `state` field). Lifecycle is instead modeled through three independent signals: `active` (Boolean, default `True`), `stage_id` (a `crm.stage` many2one with an `is_won` flag examined via `crm_stage.py`), and `probability` (Float, 0–100). "Lost" and "won" are business-level semantics layered on top of these fields by dedicated action methods (finding 8), not first-class stored states. (`models/crm_lead.py`)
6. `stage_id` is `group_expand='_read_group_stage_ids'`-driven and domain-scoped to `('team_ids', '=', False)` or the lead's own `team_id` — i.e. pipeline stages can be either global or team-specific, the same team-scoping pattern implied by `crm.team`'s presence in both this module and `sale`. `priority` uses a shared `crm_stage.AVAILABLE_PRIORITIES` constant (values/labels not independently re-verified in this pass — depth gap). (`models/crm_lead.py`)
7. A large set of computed, store=True, readonly=False "smart default" fields (`contact_name`, `partner_name`, `email_from`, `phone`, address fields, `lang_id`) are all recomputed from `partner_id`/`commercial_partner_id` via `_onchange_commercial_partner_id`/dedicated compute methods, then remain independently user-editable after computation — the same "computed-but-overridable" UX pattern seen in `purchase.order.line`'s own product-derived fields, applied here at a larger scale across nearly every identity/contact field on the lead. (`models/crm_lead.py`)

### 2.3 Business rules / states / lifecycle / exceptions
8. `action_set_lost()`: "Lost semantic: probability = 0 AND active = False" (module's own docstring) — implemented as `action_archive()` (soft-delete via `active=False`) plus `probability`/`automated_probability` reset to 0, with `**additional_values` allowing the calling wizard (`crm_lead_lost.py`) to attach a lost-reason. `action_set_won()`: "Won semantic: stage.is_won (AND probability = 100 but implied)" (module's own docstring) — implemented as `action_unarchive()` plus a per-lead search for the nearest `is_won` stage at or after the lead's current pipeline position (explicit handling of a "mixed pipeline" edge case, documented inline: normal and won stages can be interleaved by sequence), then a single grouped `write()` per resolved won-stage setting `probability=100`. Both actions are confirmed, source-based, explicit business rules — not inferred from field defaults. (`models/crm_lead.py`)
9. `action_set_automated_probability()` recomputes `automated_probability` (an ML/heuristic-derived score, computation itself not traced in this pass) and overwrites the user-facing `probability` field with it on demand — i.e. probability can be either a computed automated estimate or a directly user-edited value, and this action is the explicit bridge between the two. (`models/crm_lead.py`)
10. `controllers/main.py` exposes exactly 3 routes, all `auth='user'`, `type='http'`, `methods=['GET']`: `/lead/case_mark_won`, `/lead/case_mark_lost`, `/lead/convert` — thin GET-triggered wrappers around the model-level actions in finding 8, used for kanban quick-action buttons (inferred from route naming and method count; wrapper-body logic not read in depth beyond route/method signature — depth gap). (`controllers/main.py`)
