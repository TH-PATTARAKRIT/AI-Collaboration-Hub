## 5. RES-M4 (`mail`) — Q047 (web push from a cloned/restored environment)

A3-MD-14 left Q047 ("a cloned non-production environment must not send messages to real destinations") **INCONCLUSIVE**, noting that device rows and VAPID keys are stored in the database and a clone could keep pushing to real users' browsers "unless a neutralisation step removes them," and that "whether any neutralisation exists was not read."

**Independent re-derivation (fresh fetch, this session), attempting static resolution:**

1. `odoo/service/db.py` (blob `63c314a72de738d044e542e32bc045c21f987531`, matches every prior pin): `exp_duplicate_database(db_original_name, db_name, neutralize_database=False)` and `exp_restore(db_name, data, copy=False)` → `restore_db(..., neutralize_database=False)` (via its caller) both default the flag to `False`; when `True`, both call `odoo.modules.neutralize.neutralize_database(cr)`.
2. `addons/web/controllers/database.py` (blob `434b915ceb3a935c1fdbee248d4a4ed7a8533b48`, matches the prior D1 pin): the web `duplicate` route (~L95) and `restore` route (~L151) both take `neutralize_database=False` as their own default and pass the caller-supplied value straight through to the service layer. Nothing forces the flag on.
3. `odoo/modules/neutralize.py` (blob `4a3c572ba0b5638e7b50563b3003f80076a255af`, not previously pinned by any stage): `neutralize_database()` reads each installed module's own `data/neutralize.sql` file and executes it.
4. `addons/mail/data/neutralize.sql` (blob `e61e84219650d88823c045803f417e1fe4dc38c8`, not previously pinned by any stage) **exists** and its content, read directly: it deactivates mail templates' outgoing server and the fetchmail server, deletes the two web-push VAPID key config parameters, truncates the `mail_push` queue table, and **deletes every row of the device table** (`mail_push_device`).

**A2 verdict: VERIFIED, and Q047 is resolved at source for the `mail` module's own push-device state, not merely bounded.** `mail` ships a neutralisation script that fully removes push-device rows and VAPID keys — so *if* neutralisation runs, device/endpoint state does **not** survive a duplicate or restore. But neutralisation is **opt-in**: both the service-layer functions and the web controller routes default `neutralize_database` to `False`, and nothing in the read files forces it on for a plain duplicate or restore. **Net static answer: by default, device/endpoint state (and therefore the ability to push to real destinations) survives a duplicate or restore of a database with `mail` installed; it is removed only when the operator explicitly requests neutralisation.** This is a source/configuration-default fact, not a runtime behaviour — it needs no runtime execution to state, because the outcome is fully determined by which value the operator passes to an already-read function, and the read establishes the default. PROOF R2C's case records this as PASS at the SOURCE/CONFIG layer, tagged POST-DECLARATION per §0.2.
