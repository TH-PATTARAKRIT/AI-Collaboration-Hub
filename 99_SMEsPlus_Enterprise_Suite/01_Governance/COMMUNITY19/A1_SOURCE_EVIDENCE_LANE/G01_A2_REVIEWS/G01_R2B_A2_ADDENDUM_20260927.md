| # | Step | Source pointer | Observation |
|---|---|---|---|
| T1 | Controller reads the stored minimum-score parameter with no default argument | E4 (`ir_http.py`), the score-check block | `request.env['ir.config_parameter'].sudo().get_param('recaptcha_min_score')` is called with one argument |
| T2 | `get_param`'s own signature | X6 `ir_config_parameter.py`, the `get_param` method | `get_param(self, key, default=False)`: an absent parameter and no default argument returns Python `False` |
| T3 | Conversion | E4, the score-check block | The stored value (or `False`) is passed to `float(...)`. `float(False)` evaluates to `0.0` with no exception. `float("abc")`-shaped stored text would raise `ValueError` on that line, but that is a separate, non-absent scenario |
| T4 | Comparison | E4, same block | The bot-score check is `score < float(min_score)`. With `min_score` absent (→ `0.0`), the comparison is false for every reCAPTCHA response score in the valid `0.0`–`1.0` range, so the request always proceeds past the score check. The gate is **silently off**, not erroring |
| T5 | Settings-screen default | E5 (`res_config_settings.py`), the `recaptcha_min_score` field declaration | The field declares `default="0.7"` |
| T6 | Screen read path | X5 `res_config.py`, `get_values` (called by `res.config.settings.get_values`) | `IrConfigParameter.get_param(icp, field.default(self) if field.default else False)`: when the field has a default and the stored parameter is absent, `get_param` returns that default, `"0.7"`, which the float branch then converts to `0.7`. **The screen therefore shows `0.7` while the enforced runtime gate (T4) is `0.0`/off** |
| T7 | Saving `0.0` | X5, `set_values`, the float/integer branch | `value = repr(value) if value else False`: Python's `0.0` is falsy, so a saved value of exactly `0.0` becomes `False` before being passed to `set_param` |
| T8 | Effect of `set_param(key, False)` | X6, `set_param` | When `value is False`, the existing parameter row is `unlink()`-ed (deleted), not set to a stored `"0.0"`. **Saving `0.0` therefore deletes the parameter and returns the field to the absent state (T1–T4), not to an explicit zero** |
| T9 | Any settings save while the parameter is absent | X5, `set_values` | `set_values` loops over **every** config field with no changed-field filter; `current_value = IrConfigParameter.get_param(icp)` (no default, so `False` when absent) is compared against the *form* value. If the parameter is absent, the form value is either the client-displayed `0.7` (T6) or, if the field is omitted from the payload, the record falls back to the same `default_get` → `0.7` path. Either way `value` resolves to `"0.7"` (non-empty, truthy), `current_value (False) != "0.7"`, so `set_param(icp, "0.7")` **creates** the parameter with `"0.7"`. **Any unrelated settings save while the parameter is absent silently rewrites it to `0.7`**, turning a previously-off gate (T4) into an active `0.7` threshold with no explicit admin edit of that field |

**Original Lane A item 12 (verbatim, unedited):**

> "12. Source observation (not runtime-proven): the minimum-score parameter is converted to a number outside the guarded block; the default 0.7 lives on the settings field, so if the parameter was never saved the conversion appears liable to fail with an unhandled error. Also a missing `score` in a successful response is treated as falsy (effectively below threshold). Flag for A1/Proof. [E4, E5]"

**Corrected static reading (this erratum, R2):**

Item 12's premise that an unsaved parameter is "liable to fail with an unhandled error" is **not what the anchor source does**, and its second sentence ("missing score … effectively below threshold") is also inverted. Independently re-derived (section 1, steps T1–T9):

- The minimum-score parameter, when absent, is **not** an unconverted default `0.7` reaching the conversion — it is read with `get_param`'s own hard default of Python `False` (T1–T2), which `float()` converts to `0.0` **without raising** (T3). There is no unhandled-error path for the absent-parameter case.
- Because the enforced threshold in that state is `0.0`, the score check `score < float(min_score)` is false for every score in the valid range, so the reCAPTCHA gate is **silently off**, not erroring and not "effectively below threshold" (T4). A **missing** `score` in a successful verifier response is likewise read as `False` → `0.0` by the same conversion path, which also compares as "not below" a `0.0` threshold — it does **not** make the request fail the score check, and it does not independently make the gate stricter; if anything, in the ordinary absent-parameter state it compounds the same silent-off condition.
- The settings **screen** shows `0.7` in this state (the field's declared default, read back through `get_values`, T5–T6) while the **enforced** value is `0.0`/off (T4) — a screen/enforcement divergence, not an error.
- Saving an explicit `0.0` does not store a zero; it **deletes** the parameter and returns the module to the same absent/`0.0`/gate-off state (T7–T8).
- Any settings save performed while the parameter is absent — even one that does not touch this field — **rewrites it to `0.7`** (T9), because `set_values` compares every config field against its stored value with no changed-field filter, and the absent field's form value resolves to the displayed default. This can silently re-arm a gate an administrator had left off.

**Disposition:** item 12 is **superseded in substance** by this erratum for static purposes. It is not deleted from the Lane A packet (clean-room / immutability rule); this note is the erratum the packet references. Downstream consumers should read item 12 together with this note, not item 12 alone. No runtime claim is made; T1–T9 are source/language-built-in facts only (`float()` behaviour verified locally against Python's documented semantics, not executed against the live application).
