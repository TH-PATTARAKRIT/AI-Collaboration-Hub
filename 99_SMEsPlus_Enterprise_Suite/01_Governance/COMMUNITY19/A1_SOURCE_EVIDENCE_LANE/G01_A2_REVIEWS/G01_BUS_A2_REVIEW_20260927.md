## 4. Semantic / business findings

- SF-B01 (delivery semantics, C18): For an ERP, the bus must be framed as a best-effort UI refresh channel, not a reliable business event or audit channel. A1's "at-least-once" framing would mislead downstream design into relying on it for guaranteed delivery.
- SF-B02 (authorization model, C05/C06): Correct and important. For a multi-tenant SaaS, "unguessable string = authorization" is a capability-token model with no revocation and no audit; A1 RISK framing is accurate.
- SF-B03 (company scope, C07/C08): Correct. Additional nuance: group channels are global per database, so a group-targeted message reaches every member of the group across all companies of that database; attachment-routed messages go to the acting user, not the record owner.
- SF-B04 (cross-origin, C14): A1 frames the CORS `*` declaration as the risk. Semantically, browsers do not apply CORS to WebSocket handshakes, so the declaration neither grants nor removes protection for the socket itself; the effective control is Origin validation. Source requires an Origin header to be present but compares it to Host/scheme only when the environment flag is set, and even then downgrades to an anonymous session rather than rejecting. The CORS `*` declaration is more consequential on the JSON polling-fallback route (OM-B02), where CORS does apply; its real effect depends on framework credential handling (runtime).
- SF-B05 (replay, C09): Retention (default 24 h) is the real replay horizon for any subscriber of a channel, not the 50 s buffer. Payloads are stored readable in the database for the retention period.
- SF-B06 (revocation, C13): Session revocation is near-real-time only when traffic occurs; permission revocation is not propagated to open subscriptions at all within this module.
- SF-B07 (rate limiting, C11): Limiter governs inbound frames per socket only; there is no limit on sockets per user/tenant or on outbound fan-out in this module. A1 RISK "not per tenant" is correct.

## 5. Omissions (material, not in A1)

- OM-B01 Shared notification medium across tenants: the dispatcher listens on the cluster maintenance database with one fixed notify channel for all databases served; tenant separation relies solely on the DB name embedded in each channel key, and notify payloads carry channel identifiers (DB name, model, record id) visible to any listener on that cluster. For DB-per-tenant SaaS this is the actual tenant boundary and is not stated by A1.
- OM-B02 Polling fallback route is public, declares CORS `*`, accepts client channels and client last id on every call (full replay per SF-B05), and uses a session marker only to detect expiry.
- OM-B03 Subscription frozen at subscribe time (see C13 PARTIAL).
- OM-B04 Loss window for long transactions (see C18 PARTIAL); source advises long transactions to publish close to commit — a design obligation on every publisher.
- OM-B05 `broadcast` channel is appended for every socket including anonymous/public sockets; anything sent to it is public within the database. Anonymous sockets also receive the public user's group channels.
- OM-B06 Outdated-worker rejection applies only when a user agent is present; non-browser clients bypass the version gate (source cites IoT devices). BR6 overstates rejection.
- OM-B07 Handshake persists the session server-side before upgrade; dispatch follows session rotation markers to the new session id.
- OM-B08 Dispatcher error loop sleeps 50 s per process on failure; combined with OM-B01 a cluster-level notify failure silences all tenants on that process (A1 lists the 50 s gap but not its cross-tenant scope).
