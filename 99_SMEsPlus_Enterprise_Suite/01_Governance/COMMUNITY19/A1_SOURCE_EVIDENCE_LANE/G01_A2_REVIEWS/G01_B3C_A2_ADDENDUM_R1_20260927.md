## 1. `phone_validation`

### 1.1 A3-PHON-D1: severity of R1 (removal-side wrong-subject un-suppression)

**Independent re-derivation** (`models/phone_blacklist.py`@d94486f6; `models/models.py`@dccf9fbf; `models/mail_thread_phone.py`@01ca256f; `odoo/orm/domains.py`@63724c20; `odoo/orm/fields_textual.py`@8653b820; base `res_users.py`@9d42d77a):

1. The public remove formats its input with raising off (L104–106). An unformattable input yields "no value". The internal remove receives that value unchanged (L108).
2. The internal remove looks up existing entries with the active filter off, using the list of values (L112). The number field declares a custom search (L15). The search method replaces each term with its formatted value, falling back to the raw term (L70–76). A "no value" term is formatted on the acting user's record. The generic formatter, when given no number, takes the first non-empty number field of that singleton record (`models.py` L75–82). On users, the phone is exposed through partner delegation (base `res_users.py` L165, L255).
3. The ORM does not drop the "no value" term before the search method runs. The in-condition null-drop optimization applies only to field types whose falsy value is "none" (`domains.py` L1343–1356), and text fields declare an empty string as their falsy value (`fields_textual.py` L38). The field search method is honoured for fields that declare one (`domains.py` L957–965).
4. So the lookup resolves to the acting user's own number. If that user's entry exists (active or archived), it is archived (L114–117).
5. **Absent-entry branch (new fact, source-confirmed).** The "missing" list is computed by comparing the submitted values with the numbers found (L113). The submitted "no value" never equals a stored number, so it is always treated as missing. Create is then called with that value and the inactive flag (L118–119). Create formats it on the acting user's record, which again gives the user's number (L35). Create then searches existing entries with the active filter off (L45):
   - If the user's entry exists, it is kept inactive and not reactivated (L48–50), and no duplicate is created.
   - If no entry exists for the user's number, **an archived entry for the acting user's number is created** (L54–55). That is a false "unblocked" record for a person who never asked for anything.
6. The mixin reset helper passes each record's sanitized number (no value when absent) to the internal remove under elevation (`mail_thread_phone.py` L245–246). Elevation changes only the superuser flag, not the acting user, so steps 2–5 still resolve to the acting user.
7. If the acting user has no number, the formatter returns "no value" even with raising on (`models.py` L81–82). The failure then comes from the required-field check (L15), not from validation.
8. Audit observation (LOW, not a verdict): when the acting user's entry exists and a message is supplied, the same entry receives a tracking log message (L115–116) and then a posted note (L120–125). This happens because create returns the existing record. One removal therefore produces two audit entries on the wrong subject's entry.

**Position: AGREE** with A3 CH-1/CH-2. The removal direction lifts an objection for a person who did not ask for that. In the absent-entry branch, it also fabricates an "unblocked" record for them. The consequence is at least as serious as the add direction.

**Correction (SF-PHON-01-R1, replaces the SF-PHON-01 impact statement for consumption; SF-PHON-01 stays HIGH):**
"SF-PHON-01 (HIGH) covers both directions. (a) **Add:** an unformattable number submitted to add, or a mixin record with no sanitized number passed to the elevated set helper, is replaced by the acting user's own number, which is then suppressed or reactivated. (b) **Remove (R1, HIGH):** an unformattable number submitted to remove, or a mixin record with no sanitized number passed to the elevated reset helper, resolves to the acting user's own number. That user's existing entry, active or archived, is archived, which un-suppresses them. If no entry exists, an archived entry for the acting user's number is created. (c) In either direction, if the acting user has no number, the call fails on the required-field check rather than on validation. (d) The audit trail records the acting user's number, not the submitted input. Scope: static inference confirmed end to end on source. Runtime confirmation is pending (PR-PHON-01, PR-PHON-11)."

O-PHON-01 severity: HIGH (unchanged). It now explicitly includes the removal direction and the absent-entry branch.

## 2. `privacy_lookup`

### 2.1 A3-PRIV-D1: fold the multi-character email wildcard into SF-PRIV-01

**Independent re-derivation** (`wizard/privacy_lookup_wizard.py`@3b6d52e0; `odoo/tools/mail.py`@2b05c91f; `odoo/tools/sql.py`@431bd6f0):
- The email input is trimmed and wrapped in multi-character wildcards, without escaping (L48). It is used unescaped for user logins (L73) and for every non-normalized email-like field (L112–121). Normalized-email fields use equality (L115, L120).
- Validation calls core normalization (L49–51). Normalization splits addresses through the standard-library parser and keeps only candidates that contain "@" (`mail.py` L741–786, L812–846). It then lower-cases the local part and domain, with no domain or character validation (`mail.py` L881–889). Statically, nothing rejects a local part and domain made only of wildcard characters. The percent sign and the underscore are ordinary atom characters for the parser. Core escape helpers exist (`mail.py` L953–955; `sql.py` L673–674), but the module calls neither.
- An input of `%@%` therefore passes validation. Its wrapped form matches every login and every non-normalized email-like value that contains "@", whatever the name.

**Position: AGREE.** **SF-PRIV-01-R1 (HIGH; replaces the parent SF-PRIV-01 scope statement):**
"Name and email are inserted as case-insensitive pattern operands without escaping. Over-matching can be caused through **either** input. (a) **Name:** a name made of the multi-character wildcard matches every partner that has a name. Every such partner becomes an indirect reference, which pulls in users, authored messages and every record on a scanned model that holds a non-cascade partner reference. (b) **Email (Proof R1):** an email made of wildcards, such as `%@%`, passes validation and matches every user login and every non-normalized email-like field value containing '@', independent of the name. (c) Without deliberate metacharacters: the underscore, common in real addresses, acts as a single-character wildcard in the email branch, and a plain name matches all case-insensitive homonyms. Remediation of the over-matched set runs elevated and across companies, and bulk delete has no confirmation (SF-PRIV-09)."

### 2.2 A3-PRIV-D2: "whole-DB lookup under sudo" wording

**Re-derivation:** discovery flushes pending writes and executes the composed statement directly on the database cursor (L164–170). It uses no elevated environment and needs none. Access rules and company rules never apply to it. Elevation is used for:
- the line display name (L282);
- archive/unarchive (L295);
- delete (L301);
- the target-model selection listing (L222).

Discovery scope is:
- partners (L53–65);
- users (L66–78);
- messages authored by matched partners (L79–86);
- every table-backed, non-transient model outside the exclusion list (L33, L99–106) that has a stored email-like field (L112–130) or a stored, non-cascade many-to-one reference to partners (L132–143).

Models with neither are not scanned. So "whole database" is directionally correct but not literal.

**Position: AGREE.** The replacement wording applies to A2 §4 business review ("Its reach is database-wide under a single system role") and to O-PRIV-01 ("whole-database scope"):
"Discovery is a raw SQL lookup on the database cursor. It needs no elevation, and access rules and company rules never apply to it. Its scope is database-wide across partners, users, messages authored by matched partners, and every table-backed, non-transient, non-excluded model that has a stored email-like field or a stored non-cascade partner reference. It is not literally every table. Elevation (sudo) is used only for line display names, archive/unarchive, delete and the model-selection list."

REC applies the same wording to REC-PRIV-19 and REC §4 (REC addendum).

### 2.3 A3-PRIV-D5: SF-PRIV-06 wording (legal classification removed)

**Re-derivation:** the masking rules keep the first character of each word or dot-segment, the segment lengths as a mask count, the TLD and three large public domains. The log also stores the date, the handling user and the found-records text (A1 C11, parent A2 C11 VERIFIED).

**Position: AGREE.** **SF-PRIV-06-R1 (MED; severity unchanged):**
"The log masking keeps initial letters, segment lengths, the TLD and common public domains. Combined with the date, the handling user, model names and record ids in the found-records text, the masked values can still help re-identify a subject. The field naming ('anonymized') suggests stronger protection than the mechanics provide. Design implication: the SMEsPlus log design should state which identifiers it keeps and why. Legal classification is out of scope for this review."
