## 1. `auth_signup`

### 1.1 A2-B3A-01 — O4 amended to O4-R1 (A3 CH-06, D-ASGN-A3-01). **Re-derived: AGREE with A3**

Independent re-read:
1. The link signature is a keyed hash whose key is the per-database secret parameter, unless a caller passes another secret (misc, signing helper around L1780-1800).
2. The platform's database-duplicate operation re-initialises the default parameters with the force flag after copying (db service L185-208). The restore operation does so **only** when the restore is flagged as a copy (L319-382). The forced re-initialisation writes a new random secret (config-parameter defaults L18-25, init L45-57).
3. Therefore: platform duplicate → new secret; restore flagged as copy → new secret; restore **not** flagged as copy → secret kept; any copy made outside the platform (for example a raw database dump and reload) → secret kept, because no code path runs.
4. **Additional A2 observation (not raised by A3).** The same forced re-initialisation also resets the base-URL parameter to a local default and resets the login-cooldown parameters. On the two regenerating paths, links built in the clone therefore target the local default base URL until an administrator changes it. On the two secret-keeping paths the base URL is the production value copied from the source. This is topical to the "base-URL targeting" dimension that A3 CH-14 found unevidenced for Q032. The platform's optional neutralisation step was not read.
5. The secret is shared by every signing scope in the database, so the clone behaviour applies equally to other signed artefacts (for example the portal chatter hash; see section 4.3).

> **O4-R1 (LOW-MED, unchanged severity).** Sign-up and reset links are signed with the per-database secret. A copy made by the platform duplicate operation, or by a restore flagged as a copy, gets a new secret, so links issued before the copy are predicted to fail verification in the copy. A restore not flagged as a copy, and any copy made outside the platform, keep the secret, so links issued in one copy are predicted to verify in the other while the bound attributes still match. On the regenerating paths the base-URL parameter is also reset to a local default.

A1 item classes consulted: C05, BR3, states (link lifecycle), G3.

### 1.2 A2-B3A-02 — C18 refinement R1 (A3 CH-08, D-ASGN-A3-02). **Re-derived: AGREE with A3**

Independent re-read of the auth_signup partner model (blob `02aab000`):
1. The single-partner entry runs the multi-partner builder elevated, and **then** checks model-level write rights: on users when the partner has another internal user, on partners when it has another portal user (L29-36). A partner with **no user** triggers neither check.
2. The multi-partner builder has no rights check (L38-85). If the caller's context carries the "signup valid" flag and the partner has no user, it prepares a sign-up type elevated (L46-47). It embeds a signed token only when the partner has a pending type or the context forces one (L55-58); the token is generated elevated.
3. A token for a userless partner takes the invited path, which the free-sign-up gate does not apply to (auth_signup users model, around L96-98; consistent with A3 CH-08).
4. Both builders are private methods (not RPC-callable). Exposure depends on server-side callers in other modules.
5. Candidate caller paths from a default-branch code index (not yet read at the anchor; **not** evidence): multi-partner builder — portal share wizard, hr employee model, survey controller, website_slides controller; single-partner entry — auth_signup users model, website_sale controller, plus the auth_signup mail templates and e-mail views. The portal grant wizard and mail notification link builders must also be checked because they are the flows A3 named.

> **C18-R1 (A2 note on the parent PARTIAL verdict; verdict unchanged).** There is no rights check at all when the target partner has no user, on either entry. The single-partner check covers only partners that already have another internal or portal user, and only at model level. Reachability is decided entirely by server-side callers in other modules, which no stage has enumerated at the anchor.

## 2. `base_setup`

### 2.1 A2-B3A-03 — F1 / O3 amended to F1-R1 / O3-R1 (A3 CH-02, D-BSET-A3-01 and -02). **Re-derived: AGREE with A3; the parent A2 F1 wording was itself narrower than source**

Independent re-read:
1. The KPI route has no authentication, saves no session, and verifies the supplied key with the remote-call scope only (kpi L102-105, route L149-150). The key check accepts a key whose owner is active, whose expiry is unset or in the future, and whose scope is unset or equals the requested scope. It has no share, internal or group term (core users L1725-1752).
2. For a verified key, the route returns id, name, login and latest log date of every active non-share user (kpi L126-138).
3. The portal allow-keys parameter is read only by the portal override of the **key-creation wizard** gate (portal key-description L11-20; base gate "internal users only", core users L1834-1836). Portal ships no users-model override at the anchor (portal models index; no users file).
4. Keys are removed only by self-service account deletion, which is itself limited to share users (core users L944-967), by the expiry clean-up (L1715-1722), or by explicit revoke. The core users write (L596-640) has no key clean-up on a group or user-type change.
5. Consequence: an internal user who created a key and is later changed to a portal (share) user keeps that key. It still passes the KPI check whatever the allow-keys parameter says, until the key's expiry. Keys created by a non-system user always carry an expiry capped by a group-derived maximum (L1577-1589); a key created by a system administrator can be persistent.
6. **Additional A2 observation (not raised by A3).** A separate programmatic key-generation path (L1620-1690) is gated by a different parameter that is off by default (administrators are exempt). It requires the caller to present an existing valid key of their own, and it does **not** re-run the internal/portal creation gate. Where that parameter is enabled, a demoted owner holding an unscoped key could mint further keys, bounded by the key-count limit and by the expiry cap derived from the owner's **current** groups.

> **F1-R1 / O3-R1 (HIGH, unchanged severity).** The KPI key check has no role, share or group term and accepts unscoped keys. A portal-held key reaches the roster **independently of** the portal allow-keys parameter whenever the key was created while its owner was internal (and survived a change to portal), was created by server code, or was minted through the programmatic path. The allow-keys parameter only governs creation through the key wizard. The parent wording "a portal user if the deployment lets portal users create keys" is withdrawn as incomplete.

A1 item classes consulted: C15, BR3, states (none for keys in this module), G4, CRQ-BSET-01.

## 4. `portal`

### 4.1 A2-B3A-05 — O2 widened to O2-R1 (A3 CH-P2, D-PRTL-A3-01). **Re-derived: AGREE with both halves of A3 CH-P2**

Independent re-read:
1. The records-pager helper (portal controller L96-121) browses the previous and next ids from the environment of the record it is given, reads their access URL, and ensures (mints if empty) their tokens. It has no explicit read check.
2. Its only in-module caller, the page-view values builder (L982-1017), passes the document returned by the access gate. The gate returns the record bound to the superuser account (L961-980). Neighbours are therefore read under the superuser, so **even implicit ORM read enforcement is bypassed**; the mint itself writes elevated (portal mixin L34-39). Understated by the parent A2 wording.
3. The id list comes from the server-side session under a route-specific key (L1014). In the one downstream module read (sale portal controller), the list routes that fill it require a logged-in user and store the ids of that user's own search results (L106-115). The pager runs only if the current document id is in the list.
4. Therefore a token-only, not-logged-in visitor cannot supply a history, and a logged-in user's history holds only records that user could list. The realistic exposure is **stale history**: records readable when the list was built, whose access was lost later in the same session. Overstated by the parent Proof R1 extension ("crafted or previous session history").
5. Note: the same sale list routes already ensure tokens for every listed document, so the pager usually embeds existing tokens rather than minting new ones.

> **O2-R1 (MED; unchanged severity).** Five mint invocations exist in four functions (share-URL builder, portal-URL builder, customer-notification grouping, and the pager for previous and next). The pager site runs on the superuser handle and bypasses both explicit and implicit read checks. Its reach is limited to ids in the caller's own session history, filled by login-required list routes, so the exposure is stale history after access loss within a session, not attacker-crafted history.

## 5. `base_automation`

### 5.1 A2-B3A-07 — O14-R1 and the C11 note amended to O14-R2 (A3 RD-1). **Re-derived: AGREE with A3**

Independent re-read:
1. The time processor's first step searches the rule model for active time rules in the job's own environment with no elevation (module model L1184-1191). Per-rule last-run is also written unelevated (L1214).
2. The rule model's only access row grants the settings (system) group full rights (module ACL, one row).
3. The ORM search checks model read access for any non-superuser environment before querying (orm models L5364-5366). This closes the "ORM enforcement not re-read" limitation A3 recorded for RD-1.
4. The scheduler builds the job environment from the job's configured user (ir_cron L426, L482). So a job reassigned to a user outside the settings group is predicted to raise an access error at the very first rule search, before any rule is selected. The run is classified FAILED (processed count zero), which feeds the deactivation path (O3-R1).

> **O14-R2 (MED; supersedes O14-R1 and the "reassigned ordinary user" sentence of the C11 note).** Condition evaluation is elevated on the event, message, onchange and webhook paths. On the time path it runs in the job user's environment without module elevation: superuser mode under the predicted default job user; that user's record-rule visibility when the job user is in the settings group; and **a FAILED run with nothing processed** when the job user is outside the settings group, because the rule model itself is unreadable to that user.

### 5.2 A2-B3A-08 — O18 amended to O18-R1 (A3 RD-2). **Re-derived: AGREE with A3; ordering point settled**

1. Outside any per-rule isolation in the time processor: the initial rule search (L1191), the per-rule active check (guarded only against a missing record, L1195-1199), the record selection (L1203), and the last-run write and progress commit (L1214-1216). Only record processing and flush are isolated (L1205-1212).
2. The rule model declares no ordering attribute, and the ORM default ordering attribute is the record id (orm models L434). Rules are therefore iterated in id order.
3. A persistent selection error on rule R ends every run at R. Rules after R in id order are never processed in any run (not only "that run"). Every such run is FAILED, so the deactivation path (O3-R1) is also driven. "Healthy rules still advance within each run" (O3-R1) holds only for processing-phase failures and for rules before R.

> **O18-R1 (MED).** Record selection, the rule search, the active check and the last-run write sit outside per-rule isolation. A persistent selection error permanently starves every rule later in id order and drives job deactivation. An error in the last-run write has the same effect.

### 5.3 A2-B3A-09 — O3-R1 extended to O3-R2 (A3 RD-3). **Re-derived: AGREE with A3**

1. The scheduler classifies a run as FAILED **without executing it** when the job has timed out at least 3 consecutive times and the last progress shows no processed work (ir_cron L35, L429-443). This module never reports a processed count, so repeated worker timeouts (for example a large backlog) alone feed the failure counter and can deactivate the single job with no rule error.
2. The module's job-update routine returns silently if it cannot lock the job row (module model L672-675). A restart attempt made while the job is running or locked is a no-op.
3. The routine sets the job active only when at least one active time rule exists (L676-678). It is called on create, delete and critical writes of **any** rule, including non-time rules.
4. The failure counters are reset at deactivation (ir_cron L571-603), so after re-activation a still-failing rule needs a new full cycle (at least 5 FAILED runs spanning more than 7 days) before the next deactivation. A persistent failure therefore makes the job oscillate between active and inactive.
5. The base admin-notification hook is documented in source as doing nothing unless overridden (ir_cron L388-395); the deactivation path itself logs a warning. This confirms the R5 refinement of the earlier Proof addendum.

> **O3-R2 (HIGH; supersedes O3-R1 wording, adds to it).** As O3-R1, plus: repeated worker timeouts also count as FAILED for this module and can deactivate the job with no rule error; a restart through a rule write is silently skipped when the job row is locked and requires at least one active time rule; any rule's create, delete or critical write re-activates the job; and after re-activation a persistent failure makes the job oscillate.

### 5.4 A2-B3A-10 — new omission O19 carried from base (A3 base D4). **Re-derived: AGREE with base A3 Ch-5 and base A2 O3**

The base server-action gate checks group membership against the environment's user, which keeps the real uid under elevation (ir_actions L1215-1221). Model and record checks are skipped under elevation. A group-restricted action attached to an automation therefore raises for a triggering user outside the group, and on the synchronous paths the triggering operation is expected to fail with it. On the time path the check is made against the job user (the superuser account under the predicted default); whether that account holds a given group is data-dependent and is **not** claimed.

> **O19 (MED, new omission).** The per-action gate does restrict rule-triggered actions **that carry groups**: a triggering user outside the action's groups gets an access error that can block that user's own edit. Actions without groups are not restricted by the gate under elevation. (Base A2 O3; base Proof PC-BASE-32.)
