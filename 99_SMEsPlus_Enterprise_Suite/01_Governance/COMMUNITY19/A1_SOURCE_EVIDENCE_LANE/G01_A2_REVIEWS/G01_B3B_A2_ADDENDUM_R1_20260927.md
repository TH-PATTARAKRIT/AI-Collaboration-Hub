### 2.1 D-W1 / A3-W-01: OM-W02 and SF-W02b narrowed

**Independent re-derivation.** The export routine (export.py ~L554-637) resolves records in the caller's environment (browse by ids, else search by domain; ~L569). It takes the **grouped branch only when grouping is requested and the export is not in import-compatible mode** (~L571-572); in that branch it calls the ORM export method **once on the whole resolved set before any grouping** (~L573), empty or not. Otherwise it takes the **flat branch**, which splits the id list into fixed-size batches and calls the ORM export method per batch (~L614-619). The splitter yields nothing when the first piece is empty (tools/misc.py ~L684-697), so on an empty set the ORM export method is never reached, and the writer emits a header row only. The info log line is written after either branch, including a count of zero (~L621-627). The ORM export method's first step refuses unless the environment is admin (superuser mode or the Access-Rights group) or the user holds the export group (orm/models.py ~L889-890; environments.py ~L182-185). For CSV, the grouped branch then refuses anyway because CSV grouped export is unsupported (~L661-662), but only after the ORM gate has run.

**Position: AGREE with A3.** A2's parent wording ("an empty-result export never calls export-data, so it returns a header-only file without the group check") is unconditional and is wrong for the grouped non-import-compatible branch.

**OM-W02R1 (replaces OM-W02 for consumption):** "On the **flat** export path (no grouping requested, or import-compatible mode), an export whose resolved record set is empty never reaches the ORM export gate. The caller receives a header-only file even without export rights, and the info log still records an export of zero records for that caller. On the **grouped, non-import-compatible** path the ORM export gate runs on the (possibly empty) set before grouping, so a caller without export rights is refused." Weight LOW, unchanged. A3's audit nuance is adopted: the zero-count log line is an **audit-accuracy** point (a logged export event for a caller who may lack export rights), not a data-egress point, because no row data leaves.

### 4.1 A3-HROU-D1/D2 origin: A2 C03 wording

**Independent re-derivation.** In the module's match step (ir_http.py ~L367-481): when the first match finds an endpoint, frontend and frontend-multilang flags are set from the route's website and multilang flags, and a non-website endpoint returns immediately (~L372-377). When the first match raises not-found, the module splits a candidate language segment off the path (~L379-381) and continues **without any route flag**: the redirect permission defaults to allowed for non-POST requests because no multilang flag was set (~L384-387); the language is resolved under a temporary public identity (~L398-411); redirect branches for missing, default, aliased and trailing-slash language segments are reachable (~L421-459); a valid language segment triggers an internal reroute (~L461-465). The final re-match either finds an endpoint (flags then come from that endpoint, ~L472-475) or raises not-found **after forcing both frontend flags true** (~L476-480), which sends the error into the frontend error handler (~L570-606).

**Position: AGREE with A3 (refined).** A2's parent C03 verdict already contained the parenthetical "(and for unmatched paths)", but its closing sentence "Opt-in is per route flag" states the conclusion without that qualifier, and REC and PROOF consumed the unqualified sentence. **C03 A2 verdict R1 (clarifies, does not change PARTIAL):** "A1's RISK 'global to every request' is overbroad for **matched** endpoints, where language, canonical and frontend-error behaviour are opt-in by the route's website/multilang flags. For **unmatched** paths the behaviour is request-wide and flag-independent: every unmatched path goes through language resolution, may be redirected (non-POST) and, if still unmatched, is rendered by the frontend error handler with the frontend flags forced on. A1's RISK is therefore partly supported." The PARTIAL verdict stands; A1 and A2 are each partly supported.

## 6. `mail` — A2 corrections and verdicts on A1 items not carried by REC

### 6.1 A3-D1 / CH-1a: C28 zip wording

**Independent re-derivation.** The zip route is POST, http, public and has no guest-context decorator; it browses the requested ids on the attachment model in the request environment and builds each stream through base binary streaming (mail controllers/attachment.py ~L22-47, ~L110-118). Base streaming converts an attachment record by reading its stored fields on that same, non-elevated record (base ir_binary.py ~L69-70; ir_attachment.py ~L913-938). An ORM read of stored fields runs the model's access-filtering search on the ids and raises an access error for any id that the search filters out (orm/models.py ~L3795-3824). The attachment search admits public attachments for read, admits attachments without a linked record only for system users or their creator, and filters linked attachments by access to the linked record (ir_attachment.py ~L620-660). So an unreadable id raises an access error and the whole zip fails; no partial bytes are returned.

**Position: AGREE.** A2's parent C28 wording ("no module-level access check; it depends on base binary streaming") is accurate and is not changed. **A2 R1 annotation to C28/SF-13:** "Base binary streaming enforces attachment read access implicitly in the request environment. The zip route's missing guest context tends to fail closed: token-bearing guests lose access; unauthorised callers do not gain it. Static prediction; runtime decides (PR-03)."

### 6.2 A3-D2 / CH-1b: G9 closure — base company-context semantics

**Independent re-derivation.** The environment's company set (orm/environments.py ~L246-283): when the allowed-company context is empty, it resolves to **all of the user's companies** (with an in-source rationale). When the context is non-empty and names a company outside the user's companies, it raises an access error, **unless the environment is in superuser mode**. The single-company accessor behaves the same way (~L216-243). The validation is **lazy**: it runs when the company set is evaluated (for example by a company-dependent record rule), not when the context is set. A record switched to a user with the "with user" helper leaves superuser mode (orm/models.py ~L5994-6001). An environment for the superuser id is always in superuser mode (environments.py ~L64-67), and the read-access probe returns true in superuser mode (orm/models.py ~L4123-4128).
