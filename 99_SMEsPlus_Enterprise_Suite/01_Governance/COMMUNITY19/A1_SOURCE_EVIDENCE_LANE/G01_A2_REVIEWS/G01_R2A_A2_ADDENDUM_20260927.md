## 1. `auth_signup` — R-ASGN-1 (wording; base-URL reset persistence)

**Independent re-derivation (before adopting A3's correction).** At the anchor, the login-success handler that records a browser-supplied `base_location` runs only when the authenticating user belongs to the system-administrator group. It reads the `web.base.url.freeze` configuration parameter and **overwrites** `web.base.url` with the browser-supplied value **unless** the freeze parameter is set (`odoo/addons/base/models/res_users.py`, blob `9d42d77a…`, the browser-base-URL-guessing block inside the authenticate/login-success path). The forced-defaults table written by the platform's duplicate/copy-restore re-initialisation (already established in the B3a cycle) resets `web.base.url` to a local default but does **not** include `web.base.url.freeze` among the forced rows.

**Position: AGREE with A3.** The parent A2 addendum R1 wording ("the base URL is reset to a local default … until an administrator changes it") is imprecise: it implies the reset value can only be undone by a deliberate admin edit of the parameter. In fact:
- If the source database's `web.base.url.freeze` parameter was **not** set, the very next successful login by any system-group user whose HTTP request context carries a base location **automatically overwrites** `web.base.url`, with no explicit admin action on that parameter.
- If the source database's freeze parameter **was** set, that freeze value is copied into the clone (it is not among the forced defaults), and the local default then **persists** until a person changes it by hand — matching the parent's original claim, but only in this one branch.

> **O4-R1 wording correction (auth_signup, supersedes the B3a O4-R1 sentence on base-URL persistence).** "On the regenerating paths (platform duplicate; restore flagged as a copy), the base-URL parameter is reset to a local default. Whether that default persists depends on the `web.base.url.freeze` parameter, which is not itself among the forced defaults: if the source database had it unset, the next successful system-user login whose request carries a base location automatically rewrites `web.base.url` to that location; if the source database had it set, the freeze is copied into the clone and the local default persists until changed by hand." No severity change (LOW, unchanged from A3's rating).

## 4. `bus` — R-BUS-1, R-BUS-2 (source fact), R-BUS-3

### 4.1 R-BUS-1 (wording; delayed-delivery mechanism)

**Independent re-derivation.** This addendum re-confirms, rather than merely accepts, the batch-2 A3 re-check's own re-derivation (its §2(a)): a dispatcher-loop exception causes a 50 s sleep and a re-LISTEN, during which no periodic re-poll of the notification table occurs; dispatch is trigger-only (a NOTIFY for a subscribed channel, or a `subscribe` call). Separately, and **not previously cited by either the remediation controller or A3's own first pass**, every socket carries a hard keep-alive lifetime set once at construction (a base constant plus jitter) and never extended; on expiry the server closes the socket, and a reconnecting client's `subscribe` call is itself a dispatch trigger. **AGREE with the batch-2 A3 re-check's ruling**, which is itself a refutation of both A3's original "delay of up to ~50 s" framing and a qualification of the remediation's own "not bounded by the module" framing (the keep-alive close bounds the delay **in practice, for a client that reconnects**, though not by module design).

> **OM-B08-R2 wording (bus, supersedes OM-B08-R1).** "A dispatcher error on one process pauses wake-ups for every database's sockets on that process for at least the 50 s retry sleep. Notification rows stay stored. Rows whose NOTIFY fell in the pause are delivered at each affected socket's **next wake-up trigger** (a later notification on a subscribed channel, a client resubscribe, or a reconnect after the socket's own keep-alive expiry forces a close). The module sets no periodic re-poll and does not itself bound the delay; in practice, a client that reconnects receives the missed row within its socket's remaining keep-alive lifetime (default one hour to ninety minutes from open). Loss occurs only if no such trigger arrives before the 24 h garbage-collection retention window expires (for example, a client that never reconnects, or a keep-alive setting large enough to approach that window)." **Neither the "~50 s" framing nor the "silences all tenants" framing is reintroduced.**

### 4.2 R-BUS-2 (REC did not scan all A1 item classes; Q021 wrongly listed as "no evidence")

**Independent re-derivation.** The bus A1 package's item class list includes claim **A1-G01-BUS-C18** ("per-socket in-memory history of dispatched ids (10 s) de-duplicates and tolerates out-of-order commit visibility") and Lane-A-only observation **#12** ("Ordering/duplicate control: per-socket in-memory history of dispatched ids kept 10 s … last-id advances only past contiguous expired entries"). The bus question bank's Q021 topic (paraphrased, per the parent REC's own no-evidence list) is duplicate-subscription registration not multiplying delivery. Both C18 and Lane A item #12 describe the same per-socket de-duplication mechanism that would be the relevant control for that topic. **AGREE with A3**: the batch-2 REC addendum's rule-3 rescan (§4.1 D-BUS-04) corrected several other QIDs but left Q021 on the "no evidence yet" list, without recording a scan against C18/Lane-A #12 for it. This is a REC-owned correction (recorded in the companion REC addendum §1); A2 records the source fact only.

### 4.3 R-BUS-3 (citation precision; cookie-setter helper)

**Independent re-derivation.** At the anchor, the session-save path (`odoo/http.py`, blob `ebfc2ac8…`) calls `self.future_response.set_cookie(...)` to set the `session_id` cookie. `FutureResponse.set_cookie` is defined earlier in the same file (the method whose body reads, in substance, "if `expires` is the sentinel, default to one year; if cookies are disallowed for the request, zero the max-age; call the base implementation with the same `secure`/`samesite` defaults as the plain `Response.set_cookie`"). A **separate** class, `Response`, also defines its own `set_cookie` with an identical default-argument signature, but that method is **not** the one the save-path line invokes; it is used by a different response object. **AGREE with A3.** The prior addenda (A2 batch-2 §1, REC batch-2 §1.2 REC-BUS-14) cited only the `Response.set_cookie` definition as "the cookie helper," which happens to share identical defaults with `FutureResponse.set_cookie` (the one actually invoked at the request-path save), so the underlying fact (HttpOnly set; no explicit SameSite; no explicit Secure) is unaffected, but the citation named the wrong of the two identically-shaped methods.

> **SF-B04-R2 citation correction (bus, no wording change to the finding itself).** Add: "The request-path session-cookie save (`odoo/http.py`, the `session_id` cookie set inside session persistence) invokes `FutureResponse.set_cookie`, not `Response.set_cookie`. Both methods share identical defaults (`secure=False`, `samesite=None` unless the caller passes otherwise), so the finding (HttpOnly present; no explicit SameSite; no explicit Secure at the anchor) is unaffected. The citation is corrected to point at the method actually called on this path." No severity change; no verdict change.
