## 1. `phone_validation` — R-PHON-1: audit-duplication observation has no REC item or proof requirement

### 1.1 Independent re-derivation

Re-read `phone_blacklist.py`@d94486f6 in full (140 lines):

1. `create()` (the model-level override, L22–58) sanitizes every requested number on the **acting user's own record** with `raise_exception=True` (L35), searches existing entries **including archived ones** (`active_test=False`, L45), computes `numbers_to_keep_inactive` for entries requested inactive (L47–48), leaves those existing entries **inactive** and excluded from re-activation (L48), excludes them from `to_create_filtered` (L51–52), and returns the **union** `existing | created` (L57–58).
2. `_remove()` (L108–127) first searches `records` (active_test off) for the submitted numbers (L112), computes `todo` by set membership against `records.mapped('number')` (L113). If `records` is non-empty: it calls `records._track_set_log_message(message)` (L115–116, a **tracking/chatter log message**) and then `records.action_archive()` (L117).
3. If `todo` is non-empty (which, per A3 R1 §2.1 step 5 and independently confirmed here, is **always** true for a "no-value" submitted term, since a no-value term can never equal a stored number), `_remove` calls `self.create([{'number': n, 'active': False} for n in todo])` (L118–119) — the model-level `create()` from step 1.
4. Inside that nested `create()` call: the no-value term is re-sanitized on the acting user (L35, again resolving to the acting user's own number by the same mechanism A3 R1 documents in §2.1). The search at L45 (active_test off) finds the **very entry that step 2 just archived** (it was found and archived, not deleted). That entry's number is in `numbers_to_keep_inactive` (requested `active: False`), so it is **kept inactive, not re-activated** (L48), and it is **excluded from `to_create_filtered`** (L51–52) because its number is already in `existing_numbers`. The nested `create()` therefore returns that same existing (now-archived) record as part of its `existing | created` union (L57–58).
5. Back in `_remove` (L120–125): `for record in new_records: record.message_post(...)` — this posts a **chatter note** on every record returned by the nested `create()`, which includes the acting user's entry that was just archived in step 2.

**Result, independently confirmed:** a single `_remove` call on a no-value input causes the acting user's own blacklist entry to receive **two separate audit writes** — a tracking-log message from `_track_set_log_message` (step 2) and a posted chatter note from `message_post` (step 5) — driven entirely by source-level control flow (the "found-and-archived" record is re-discovered by the nested `create()`'s own existence search and returned to the caller). This reproduces, byte-for-byte at the pinned anchor, the observation A2 recorded in the B3C addendum §1.1 item 8 and A3 R1 confirmed in §2.1 step 8/§2.1 "Strengthening observation".

**Position: AGREE.** The observation is source-confirmed independently. It was correctly flagged by A3 R1 as lacking a REC item and a proof requirement — prose inside an A2 addendum section is not itself a governed, tracked item.
