## 2. Findings by A1 completion-card section

### 2.1 Manifest / dependencies / purpose
1. WHAT: `event` ("Events Organization") is the base events-management module: creating events, tracking registrations/attendees, seat limits, per-event or per-slot scheduling, a registration questionnaire, automated email communications, badge/ticket PDF generation, and a barcode check-in flow. WHY: it is the org's single source of truth for "what event, who is attending, how many seats are left." Category Marketing/Events, license LGPL-3. (`__manifest__.py`)
2. Declared dependencies (`depends`, dependency relationships only, not group membership): `barcodes`, `base_setup`, `mail`, `phone_validation`, `portal`, `utm`. (`__manifest__.py`)
3. `data` list installs security first, then menus/views/reports, then cron + seed data (mail templates, stages/questions, a tour), then settings/tag/question views. `demo` data (users, partners, demo events/registrations) is separate and not installed by default. (`__manifest__.py`)
4. Assets are injected only into `web.assets_backend` / `web.assets_frontend` (client action for barcode scanning, tours, a couple of custom form widgets) plus report-specific SCSS bundles for badge/ticket PDFs. JS was not studied. (`__manifest__.py`)

### 2.2 Data — models, inheritance, key fields, identity/uniqueness
5. `event.event` inherits `mail.thread` + `mail.activity.mixin` (chatter/activities available). Key fields: `name` (required, translatable), `date_begin`/`date_end` (required), `date_tz`, `stage_id` (kanban pipeline, `ondelete='restrict'`), `kanban_state` (normal/done/blocked/cancel), `seats_max`/`seats_limited` and computed `seats_reserved/available/used/taken`, `is_multi_slots` + `event_slot_ids`, `event_ticket_ids`, `question_ids` (split into `general_question_ids`/`specific_question_ids` by a `once_per_order` flag on the question), `organizer_id`, `address_id` (venue), `event_url`, `badge_format`/`badge_image`, a `PropertiesDefinition` for per-registration custom properties. Many fields (`seats_max`, `seats_limited`, `event_mail_ids`, `tag_ids`, `event_ticket_ids`, `note`, `ticket_instructions`, `question_ids`, `date_tz`) are computed-and-store "sync from template" fields keyed only on `event_type_id`, explicitly emulating an onchange rather than a live dependency, to let a user later diverge from the template. (`models/event_event.py`)
6. `event.registration` inherits `mail.thread` + `mail.activity.mixin`, sets `_mail_defaults_to_email = True`. Key fields: `event_id` (required), optional `event_slot_id` and `event_ticket_id`, `partner_id`, `name`/`email`/`phone`/`company_name` (computed from the partner's contact address the first time, then user-editable and stored), `state` (draft/open/done/cancel, default `open`), a random 8-byte decimal `barcode` (unique), `registration_answer_ids`, `mail_registration_ids`. Identity: unique constraint on `barcode`. (`models/event_registration.py`)
7. `event.slot` (multi-slot sub-schedule): `event_id` (required, cascade delete), `date` + `start_hour`/`end_hour` floats (interpreted in the event's timezone), computed UTC `start_datetime`/`end_datetime`, its own seat counters. (`models/event_slot.py`)
8. `event.event.ticket` inherits `event.type.ticket` (shared base with `event.type.ticket`, the per-template ticket definition): adds `event_id` (required), sale-window datetimes, computed `is_launched`/`is_expired`/`sale_available`/`is_sold_out`, `limit_max_per_order`. (`models/event_ticket.py`, `models/event_type_ticket.py`)
9. `event.question` / `event.question.answer` / `event.registration.answer`: a question has a type (simple_choice/text_box/name/email/phone/company_name), an `is_default`/`is_reusable`/`once_per_order`/`is_mandatory_answer` set of flags, and can be scoped to event types or specific events; an answer row references either a suggested `event.question.answer` or free text, with a DB check that at least one is set. A DB check also enforces "a default question must be reusable." (`models/event_question.py`, `event_question_answer.py`, `event_registration_answer.py`)
10. `event.mail` is the communication scheduler: one row per event per communication rule, holding `interval_type` (after_sub / before_event / after_event_start / after_event / before_event_end), `interval_nbr`/`interval_unit`, a computed `scheduled_date`, a polymorphic `template_ref` (Reference field, currently only `mail.template`), and computed `mail_state` (running/scheduled/sent/error/cancelled). `event.mail.registration` and `event.mail.slot` are the attendee-level and slot-level execution-tracking rows respectively. `event.type.mail` is the template-side definition copied onto `event.mail` when an event is created from an `event.type`. (`models/event_mail.py`, `event_mail_registration.py`, `event_mail_slot.py`, `event_type_mail.py`)
11. `event.type` is a reusable template holding default seats limit, timezone, tag defaults, default questions, and default `event.type.mail`/`event.type.ticket` lines that are copied onto a new/changed `event.event`. `event.stage` is a simple kanban-pipeline definition with a `pipe_end` flag. `event.tag` / `event.tag.category` provide a colored, sequenced tagging taxonomy. (`models/event_type.py`, `event_stage.py`, `event_tag.py`)
12. Extension of `mail.template`: a custom `_search` override adds a hidden domain (`model = 'event.registration'`) when a context flag `filter_template_on_event` is set, used to restrict the reference-field picker in the UI; `unlink()` cascades to delete any `event.mail`/`event.type.mail` rows referencing the deleted template. (`models/mail_template.py`)
13. Extension of `res.partner`: computed `event_count` (visible only to `event.group_event_registration_desk`+), and a computed, cached "is this static-map URL still valid" boolean that performs a live outbound HTTP GET to the generated Google Static Maps URL. (`models/res_partner.py`)
14. Extension of `res.config.settings`: toggles for optional add-on modules (`event_sale`, `pos_event`, `website_event_track` and its sub-features, `website_event_exhibitor`, `website_event_sale`, `event_booth`), a Google-Maps-static-API key/secret pair (base64-validated), and the barcode-feature toggle. (`models/res_config_settings.py`)

### 2.3 Business rules / states / lifecycle / exceptions
15. Registration state machine: draft → open (default) → done (attended) or cancel; `write()` intercepts a transition into open/done to (re)trigger the mail schedulers, and a transition into `done` posts a chatter log message with the attendance date. (`models/event_registration.py`)
16. Seat-availability enforcement: `event.event._verify_seats_availability` raises a `ValidationError` (listing the offending event/slot/ticket names and the shortfall) if requested seats exceed availability; it is invoked from `event.registration._check_seats_availability`, an `@api.constrains` on `active/state/event_id/event_slot_id/event_ticket_id`, so registrations cannot silently overbook once they reach `open`/`done`. Availability accounts for a three-level cap: event-level `seats_max`, per-slot cap, and per-ticket `seats_max`, taking the tightest applicable limit. (`models/event_event.py`, `event_registration.py`)
17. Multi-slot events: `is_multi_slots` requires every registration to carry an `event_slot_id` belonging to the same event (`_check_event_slot` constraint), and every slot must fall within its event's `date_begin`/`date_end` window (`event.slot._check_time_range`) with `start_hour < end_hour` in [0,24) (`_check_hours`). A slot cannot be deleted while it has registrations (`@api.ondelete`). (`models/event_registration.py`, `event_slot.py`)
18. `event.event._check_closing_date` forbids `date_end < date_begin`; `_check_event_url` requires a URL with scheme+host if set; `_check_slots_dates` forbids slots outside the event's own date range (event-level mirror of the slot-level check). (`models/event_event.py`)
19. Ticket rules: a ticket's sale window must be coherent (`start_sale_datetime <= end_sale_datetime`), `limit_max_per_order` cannot exceed the ticket's own `seats_max` nor the module constant `EVENT_MAX_TICKETS` (30) and cannot be negative; a ticket cannot be deleted while it has registrations. (`models/event_ticket.py`)
20. Question rules: a question's `question_type` cannot be changed once attendee answers exist (`write()` guard, `UserError`); a question cannot be deleted once answered, nor if it is one of the seeded default questions (`@api.ondelete` guards); an answer option cannot be deleted once selected by an attendee. A DB check couples `is_default` to `is_reusable`. (`models/event_question.py`, `event_question_answer.py`)
21. Registration open/sold-out logic (source-visible, not runtime-proven): `event_registrations_open` is false once the event is cancelled or past its end date, or once its seat cap is exhausted, or (for multi-slot events) once every launched, non-expired slot/ticket combination is sold out; `event_registrations_sold_out` and each ticket's `is_sold_out` are derived from the same per-slot/per-ticket availability computation. (`models/event_event.py`, `event_ticket.py`, `event_slot.py`)
22. Automated communications: `event.mail.execute()` branches on `interval_type == 'after_sub'` (attendee-based, tracked per registration via `event.mail.registration`) vs event-based/slot-based one-shot sends; batch size and per-cron-run cap are read from `ir.config_parameter` (`mail.batch_size`, `mail.render.cron.limit`, default 50/1000) with auto-commit between batches outside test mode; failures are caught per scheduler, logged to chatter on the event (rate-limited to once per hour via `error_datetime`), and do not abort the rest of the cron run. On `event.event` creation/edit, `_compute_event_mail_ids`/`_compute_event_ticket_ids`/`_compute_question_ids` reconcile inherited template lines against existing ones, explicitly protecting lines that already have registrations/answers/sent-mail from being dropped. (`models/event_mail.py`, `event_mail_registration.py`, `event_event.py`)
23. Autovacuum: `_gc_mark_events_done` (on `event.event`) automatically moves any event whose `date_end` has passed into the first stage flagged `pipe_end=True`. RISK: an unattended, admin-run background job silently changes the kanban stage (business-visible state) of every ended event. (`models/event_event.py`)
24. Barcode check-in: `register_attendee(barcode, event_id)` looks up a registration by barcode and classifies the scan (`canceled_registration` / `unconfirmed_registration` / `not_ongoing_event` / `need_manual_confirmation` if the barcode belongs to a different event than the desk is scanning / `confirmed_registration` on success / `already_registered`); a successful first scan calls `action_set_done()`. (`models/event_registration.py`)
25. Ticket/badge access control for the public download route is HMAC-based: `_get_tickets_access_hash` derives a keyed hash over `(event_id, sorted(registration_ids))` using `tools.hmac`; the controller compares it with `consteq` (constant-time compare) before serving the PDF/HTML, and the event is sudo-loaded specifically to allow access to tickets sent before the event was published. (`models/event_event.py`, `controllers/main.py`)

### 2.4 Security
26. Three groups form an implied hierarchy under a new "Events" privilege: `group_event_registration_desk` (implies `base.group_user`) → `group_event_user` (implies the desk group) → `group_event_manager` (implies user; `base.user_root` and `base.user_admin` are added to it directly in seed data). (`security/event_security.xml`)
27. ACL pattern (35 rows) largely follows: registration-desk = read-only (and, for `event.registration`/`event.question.answer`, read+write but no create/unlink) on most models; `group_event_user` = full CRUD on templates/tickets/slots/stages/tags/questions but only read+write+create (no unlink) on `event.event` and `event.tag` themselves; `group_event_manager` = full CRUD everywhere. Three models (`event.event.ticket`, `event.registration`, `event.tag`) additionally carry an explicit "no access" (`0,0,0,0`) row with an empty group column, i.e. the base ACL row denies all and access is granted only through the group-specific rows layered on top. (`security/ir.model.access.csv`)
28. Multi-company: three `ir.rule` record rules restrict `event.event`, `event.registration`, and `event.event.ticket` (the last via `event_id.company_id`) to `company_id in company_ids + [False]`, i.e. records with no company set remain visible across companies. No company rule is declared for `event.slot`, `event.mail`, `event.question`, or `event.tag`/`event.stage` (these are not company-scoped fields in this module; not verified whether a downstream module adds one). (`security/event_security.xml`)
29. The `res.partner.event_count` field is restricted to readers holding at least `group_event_registration_desk` (field-level `groups=`). (`models/res_partner.py`)
30. Controller-side: the ICS route and the ticket/badge PDF route both use `auth="public"`; ticket/badge access is gated by the HMAC+consteq check in finding 25 rather than by session/group membership, so RISK: the actual authorization boundary for ticket downloads is a possession-of-hash test, not an ACL — A1/A2 should confirm the hash cannot be derived or brute-forced from public data. The barcode-scanner init route requires `auth="user"` (no group check visible at the controller level; relies on backend view/menu access to reach the barcode client action, and ACL on `event.event` read for the manager/user/desk groups). (`controllers/main.py`, `security/event_security.xml`)
