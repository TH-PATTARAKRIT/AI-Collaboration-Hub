### 3.1 Refinements and observations (for A3; they do not change any verdict)

- R1 (PC-23): with no company context, the activated set defaults to all of the user's allowed companies. For scheduler jobs (O10, PR-13), the static prediction is therefore that company B **is** included and company C is excluded by rule for a non-superuser job user.
- R2 (PC-24 + PC-36 + supplementary): `odoo/modules/loading.py` was fetched **after** predeclaration and read for one point only. Module data loads in an environment created for the superuser account uid. With PC-36 (seeded jobs default to the loading user) and PC-24 (that uid forces superuser mode), the static prediction is that **seeded jobs run in superuser mode with the superuser account as recorded actor**. This goes beyond A2's C29 PARTIAL, which left the point to G1, and supports its direction. It is not a predeclared verdict. The runtime test is PC-BASE-12.
- R3 (PC-29): the access-rights manager can set other users' passwords through the admin set-password path, which reaches administrator accounts. No source guard was found. Combined with O7, this is a second possible self-elevation route. It is recorded as an observation only; runtime PC-BASE-19 may add a variant.
- R4 (PC-38): company-consistency enforcement is opt-in and is not skipped under superuser. Elevated code can therefore still be refused for cross-company links on opted-in models, while non-opted models get no such check. This bears on Q031 lineage.
- R5 (PC-32, cross-module): see REC section 5, item 3. The base_automation Proof R4 wording ("gate does not restrict") holds only for actions without groups.

## 6. Design-implication note — S1 and O7 (tenant boundary; neutral, non-prescriptive)

This note is for SMEsPlus data-architecture and IAM design. It states implications only. It does not prescribe a schema, and it does not recommend copying the reference ERP's model, rule mechanism, naming or workflow.

- **S1: company visibility is not tenant isolation.** In the reference, "company" is a user-selectable visibility filter inside one shared data store (PC-22, PC-23). It is bypassed by any elevated execution (PC-24). By design it exempts staff identities and their contact records (PC-25, PC-27). It is fully visible to one administrative role (PC-26). It defaults to "all allowed companies" when no selection is present (R1). Implication: SMEsPlus should treat the tenant boundary as a separate, stronger control than any intra-tenant company or branch scoping. Such a boundary should not depend on a client-supplied selection, on per-rule configuration, or on the absence of elevation. It should also hold for background work, automation and credential-based (API key) access, which in the reference carry no tenant or company binding (PC-35, PC-40).
- **O7: who can move the boundary.** In the reference, a delegated access-administration role can create, edit and archive the very rules that separate companies, can change group membership including the top administrative group, and can set other users' credentials (PC-28, PC-29, R3). Implication: SMEsPlus should define who may change isolation rules and role grants as its own governed control, separate from the tenant's own administrator. Changes to isolation-relevant configuration should be attributable and reviewable. Tenant-level administrators should not be able to widen their own scope or reach outside the tenant.
- **Adjacent (S5, R2).** In the reference, background and automated effects run with unrestricted authority while recording a user identity that can look ordinary, or with the platform's own superuser identity. Implication: SMEsPlus audit design should record "who initiated" and "under what authority/scope" as distinct facts.

Routing: `smesplus-data-architecture-expert` (tenant/company scoping) and `smesplus-iam-access-control` (role administration, delegated scopes). Boss remains final authority.
