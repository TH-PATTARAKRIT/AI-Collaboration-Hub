## 5. Approved Two-Tier Product / Deployment Model

There are only TWO deployment tiers:

### 5.1 STANDARD
- Shared Resource
- Multi-tenant Cells
- Cost optimized for Thai SMEs
- Many Standard servers/cells are allowed
- Horizontal scaling by adding Cells/Servers

### 5.2 ENTERPRISE
- Dedicated Resource
- Dedicated Tenant Environment
- Stronger isolation / SLA / performance sizing

There is no separate PRIVATE commercial tier.
What might otherwise be called private/dedicated is handled under ENTERPRISE.

Deployment Tier != Company Size
Deployment Tier != Number of Companies
Deployment Tier != Holding Structure
Deployment Tier = Resource Isolation + SLA + Operational Requirement

## 6. One Product, One Core, Many Cells

Mandatory product invariant:

ONE SMEPLUS PRODUCT
ONE CORE CODEBASE
MANY DEPLOYMENT CELLS

Standard and Enterprise must NOT become separate source-code products.

Infrastructure scaling belongs to SaaS/Deployment Architecture, NOT customer-specific source-code forks.

A future deployment may include large numbers of Standard servers/cells. This is allowed if routing, placement, version compatibility, security, capacity and operations remain controlled.

Standard for the entire country must NOT depend on one national monolithic application/database/server installation.

Both tiers must preserve the same minimum integrity for:

- Security
- Accounting correctness
- Transaction integrity
- Auditability
- Backup / restore
- Reconciliation
- Upgradeability

Shared by default for affordability.
Dedicated by choice or requirement.

## 13. Cell Capacity Model

Do NOT freeze a rule such as `1 Cell = 1000 tenants` as an architecture constant.

A Cell is governed by a measurable CAPACITY ENVELOPE.

At minimum assess:
- active tenant count
- transaction throughput
- data volume/storage
- DB load / IOPS
- CPU
- memory
- background/queue jobs
- heavy reports
- integration load
- AI workload where applicable
- latency/response indicators
- safety margin

When threshold is approached:
STOP NEW PLACEMENT
-> ADD OR USE ANOTHER STANDARD CELL

Capacity should scale by adding Cells before overloading a Cell.

## 15. Engineering Capability Direction

SMEsPlus clean-room ERP requires system-engineering discipline, not ordinary CRUD web development only.

Adopt with controlled refinement:

### 15.1 Domain-Driven Design
- Strong domain boundaries
- Bounded Contexts
- Explicit contracts
- Avoid spreading monolith coupling
- Do NOT mandate microservices merely because DDD is used

### 15.2 Business State Machines
For material documents define:
- Allowed Transition
- Forbidden Transition
- Actor
- Preconditions
- Side Effects
- Reversal
- Audit Event

### 15.3 TypeScript / Runtime / Database Integrity
Use strict domain contracts where appropriate.
Integrity is layered:
Type Safety + Runtime Validation + Database Integrity + Authorization + Business Invariants

### 15.4 High-Integrity Transactions
Design around business invariants first.
Then select appropriate transaction/isolation/locking strategy based on evidence.

Freeze the invariant, not the mechanism.

### 15.5 Idempotency
Retries, duplicate API calls, queue redelivery, webhook replay and timeout recovery must not accidentally create duplicate business effects.

### 15.6 Temporal Integrity
Model time explicitly where material:
- transaction date
- document date
- posting date
- accounting period
- effective date
- tax date
- FX rate date
- correction date

### 15.7 Immutable Historical Facts
Differentiate:
- Mutable Working State
- Immutable Finalized Historical Fact

Finalized financial/stock/payment/tax/approval/audit facts should use reversal/correction/adjustment facts rather than destructive history rewrite.

## 16. Database / Infrastructure Cost Direction

Target market is Thai SMEs.

Architecture objective:
**Minimize database/server/OS/infrastructure licensing and operational cost per Standard tenant while preserving security, accounting integrity, performance, recoverability, auditability and upgradeability.**

Do not force dedicated Enterprise infrastructure economics onto every Standard tenant.

Possible future mechanisms may include:
- PostgreSQL
- shared DB/cluster
- stronger Enterprise isolation
- dedicated Enterprise DB/resources
- shared or dedicated cache/queue/storage as justified

These are CANDIDATES, not frozen mechanisms.

Do not freeze PostgreSQL RLS, schema-per-tenant, DB-per-tenant, AsyncLocalStorage, distributed locks, microservices, or any exact topology without controlled design/evidence.
