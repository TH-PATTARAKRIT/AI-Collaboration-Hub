## 3. Removal Strategy vs Costing Method — Mandatory Relationship Finding

The governing clean-room rule requires this session not to treat warehouse removal/picking strategy as the same thing as an accounting costing method unless the reference ERP's own documentation explicitly ties them together, and to research and state the actual relationship rather than assume it.

**Finding: the reference documentation treats these as two independent concepts, and states this independence directly.** A removal strategy (evidenced under the labels First-In-First-Out, Last-In-First-Out, and First-Expired-First-Out across versions 13.0 through 19.0 — `Reference ERP official documentation — Removal Strategies, version 13.0/16.0/19.0, retrieved 2026-09-02`) determines **which physical lot/serial/unit is picked** when a location holds multiple incoming batches — a logistics/warehousing decision about physical selection. A costing method (Standard, FIFO, AVCO — see §4 below) determines **how the accounting value of inventory is computed** for the ledger. The documentation-derived synthesis obtained in this session states the distinction explicitly: removal strategy governs "which physical products are picked," costing method governs "how inventory value is calculated for accounting purposes," and that "you can choose one removal strategy (e.g., LIFO) while using a different costing method (e.g., FIFO) for financial reporting."

**A same-named coincidence exists and must not be mistaken for a tie.** The reference system offers a "First In First Out" *removal strategy* and a "First In First Out" *costing method* that share a label and, in the common case where a company also happens to use FIFO costing, tend to move together operationally — but the documentation does not state that selecting the FIFO removal strategy requires, causes, or implies the FIFO costing method, or vice versa. **Fact status: PROVISIONAL** — corroborated by a search-tool synthesis rather than a single verbatim-quoted authoritative sentence stating "these are independent"; file `04`/`11` should re-verify against a direct read of the current-version Product Category and Removal Strategies pages before this finding is upgraded to VERIFIED and used as a load-bearing precedent in the Product Category/Product override precedence matrix.

**SMEsPlus candidate implication (Layer C, CANDIDATE only):** if SMEsPlus preserves this reference distinction, warehouse removal policy (a Stock Truth / physical operations concern) and costing method (a Financial Truth / Accounting concern) should be modeled and governed as two separate policy axes, consistent with the Inventory-emits-facts / Accounting-decides-postings boundary — not collapsed into one "FIFO" setting. This is a candidate observation for `JT-01`/`JT-02`, not a decision.

## 4. Method-by-Method Deep Research

### 4.1 Standard Cost

| Sub-dimension | Evidence / Finding |
|---|---|
| Receipt cost formation | The product carries a fixed, manually-defined unit cost on the product record; a receipt does not change this cost. Evidence: `Reference ERP official documentation — Automatic Inventory Valuation Configuration, version 18.0, retrieved 2026-09-02` — "Standard Price" is described as the default costing method, cost "manually defined on the product form," used to compute valuation. Version 13.0 evidence uses near-identical wording ("products valued at manually-defined cost on product form"), indicating this mechanic is stable across the version range checked. |
| Issue cost release | Every outbound movement (delivery, consumption) releases inventory value at the same fixed standard cost, regardless of the actual price paid on any specific inbound lot. |
| Cost layer or average identity | No layering and no running average — a single scalar cost applies to the whole quantity on hand at any moment; the "identity" is the manually-set standard price itself, not a computed figure. |
| Price difference | This is the method's defining accounting exposure. Evidence: `Reference ERP official documentation — Inventory Valuation / Valuation Cheat Sheet, version 19.0, retrieved 2026-09-02` — a Price Difference Account is available specifically "when using Perpetual valuation with Standard Price costing," and "records the difference between the product's standard price... and the actual billed price." This is the mechanism by which a vendor bill priced above or below the standing standard cost does not distort the Inventory Asset account; the delta is diverted to the Price Difference Account instead. |
| Negative stock effect | Not materially exposed to the layering/estimation problems documented for FIFO (§4.3), because there is no layer to run out of — the standard cost applies uniformly whether the on-hand quantity is positive or negative. **Fact status: HOLD** — no direct documentation statement was found in this session confirming Standard Cost's negative-stock behavior is fully benign; this is an inference from the absence of a layering mechanic, not a cited statement, and must be independently verified before use as a design input. |
| Return cost basis | Both purchase and sales returns should, by the same fixed-cost logic, value at the current standard cost at the time of the return movement — no discrete "return recalculation" mechanic is needed because there is nothing to recalculate. **Fact status: HOLD** — inferred, not directly evidenced in the sources retrieved this session; file `19` must independently confirm. |
| Landed cost effect | A landed cost added after receipt under Standard costing does not change the standing standard price automatically; it would flow through the same Price Difference-adjacent mechanic used for vendor-bill-price variance, or require a manual standard-cost revision. **Fact status: HOLD** — the Landed Costs documentation reviewed this session (`Reference ERP official documentation — Landed Costs, version 18.0/19.0, retrieved 2026-09-02`) describes the general posting mechanic (additional valuation adjustment through a configurable journal) but was not read in this session specifically cross-referenced against Standard-cost interaction; treat as provisional until file `21` verifies. |
| Late supplier bill effect | A late vendor bill priced differently from the standard cost used at receipt is exactly the scenario the Price Difference Account exists to absorb (see row above); this is the clearest, most directly evidenced late-cost mechanic among the three native methods. |
| Cost method change | Evidence: `Reference ERP official documentation — Automatic Inventory Valuation Configuration, version 18.0, retrieved 2026-09-02` states explicitly: "Changing the costing method greatly impacts inventory valuation. It is highly recommended to consult an accountant first before making any adjustments here." Further evidence (documentation-search synthesis, this session): when the costing method changes *away from* Standard, "products already in stock that were using the Standard costing method do not change value; rather, the existing units keep their value, and any product moves from then on affect the [new method's] cost." |
| Existing-stock conversion | Per the row above, existing stock value is **not retroactively rebased** on a method change; only forward movements adopt the new method's mechanics. This is a materially important finding for migration design (file `26`) — it implies the reference system does not attempt a historical cost-layer reconstruction on method change, and any SMEsPlus candidate should not assume one is available "for free." |
| Close/reconciliation | Because Standard Cost holds a static value, period-close reconciliation activity concentrates on the Price Difference Account balance (unexplained/unreleased variance), not on recomputing inventory value itself. |
| Migration/opening balance requirements | Simplest of the three native methods to seed at cutover — a single opening standard cost per product, no layer history or running-average history required. This must still be evidence-checked against the actual opening-balance certification requirement in file `26` (`JT-11`/`G-5`), not assumed sufficient on its own. |
| COGS consequence — Periodic | Under Periodic, COGS as a discrete figure is not posted per-transaction (file `14` Row 3); Standard Cost's role under Periodic is chiefly to value the closing physical count consistently, feeding the Opening + Purchases − Closing = COGS-candidate identity (file `27`) with a stable per-unit figure. |
| COGS consequence — Perpetual | Under Perpetual, COGS is released at the standard cost per unit at the recognition event (file `14` Row 3, version-qualified `[pre-19]`/`[19+]`); any variance versus actual purchase cost is isolated in the Price Difference Account rather than distorting COGS, which is the method's principal accounting attraction under Perpetual. |

### 4.2 Average Cost (AVCO / Weighted Average)

| Sub-dimension | Evidence / Finding |
|---|---|
| Receipt cost formation | Evidence: `Reference ERP official documentation — Automatic Inventory Valuation Configuration, version 18.0, retrieved 2026-09-02` and corroborating version-13.0 wording — the cost is recalculated as "each product has the same value and this value is the average purchase cost," described in newer-version wording as "dynamic, and constantly adjusts based on the purchase price of products" (a weighted average, per the "weighted average of all units" phrasing evidenced against version-19.0 cheat-sheet retrieval). Each receipt event recomputes the single average identity by blending the new quantity/cost into the prior on-hand quantity/value. |
| Issue cost release | Every outbound movement releases value at the current weighted-average unit cost in effect at the moment of the movement — not a specific batch's cost. |
| Cost layer or average identity | A single running weighted-average figure, recomputed on each qualifying inbound movement; no discrete layers are retained (contrast FIFO, §4.3). |
| Price difference | A Price Difference Account concept is also evidenced for AVCO in an automated-valuation context: documentation-search synthesis this session states a journal entry is generated "when shipments that use AVCO costing method are received," with a configurable Price Difference Account handling the accounting adjustment — this differs from the Standard-cost usage of the same account type (Standard: variance vs a *fixed* cost; AVCO: adjustment arising around receipt-side accounting entries). **Fact status: PROVISIONAL** — drawn from search synthesis, not a verbatim-quoted primary sentence; file `21` should re-verify directly. |
| Negative stock effect | Not specifically evidenced in this session's retrieval (the negative-stock mechanic explicitly documented in the sources gathered was FIFO-specific — see §4.3). **Fact status: HOLD.** Do not assume AVCO's simpler single-average mechanic is immune to negative-stock estimation problems; it plausibly still requires an estimated cost for the negative portion, but no direct citation was obtained this session. |
| Return cost basis | Directly evidenced and materially important: `Reference ERP official documentation — Average Price on Returned Goods, version 19.0, retrieved 2026-09-02` states plainly that the system "does **not** automatically update the AVCO calculation, because this can potentially create inconsistencies with inventory valuation" — a return is valued at the average cost that existed when the goods left inventory (i.e., the return reverses the original outbound transaction's cost), and does **not** trigger a fresh weighted-average recomputation blending the returned quantity back in as if it were a new receipt. This is a specific, citable, non-obvious rule that any SMEsPlus candidate must treat as a genuine business-meaning question, not a default assumption either way. |
| Landed cost effect | A landed cost added under AVCO would, by the general average mechanic, be expected to blend into the running average on the next qualifying event — but this was not independently confirmed against the Landed Costs documentation in this session. **Fact status: HOLD**, owned by file `21`. |
| Late supplier bill effect | Consistent with the Price Difference Account finding above — a late bill priced differently from the receipt-time valuation is a documented trigger for an accounting adjustment under AVCO with automated valuation, though the exact posting mechanics were not read verbatim this session. **Fact status: PROVISIONAL.** |
| Cost method change | Same general warning applies ("greatly impacts inventory valuation... consult an accountant first," version 18.0 evidence, §4.1). AVCO-specific existing-stock treatment on a method change was not independently evidenced in this session beyond the general Standard-cost-framed statement in §4.1; file `15` follow-up (a future revision or file `26`) should confirm whether switching *into* AVCO seeds the average from the existing stock's carried value or from a fresh computation. **Fact status: HOLD.** |
| Existing-stock conversion | See row above — `HOLD`, not evidenced specifically for AVCO in this session. |
| Close/reconciliation | Because AVCO continuously recomputes a single figure, reconciliation activity concentrates on verifying the running average against a physical count and on any Price-Difference-Account balances, rather than on reconstructing per-batch history (there is none to reconstruct). |
| Migration/opening balance requirements | Requires seeding one opening average cost per product per company (and, if location- or lot-tracked cost pools exist, potentially per pool) — evidence for exact scope of "per what" was not independently confirmed this session; file `26` owns final scope. |
| COGS consequence — Periodic | As file `14` Row 3 states, Periodic does not post COGS transaction-by-transaction; AVCO's role is to provide a defensible, non-batch-specific per-unit value for the physical closing count feeding the Opening+Purchases−Closing identity. |
| COGS consequence — Perpetual | COGS is released at the current running-average unit cost at the recognition event; because the average continuously blends new purchase prices, COGS under AVCO/Perpetual will not exactly match any single receipt's actual cost, unlike Standard (deliberate, isolated variance) or FIFO (exact matched historical cost) — this is a defining trade-off to carry into `JT-02`. |

### 4.3 First In, First Out (FIFO)

| Sub-dimension | Evidence / Finding |
|---|---|
| Receipt cost formation | Each inbound movement creates a discrete valuation layer at its own actual cost; layers are not blended. Evidence: `Reference ERP official documentation — Automatic Inventory Valuation Configuration, version 18.0, retrieved 2026-09-02` — "First In First Out (FIFO)... tracks costs in real-time by lot," and version-13.0 wording: "financial FIFO," "the first value 'in' is the first value 'out'." |
| Issue cost release | Outbound movements consume the oldest remaining layer(s) first, at that layer's actual cost, until the layer is exhausted, then proceed to the next-oldest layer. Evidence: "the oldest purchase price used as the cost for the next good sold until an entire lot of that product is sold" (documentation-search synthesis, version 17.0/18.0 sources). |
| Cost layer or average identity | Discrete, ordered layers, each retaining its own individual valuation until consumed — evidenced directly: "remaining units from each previous incoming move retain their own individual valuation" (`Reference ERP official documentation — Automatic Inventory Valuation Configuration`, version 18.0, retrieved 2026-09-02). This is the method's defining structural difference from both Standard (one scalar) and AVCO (one running blend). |
| Price difference | Because FIFO uses each layer's real cost directly, the Price Difference Account mechanic evidenced for Standard costing does not apply in the same way; a vendor-bill price differing from the receipt-time valuation under FIFO is more naturally a valuation-layer correction than a diverted variance account entry. **Fact status: HOLD** — no direct FIFO-specific Price Difference Account statement was retrieved this session; do not assume the Standard-cost mechanic transfers unchanged. |
| Negative stock effect | The most directly and richly evidenced negative-stock mechanic among the three native methods. Documentation-search synthesis this session, corroborated by the "Using Inventory Valuation" documentation line (version 17.0/18.0): when stock goes negative under FIFO with automated valuation, the system values the negative-quantity outbound movement at an **estimated** price (there is no real layer to draw from yet), producing a "faulty valuation layer valued at an estimated price"; when a future receipt arrives, the system "compensates" that faulty layer using the new receipt's real price — "if the estimated price is equal to the real price, no layer is created and the original layer is marked as compensated" — otherwise a revaluation journal entry is generated automatically to true up the difference. A manual "Adjust Valuation" action is also documented as available against specific incoming-move layers. **This is a materially important, well-evidenced mechanic for JT-02 and for negative-stock policy generally** — negative stock under FIFO does not simply fail or block; it defers correct costing until a compensating receipt occurs, with an automatic correcting entry. |
| Return cost basis | Not independently evidenced for FIFO specifically in this session (the direct citation obtained, §4.2, was AVCO-specific). By the layer mechanic's own logic, a plausible (but **unverified, HOLD**) expectation is that a return either restores/re-creates a layer at the original outbound cost or creates a new inbound layer at the return's own cost — file `19` must resolve this with direct evidence rather than inference. |
| Landed cost effect | Landed Costs functionality (`Reference ERP official documentation — Landed Costs, version 18.0/19.0/17.0, retrieved 2026-09-02`) posts an additional valuation adjustment against the original receipt; under FIFO this most plausibly means the specific layer created by that receipt is revalued upward, which is a materially different mechanic than AVCO's blend-into-running-average or Standard's Price-Difference-Account diversion. **Fact status: HOLD** — the layer-specific interaction was not independently confirmed this session; file `21` owns resolution. |
| Late supplier bill effect | A late bill priced differently from the receipt-time layer value is the general trigger documented for revaluation activity across the automated-valuation methods; FIFO's manual "Adjust Valuation" action (documentation-search synthesis, this session) — selecting the incoming move, then an "Adjust Valuation" action with a new Value and optional Description — is the most directly evidenced correction mechanic of the three methods for a manually-triggered late-cost correction. |
| Cost method change | Same general "greatly impacts inventory valuation... consult an accountant first" warning applies (version 18.0 evidence, §4.1). FIFO-specific behavior when switching *away from* FIFO (what happens to open layers) or *into* FIFO (whether prior undifferentiated stock becomes a single opening layer or is rejected) was not independently evidenced this session. **Fact status: HOLD.** A related community-sourced question found during research ("How to Reset Negative Stock Valuation Layers Before Switching to FIFO") indicates this is a recognized practical problem area in the reference ecosystem, reinforcing that it needs direct, authoritative documentation confirmation before SMEsPlus relies on any assumption here — that source itself is not treated as authoritative evidence in this file. |
| Existing-stock conversion | See row above — `HOLD`. |
| Close/reconciliation | Reconciliation activity under FIFO concentrates on verifying the sum of all open layers against the physical count, and on resolving any outstanding negative-stock "faulty layers" awaiting compensation (see Negative stock effect row). |
| Migration/opening balance requirements | The most demanding of the three native methods to seed at cutover: an accurate opening-layer history (quantity and cost per layer, in arrival order) is required to preserve correct future issue costing; a single blended "opening value" is insufficient in the way it would be for AVCO or Standard. This is a first-class input to file `26` and to `JT-11`/`G-5`. |
| COGS consequence — Periodic | As with the other methods, Periodic does not post COGS transaction-by-transaction; FIFO's role is to provide the most granular, actual-cost-based valuation of remaining closing stock, which — if fully layered from an accurate opening position — gives the closing-inventory figure in the Opening+Purchases−Closing identity a stronger actual-cost basis than AVCO or Standard. |
| COGS consequence — Perpetual | COGS is released at the actual historical cost of the specific layer(s) consumed, giving the most granular, audit-traceable actual-cost COGS figure of the three native methods, at the cost of the highest bookkeeping/migration complexity and the documented negative-stock estimation-and-compensation mechanic above. |

### 4.4 Specific Identification — Business/Accounting Requirement, Not a Native Selectable Method

| Sub-dimension | Evidence / Finding |
|---|---|
| Native availability | **Not present as a selectable costing method in the reference ERP's own documentation** across the versions searched (13.0 through 19.0/18.0/17.0/16.0). Search evidence this session found only third-party/marketplace extension modules adding a "Specific Identification Costing" capability for a mid-range version, explicitly outside the reference vendor's own documentation set and therefore **outside this session's Layer A evidence boundary** (per the clean-room rule, extension/community modules are not "the reference ERP's own documentation"). This absence is itself the material finding requested by governing prompt §9: Specific Identification is being researched here as a **business/accounting requirement**, not as an observed reference-UI method. |
| Receipt cost formation | By definition (not reference-evidenced, general accounting-method definition carried for structural completeness only): each physical unit or serial/lot-identified unit is tracked and valued at its own actual, individually-traceable cost from receipt. |
| Issue cost release | Each issued unit releases exactly its own actual cost, identified by lot/serial, regardless of arrival order — structurally the opposite of FIFO's ordering assumption and AVCO/Standard's blending/fixed assumption. |
| Cost layer or average identity | One discrete identity per physically identified unit or lot — the most granular possible, by definition, more granular than FIFO's arrival-ordered layers (FIFO layers can still contain multiple fungible units; Specific Identification distinguishes even within an arrival batch when units are individually distinguishable, e.g., serialized goods, unique high-value items). |
| Price difference / negative stock / return cost basis / landed cost / late bill / cost method change / existing-stock conversion / close-reconciliation / migration | **Not evidenced** — because this is not an implemented reference-ERP method, none of these sub-dimensions has reference-ERP behavior to cite. Each is `UNKNOWN / HOLD` in Layer A terms. Structurally, Specific Identification would be expected to have the *simplest* return-cost-basis and negative-stock story of any method (a returned or negative unit is definitionally traceable to its own specific cost, with no estimation needed) — but this is a Layer C structural inference, not evidence, and must not be presented as a reference-observed fact. |
| Thai/IAS-2-family relevance (Layer B posture) | Per the governing clean-room rule for this file: Specific Identification is a legitimate accounting/business requirement under Thai and IAS-2-family inventory-measurement standards, applicable for inventories of items that are not ordinarily interchangeable, and for goods or services produced and segregated for specific projects, **regardless of** whether the reference ERP implements it as a selectable UI method. This is noted here as the reason this method cannot be dismissed simply because the reference vendor's UI omits it. **This is classified `INTERPRETATION — REVIEW REQUIRED`, not `AUTHORITATIVE / VERIFIED`** — this file does not carry Thai statutory authority; file `24` owns the authoritative Thai/TFRS-family determination of when Specific Identification is required (e.g., for non-interchangeable or project-segregated inventory) versus merely permitted versus not addressed. This file's role is limited to preventing the false conclusion "the reference ERP doesn't offer it, so SMEsPlus doesn't need it" — that conclusion is explicitly rejected by the governing prompt and by this finding. |
| COGS consequence — Periodic / Perpetual | Not reference-evidenced (no native mechanic exists to observe). Structurally, under either timing pattern, Specific Identification's COGS release would by definition equal the exact traceable cost of the specific units sold — the strongest possible actual-cost matching of any method discussed, at the operational cost of requiring unit/lot-level cost tracking discipline throughout the physical and financial lifecycle. This is a Layer C structural statement, not a Layer A citation. |

## 6. Price Difference Account — Cross-Method Note

The Price Difference Account is directly and richly evidenced for **Standard Cost under Perpetual/automated valuation** (§4.1) and provisionally evidenced for **AVCO under automated valuation on receipt** (§4.2). It is **not evidenced for FIFO** in the sources retrieved this session, and layer-based revaluation/compensation appears to be FIFO's own distinct mechanic instead (§4.3). Treat the Price Difference Account as a Standard-cost-primary concept that may or may not generalize to other methods — do not assume a single "price difference" behavior applies uniformly across all four methods when building the SMEsPlus candidate contract (file `31`, Contract A).

## 7. Costing Method Change — Cross-Method Treatment

One documented rule applies generally, evidenced at `Reference ERP official documentation — Automatic Inventory Valuation Configuration, version 18.0, retrieved 2026-09-02`: changing the costing method "greatly impacts inventory valuation," an accountant consultation is recommended before the change, and — per the Standard-cost-framed synthesis obtained this session — **existing on-hand stock value is not retroactively rebased**; only movements from the change forward adopt the new method's mechanics. This is treated as a general finding applicable across methods in this session's evidence, but only the Standard-cost direction of the change (moving away from Standard) was directly evidenced; AVCO- and FIFO-specific change behavior (both moving away from and into each method) is `HOLD`, and file `15`'s eventual successor review (or file `26`) must independently confirm each direction of change before any migration design relies on it. This directly informs `JT-02`'s "change rules" scope.
