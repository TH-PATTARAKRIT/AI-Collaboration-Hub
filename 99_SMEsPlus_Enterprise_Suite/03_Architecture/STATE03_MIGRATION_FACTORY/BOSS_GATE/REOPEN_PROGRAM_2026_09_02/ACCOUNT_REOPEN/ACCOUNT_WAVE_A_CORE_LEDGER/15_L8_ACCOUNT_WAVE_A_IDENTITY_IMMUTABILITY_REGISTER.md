## 3. Temporal validity

No effective dating exists on any entity. The complete temporal model is one accounting date per
entry, one document date, one due date, one maximum-match date, five lock dates, one rate per day,
and optional fiscal-year records.

**Consequence.** Every configuration change applies retroactively to all history. A chart
reorganisation, an account-type change, or a merge rewrites the meaning of past reports.

## 5. The SMEsPlus immutability model — recommendation

Offered as `RECOMMENDATION` for Boss decision, derived from the evidence rather than from convention.

1. **The accounting event is the immutable unit.** It has its own identity, independent of the entry
   that presents it, and independent of any storage identifier.
2. **Immutability is unconditional.** Not a journal setting, not a company flag, not dependent on
   which module is calling. If it can be switched off, it is not immutability.
3. **Correction is additive, always.** Reversal plus re-entry, with an explicit link between the two
   so that "what was corrected, and by what" is answerable — which it is not in the reference model.
4. **Derived values are never authoritative and must be reconstructible.** Residual, payment state,
   ageing, current-year earnings and analytic lines all qualify.
5. **Provenance is part of the fact, not metadata attached to it.** Source system, source event
   identity, extraction lineage and idempotency key travel with the event permanently.
6. **Tamper-evidence keys on business identity, not on storage identity** — otherwise it cannot
   survive the migration it is most needed for (`COR-12`).
7. **Classification identity is permanent; labels are versioned.** Replacement is a succession
   relationship, never a rewrite.
