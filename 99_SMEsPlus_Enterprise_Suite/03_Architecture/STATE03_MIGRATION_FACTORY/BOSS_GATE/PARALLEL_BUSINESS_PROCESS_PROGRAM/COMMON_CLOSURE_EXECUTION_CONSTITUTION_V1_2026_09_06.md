# COMMON CLOSURE EXECUTION CONSTITUTION v1
# Bounded-Deep Closure, Challenger Recursion, Evidence Convergence & Terminality
# Effective: 2026-09-06
# Project: SMEsPlus ENTERPRISE SUITE

## 1. PURPOSE

This constitution governs every SMEsPlus **Closure Prompt**.

A Closure Prompt is not a shortened Deep Research prompt and is not permission to restart broad discovery.
Its purpose is to drive a declared evidence set and a declared question set to a defensible terminal state.

Canonical closure behavior:

`Closure -> Challenger finds a gap -> bounded in-scope deepening -> material delta -> re-challenge -> reconciliation -> repeat only while material in-scope delta exists -> terminal disposition -> stop.`

The essential constraint is monotonic scope:

**A Closure Prompt may stay at the same scope or narrow its scope. It must never broaden its scope.**

Closure must nevertheless go as deep as necessary inside the declared scope to understand every material causal mechanism, contradiction, denominator, boundary and failure mode required to answer the declared closure questions.

## 2. CLOSURE COMPLETENESS — PRECISE MEANING

"Deep until everything is known" means:

- every **declared Closure Question** is fully traced to evidence or to a named terminal dependency;
- every directly-derived material subquestion needed to answer a Closure Question is also terminally dispositioned;
- every contradiction that can alter the answer is reconciled or preserved with a named unresolved dependency;
- every load-bearing negative claim has a declared denominator, search boundary and positive/failure control;
- every material cross-process consequence is routed to its proper owner;
- no material background task or execution commitment is left undeclared.

It does **not** mean universal omniscience about the entire ERP, entire repository, all backups, all versions, or every adjacent process.

The unit of completeness is the **declared Closure Question Set**, not the whole world.

## 4. MONOTONIC CLOSURE SCOPE RULE

At prompt start, declare:
1. Closure Question IDs.
2. Allowed domains/process boundaries.
3. Allowed source/module/model/function boundaries.
4. Allowed database/deployment/evidence populations.
5. Allowed cross-process interfaces.
6. Explicit exclusions.

During execution, a newly discovered gap is classified before any further search:

### CLASS A — IN-SCOPE DERIVED SUBQUESTION
The gap is directly necessary to answer a declared Closure Question.
Action: deepen only along the shortest causal/evidence path necessary to resolve it.

### CLASS B — SAME-SCOPE MATERIAL CONTRADICTION
New evidence materially contradicts an in-scope finding.
Action: reopen only the affected finding and its direct dependencies; preserve all prior versions.

### CLASS C — CROSS-PROCESS / OUT-OF-SCOPE
The gap belongs to another Pxx/domain.
Action: create a handoff with exact evidence and question. Do not investigate the receiving process from the current process.

### CLASS D — MUTATION / EXTERNAL / BOSS DECISION REQUIRED
The question cannot be resolved read-only or with currently authorised evidence.
Action: create a named HOLD or bounded Boss Authorisation Pack. Continue unaffected closure work.

### CLASS E — NON-MATERIAL / CORROBORATIVE ONLY
The gap cannot change a declared Closure Question or gate.
Action: record if useful; do not open a new search round.

A Closure Prompt must never convert Class C, D or E into a broad discovery mandate.

## 5. CHALLENGER RECURSION — ALLOWED, BUT BOUNDED

Challenge recursion is required because challenge findings have repeatedly corrected material errors.

The permitted loop is:

`Bounded Evidence Pass`
`-> 4 AAS-03 Independent Challenges`
`-> AAS+ Reconciliation`
`-> Material Delta Test`

If and only if a material in-scope delta exists:

`Affected Question Reopened`
`-> Bounded Deepening`
`-> Re-derive Finding`
`-> Re-challenge Corrected Finding`
`-> Reconcile`

Repeat until convergence.

There is no artificial round limit when a genuine **material in-scope delta** continues to exist.
However, every additional loop must record:
- the Material Delta ID;
- the Closure Question ID affected;
- why the previous evidence was insufficient;
- the exact bounded evidence surface to inspect;
- the expected stop condition.

A challenger may force greater depth, but may not enlarge the domain.

## 6. SEARCH BOUNDARY REQUIREMENTS

Before every material source/database/filesystem search, declare:
- Closure Question ID;
- Evidence purpose;
- exact module/model/function or database population;
- path/root boundary;
- denominator unit;
- expected result class;
- stop condition.

Forbidden by default inside Closure:
- unbounded `find all` across the whole estate;
- whole `/Volumes` traversal;
- whole Google Drive/CloudStorage traversal;
- whole backup/archive sweep;
- whole repository census;
- all-version enumeration unrelated to a declared question;
- recursive search of adjacent Pxx domains.

Such a search is allowed only if the Closure Question itself explicitly defines that population and no narrower evidence route can answer it. The reason must be recorded before execution.

## 7. DENOMINATOR AND NEGATIVE-CLAIM CONTROL

A negative finding is not valid merely because a search returned zero.

Every load-bearing negative claim must declare:
- population denominator;
- selection unit;
- source/path set;
- version/generation boundary;
- positive control;
- failure control where applicable;
- search/instrument independence;
- known blind spots.

`Empty result != absence.`
`Same zero != same cause.`
`Source present != installed.`
`Installed != configured.`
`Configured != exercised.`
`Exercised != economically correct.`

## 8. BACKGROUND TASK GOVERNANCE

Every background task must have:
- Task ID;
- Closure Question ID;
- exact command/objective;
- bounded path/evidence population;
- start time;
- load-bearing vs corroborative classification;
- expected stop condition.

If a stronger route has already settled the question, a secondary corroborative task must be dispositioned rather than waited on.

If a task appears long-running, blocked, overbroad or non-progressing, perform a non-destructive health check. Preserve diagnostics before termination when termination is justified.

A terminal report is invalid while an undispositioned background task remains.

## 9. CROSS-PROCESS OWNERSHIP

A current Pxx may inspect an adjacent process only at the causal interface required to answer its own declared Closure Question.

If evidence opens a new question owned by another Pxx:
- preserve the source evidence;
- write the exact question;
- classify materiality;
- name the receiving owner;
- create/update handoff;
- STOP at the boundary.

Do not solve the receiving process inside the sending process.

## 10. FOUR AAS-03 CHALLENGERS

Every material Closure Prompt retains four independent AAS-03 perspectives:
1. Leader Functional Design
2. Leadership Database Design
3. Lead Integration & Localization
4. Lead Code & UI Architect

Each challenge must state:
- supported;
- missing;
- risky;
- challenged;
- evidence needed next.

At least one challenge should actively attempt to disprove the most consequential current conclusion.

Challenge output is evidence pressure, not a verdict.

## 11. TERMINAL DISPOSITIONS FOR EVERY CLOSURE QUESTION

No Closure Question may remain as a vague `OPEN`.

Each must end as exactly one of:
- `FACT VERIFIED — CLOSED FOR CURRENT EVIDENCE`
- `CONTRADICTED — CORRECTED AND CLOSED FOR CURRENT EVIDENCE`
- `UNRESOLVED — SPECIFIC EVIDENCE UNAVAILABLE`
- `BOSS DECISION REQUIRED — DECISION PACKAGE READY`
- `EXTERNAL / CROSS-PROCESS OWNER — HANDOFF PUBLISHED`
- `OUT OF SCOPE — ROUTED WITH EVIDENCE`

A named HOLD is a valid terminal closure state for the current execution envelope when the exact missing dependency is explicit.

## 12. CLOSURE TERMINALITY AUDIT

Before reporting terminal:
- every Closure Question has one terminal disposition;
- all material derived subquestions have terminal dispositions;
- all material contradictions are reconciled or named holds;
- all handoffs are published;
- all background tasks are finished or dispositioned;
- checkpoint is current;
- AUTO_RESUME_STATE records the exact next action if reopened;
- commit is pushed;
- remote HEAD equals intended final commit;
- no silent mutation occurred;
- no receiving Pxx was executed from the current Pxx;
- no merge or Final Freeze was inferred.

## 13. STOP RULE

When the declared Closure Question Set is terminally dispositioned:

`COMMIT -> PUSH -> VERIFY REMOTE -> UPDATE CHECKPOINT -> UPDATE AUTO_RESUME_STATE -> TERMINAL REPORT -> STOP.`

Do not keep searching merely because more information might exist.
Do not create another research round without a new material in-scope delta.

## 14. GOVERNANCE STATUS

This constitution governs execution behavior only.
It does not itself declare any domain PASS, Final Freeze, design approval, merge authority or implementation authority.
Boss remains the sole Final Approver.
