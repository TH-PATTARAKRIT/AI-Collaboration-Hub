## 1. GAP-BRP-01 — เปลี่ยนชนิด BoM (Manufacture ↔ Kit) หลังถูกใช้แล้วได้ไหม

**ได้ — ไม่มีการล็อก** ระบบไม่มีกฎห้ามแก้ชนิด BoM แม้มีเอกสารเปิดค้างอยู่

- ช่อง "BoM Type" เป็นฟิลด์ธรรมดา ไม่มีเงื่อนไขล็อกหรือ constraint
- มี **คำเตือนบนหน้าจอเท่านั้น** (ไม่ใช่กฎบังคับ) เมื่อแก้โครงสร้างของ **Kit ที่เคยถูกใช้แล้ว** แนะนำให้ archive แล้วสร้างใหม่แทน — เตือนเฉพาะการแก้ผ่านฟอร์ม ไม่ครอบคลุมการนำเข้า/API
- **ผลต่อเอกสารเปิดค้าง:** Odoo มี test จำลอง "ใบส่งของถูกยืนยันไว้ → เปลี่ยนสินค้าเป็น Kit → ตอนกด Validate" : ระบบ **แตกรายการสินค้าเป็นส่วนประกอบใหม่ในใบส่งของนั้น** และการลงบัญชีเกิดที่ **ส่วนประกอบ ไม่เกิดที่ตัวสินค้าเดิม** (ไม่มีรายการบัญชีของสินค้าที่ถูกเปลี่ยนเป็น Kit)
- การแก้ BoM (ส่วนประกอบ/จำนวน/สินค้า) จะ **ติดธงว่า "BoM ล้าสมัย"** บน MO ที่ยัง Draft/Confirmed เท่านั้น ; **การเปลี่ยนชนิดไม่อยู่ในรายการฟิลด์ที่ติดธง**

**ความเสี่ยงต่อ Migration/การควบคุม:** การสลับ Kit ↔ Manufacture กลางทางเปลี่ยน "รูปแบบการรับรู้บัญชี" ของเอกสารที่ยังไม่ปิด — ควรมีนโยบายห้ามสลับชนิดขณะมี SO/DO/MO เปิดค้าง (ระบบไม่บังคับให้)

## 2. GAP-BRP-02 — Kit มี Operations (ขั้นตอนผลิต) ได้ไหม / ผลด้านมูลค่า

- ระบบ **ไม่ห้าม** Kit ที่มี Operations (ไม่มี constraint) และมี test ที่จงใจสร้าง Kit พร้อม Operations แยกตามสี/variant
- **ขายหรือส่ง Kit โดยตรง:** ไม่มี MO — Kit ถูกแตกเป็นส่วนประกอบตอนยืนยัน/ตรวจรับ Operations ของ Kit **ไม่ถูกเรียกใช้** และไม่เกิดต้นทุนแรงงาน
- **ใช้ Kit เป็นส่วนประกอบของสินค้าที่ผลิต:** Operations ของ Kit **ถูกดึงไปเป็น Work Order ของ MO แม่** (ยกเว้นกรณี Operations ชุดเดียวกับของ BoM แม่) — นี่คือกรณี hybrid ที่ "Kit มีขั้นตอนผลิต" ทำงานจริง และต้นทุนแรงงานเข้า MO แม่
- **มูลค่า:** สินค้าที่เป็น Kit ถูกตั้งมูลค่าเป็น **0** ในรายงานมูลค่าสต็อก (กันนับซ้ำ) ; มูลค่าอยู่ที่ส่วนประกอบ
- ⇒ ตอบ hybrid case: "sell-and-lightly-assemble" **ไม่ทำงานผ่านการขาย Kit** ; ถ้าต้องการประกอบเบา ๆ ที่มีต้นทุนแรงงาน ต้องออกแบบเป็น BoM แบบ Manufacture

## 3. GAP-BRP-04 — อัตรา Work Center ผันแปรตามกะ/ล่วงเวลาได้ไหม

## 4. GAP-BRP-05 — BoM ที่ปิด Work Orders / การติดตาม expected vs actual

- ถ้า BoM **ไม่มี Operations** (หรือไม่ได้เปิดฟีเจอร์ Work Orders/Routing) → MO **ไม่มี Work Order** ต้นทุน = วัตถุดิบ + Extra Unit Cost เท่านั้น ; ไม่มีต้นทุนแรงงาน ไม่มีรายการบัญชีแรงงาน ; ไม่มีการติดตามเวลา
- ถ้าเปิดใช้: ระดับ **Work Order** เก็บ "เวลาคาดหมาย" กับ "เวลาจริง" และคำนวณ **% ส่วนต่าง** = (คาดหมาย − จริง) ÷ คาดหมาย ×100 (บวก = เร็วกว่าแผน) และเวลาต่อหน่วย
- **ไม่มี** การสรุปส่วนต่างเป็นรายการบัญชีแยก (variance account) ใน Community ; ส่วนต่างเป็นข้อมูลรายงาน ไม่ใช่การลงบัญชี
- ปิด MO โดยไม่บันทึกเวลา → ระบบใช้ **เวลาคาดหมายเป็นเวลาจริง** (100%) จึงไม่เห็นส่วนต่าง

## 5. GAP-BRP-08 — MPS (Master Production Schedule) ป้อนกระบวนการอัตโนมัติอะไรบ้าง

**ไม่พบโมดูล MPS ใน source Community** (ไม่มีโมดูล `mrp_mps` ในรายชื่อโมดูล `mrp*` ทั้งหมด) — มีเพียง **ร่องรอยในโค้ด `mrp`** ที่เตรียมรองรับแหล่งที่มา "MPS" (การไม่ผนวกคำสั่งซื้อเข้า MO เดิมเมื่อต้นทางคือ MPS) แปลว่า MPS เป็นโมดูลนอก Community ที่เชื่อมเข้ามา

⇒ **ตอบไม่ได้จาก source ชุดนี้ว่า MPS ป้อนอะไร** และ (ตามข้อกำหนด Clean-Room) ไม่ควรอนุมานจากโมดูลนอก Community
⇒ **ข้อเสนอ:** ปรับสถานะ `GAP-BRP-08` เป็น "**Out of Community scope**" ; ถ้า SMEsPlus ต้องใช้ MPS ต้องระบุแหล่งที่มา (ต่างเวอร์ชัน/ต่างใบอนุญาต) ก่อนวิจัย

> หมายเหตุเชื่อมโยง: ค้น `quality`, `planning` ก็ไม่พบโมดูล Quality ใน source Community เช่นกัน (มีผลกับ `GAP-QCP-02` — จะรายงานใน pilot Quality)

## 6. GAP-BRP-07 — Reordering Rule (Auto) มีขั้นตอนอนุมัติก่อนสร้างคำสั่งหรือไม่

- **Trigger = Auto** : ตัวจัดตารางเวลา (Scheduler) รัน **ทุกวัน** โดยผู้ใช้ระบบ (OdooBot) และสร้างการจัดหา (procurement) ทันทีเมื่อ "จำนวนที่ต้องสั่ง > 0" — **ไม่มีขั้นตอนอนุมัติก่อนสร้าง**
- **แต่เอกสารที่สร้างขึ้นเป็น "ร่าง" ที่ต้องมีคนยืนยัน** :
  - **ซื้อ:** ใบขอราคา (RFQ) สถานะ Draft — ต้องยืนยันเป็น PO ; บริษัทเปิด "Double validation" (อนุมัติสองชั้นตามวงเงิน) ได้
  - **ผลิต:** MO ที่มีส่วนประกอบและมาจาก Reordering Rule **ไม่ถูกยืนยันอัตโนมัติ** (คงเป็น Draft) ; MO ที่ไม่มีส่วนประกอบและไม่มี Work Order ถูกยืนยันอัตโนมัติ
- **Trigger = Manual** : ผู้ใช้กด "Replenish" เอง (สิทธิ์ผู้จัดการคลังจึงจะแก้กฎได้; ผู้ใช้คลังทั่วไปอ่านได้อย่างเดียว)
- ถ้าจัดหาไม่ได้ (ไม่มีผู้ขาย/เส้นทาง) : ระบบ **ไม่หยุดทั้งชุด** สร้างกิจกรรมเตือนบนสินค้า มอบให้ผู้รับผิดชอบสินค้า
- ⇒ "เกต" ของ Odoo อยู่ที่ **การยืนยันเอกสารที่สร้างขึ้น** ไม่ใช่ก่อนสร้าง ; ความเสี่ยง: RFQ/MO ร่างจำนวนมากสะสมถ้าไม่มีวินัยตรวจ

## 7. GAP-BRP-10 — ต้นทุนวัตถุดิบระดับล่างเปลี่ยน กระทบ MO ที่เสร็จแล้วไหม

**ไม่กระทบ MO ที่เสร็จแล้ว** :
- มูลค่าของ stock move เก็บเป็น **ตัวเลขที่บันทึก ณ ตอนเสร็จ** (ไม่ใช่ค่าคำนวณสด) ; MO ที่ปิดแล้วไม่ถูก re-cost ย้อนหลังเมื่อราคาส่วนประกอบเปลี่ยน
- **การเปลี่ยนราคามาตรฐาน (Standard/Average) ด้วยมือ** ระบบสร้าง "รายการปรับมูลค่า" ณ วันที่เปลี่ยน กระทบ **มูลค่าสต็อกคงเหลือ** ไม่ใช่มูลค่าของ move ที่ผ่านมา ; สินค้า FIFO ข้ามขั้นตอนนี้ (ต้นทุนมาจากล็อตจริง)
- **ทุกระดับของ BoM ซ้อน:** ต้นทุน MO ระดับบนคิดจาก **มูลค่าที่ใช้จริงของ move วัตถุดิบ** ตอนผลิต (สินค้ากึ่งสำเร็จรูปที่ผลิตมาแล้วมีต้นทุนของมันเองตามวิธีต้นทุน) จึงไม่ "ไหลย้อน" ; ต้นทุนใหม่มีผลกับ MO ที่จะผลิต **ในอนาคต**
- **ข้อยกเว้นที่ควรรู้:** ปุ่ม "คำนวณราคาจาก BoM" (สำหรับราคามาตรฐาน) คำนวณจาก **ราคามาตรฐานปัจจุบัน** ของส่วนประกอบ แบบเรียกซ้ำได้ตาม BoM ลูก — เป็นการกระทำโดยผู้ใช้ ไม่ใช่การปรับอัตโนมัติ
- **Landed cost** เพิ่มมูลค่าให้ move ที่ปิดแล้วได้ (ตั้งใจ) — เป็นข้อยกเว้นเชิงออกแบบ
