## 2. Recurrence

### 2.1 `calendar.recurrence` (calendar/models/calendar_recurrence.py)

**Model constants** (lines 17–79):
- `MAX_RECURRENT_EVENT = 720`
- `RRULE_TYPE_SELECTION`: daily/weekly/monthly/yearly
- `END_TYPE_SELECTION`: count/end_date/forever
- `MONTH_BY_SELECTION`: date/day
- `WEEKDAY_SELECTION`: MON–SUN
- `BYDAY_SELECTION`: 1st/2nd/3rd/4th/Last

**Key fields** (lines 97–122):
- `rrule` — stored Char, computed by `_compute_rrule()` (line 207), inverse `_inverse_rrule()` (line 216)
- `base_event_id` — Many2one to `calendar.event` — line 98
- `calendar_event_ids` — One2many to `calendar.event` — line 100
- `event_tz` — timezone Selection — line 101
- `until` — Date (end_type='end_date') — line 121
- `trigger_id` — Many2one `ir.cron.trigger` — line 122

**`_compute_rrule()`** (lines 207–214): Calls `_rrule_serialize()`. Written to `rrule` field only if changed. This prevents infinite write loops.

**`_inverse_rrule()`** (lines 216–225): Parses stored `rrule` string via `_rrule_parse()`. Handles timezone-aware UNTIL=...Z values by converting to recurrence local TZ.

**`_get_rrule()`** (lines 584–627): Core method. Returns `dateutil.rrule.rrule` object. Enforces:
- `MAX_RECURRENT_EVENT = 720` hard cap
- `calendar.max_recurrence_years` ir.config_parameter (default 15 years)
- For `end_type='forever'`: calculates count from years limit
- For `end_type='end_date'`: uses `UNTIL = datetime.combine(self.until, time.max)`

**`_rrule_parse()`** (lines 399–447): Model method. Parses iCal RRULE string back to Odoo field values. Strips X-prefixed extensions. Uses `dateutil.rrule.rrulestr()`.

**`_range_calculation()`** (lines 491–510): Handles past-occurrence trimming when applying recurrence. If `count` would produce too few future events, temporarily doubles count, then restores.

**`_split_from()`** (lines 320–342): Splits recurrence at a given event. Stops old recurrence, creates new one. Used for "This and following events" edit mode.

**`_apply_recurrence()`** (lines 248–287): Creates missing recurrence events. Calls `_reconcile_events()` to avoid duplicates. Creates new events with `no_mail_to_attendees=True`.

**`_setup_alarms()`** (lines 289–318): Schedules cron triggers per recurrence. Queries next future event per recurrence, calls `calendar.event._setup_alarms()` on it.

**MIGRATION FLAG**: In v19, the `recurrent_id` field (used in older versions to link individual recurrence occurrences back to the base event) is **not present** on `calendar.event`. The link is solely via `recurrence_id` (Many2one to `calendar.recurrence`) and `follow_recurrence` boolean. Any legacy migration data using `recurrent_id` must be adapted.

## 4. Alarms and Notifications

### 4.1 `calendar.event._setup_alarms()` (lines 1262–1282)

Called from `create()` and `write()`. For each alarm in `alarm_ids`:
- `alarm_type == 'email'`: Schedules an `ir.cron.trigger` at `event.start - alarm.duration_minutes`
- `alarm_type == 'notification'`: Calls `calendar.alarm_manager._notify_next_alarm()` immediately

### 4.2 `calendar.alarm_manager._send_reminder()` (lines 182–199 in alarm_manager.py)

Executed via cron. Queries events where alarm time falls between cron `lastcall` and now. Sends via `attendee._notify_attendees(alarm.mail_template_id)`. Skips declined attendees.

### 4.3 `_get_trigger_alarm_types()` (line 1249–1250)

Returns `['email']`. Override point for extending alarm notification types.

## 5. Privacy and Multi-Company

### 5.1 Privacy enforcement (lines 746–766, 888–894, 896–901)

`_fetch_query()` override: For non-superuser, when private fields requested, computes `others_private_events`. For these, replaces `name` field with `'Busy'`, other private fields with `False`.

`_check_private_event_conditions()` (lines 888–894): Returns True if:
- `privacy == 'private'` OR (`privacy` is False AND organizer's `calendar_default_privacy == 'private'`)
- AND current user is not the organizer AND not in `partner_ids`

`_get_default_privacy_domain()` (lines 1080–1091): Domain that shows:
- Events with `privacy in ['public', 'confidential']`
- Events where `user_id == current_user`
- Events with `privacy=False` AND organizer's default privacy != private

### 5.2 Multi-company

No company-specific field on `calendar.event` in Community. Privacy is per-user via `res.users.settings.calendar_default_privacy`. No `company_id` field found on `calendar.event`.

## 6. Google Calendar Sync

**Not present in Community**. No `_get_events_from_google_internal_event_id()` method exists in the Community `calendar` addon. Google Calendar sync is an Enterprise/third-party module feature. The `calendar.event` model has several override hooks (`_get_update_future_events_values()`, `_get_remove_sync_id_values()`, `_check_values_to_sync()`) at lines 1414–1422 that return empty/False — these are extension points for sync modules.

## 8. Migration Flags Summary

1. **`alarm_type = 'sms'`** not present in v19 `calendar.alarm.alarm_type`. Only `notification` and `email`. Any v16/v17 data with SMS alarms must be remapped.
2. **`recurrent_id` field** (old column on `calendar.event`) is absent in v19. Replaced by `recurrence_id` (FK to `calendar.recurrence`) + `follow_recurrence` boolean.
3. **`do_confirm()` method** on `calendar.attendee` is absent in v19. Replaced by `do_accept()`.
4. **`calendar.alarm.type` field name**: in some older versions the field was named `type`; in v19 it is `alarm_type`.
5. **`recurrence_update` field**: Non-stored Selection on `calendar.event` (line 221); must not be stored in DB.
6. **Google Calendar sync fields** (`google_event_id`, etc.) are not on the Community model; they exist only in enterprise/third-party modules.
