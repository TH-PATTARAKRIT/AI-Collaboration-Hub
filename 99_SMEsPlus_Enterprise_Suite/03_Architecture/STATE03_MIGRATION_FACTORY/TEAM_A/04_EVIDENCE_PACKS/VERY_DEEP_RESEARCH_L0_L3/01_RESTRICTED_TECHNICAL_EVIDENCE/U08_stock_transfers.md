## CAP-U08-01 Warehouse and routing configuration

**Function-ID(s):** GRV-F01 (receipt routing 1/2/3-step) and SDV-F01 (delivery routing 1/2/3-step) — both genuine matches; route-resolution/push-pull claims are tagged with both IDs because the same engine serves both flows.

### D1 — Business purpose & process semantics
A warehouse owns a location tree (view location with Stock, Input, Quality Control, Output and Packing sub-locations), eight operation types (Receipts, Delivery Orders, Pick, Pack, Quality Control, Storage, Internal Transfers, Cross Dock) and two generated routes (reception and delivery). The `reception_steps` / `delivery_steps` selections C001 C002 decide which of those objects are active and which rules link them. The business meaning: the same transfer document is reused for every handling stage; steps are inserted by configuration, not by custom documents. Needs (a sale, a reordering rule, a manufacturing need) are resolved into moves by walking rules C024; goods arrival can fire further legs by push rules C029.

### D2 — Architecture / data / object relationships
- `stock.warehouse` → `view_location_id`, `lot_stock_id`, `wh_input_stock_loc_id`, `wh_qc_stock_loc_id`, `wh_output_stock_loc_id`, `wh_pack_stock_loc_id`; picking types `in_type_id`, `out_type_id`, `pick_type_id`, `pack_type_id`, `qc_type_id`, `store_type_id`, `int_type_id`, `xdock_type_id`; routes `reception_route_id`, `delivery_route_id`, `route_ids` (m2m warehouse routes), `resupply_route_ids`; `mto_pull_id` rule C018.
- `stock.route` (company optional, selectable flags) 1—n `stock.rule` (action, locations, picking type, procure_method, delay, propagate_* flags, push_domain) C045 C049.
- Product/category/packaging/carrier/orderpoint/move can each carry `route_ids`; the moves carry `warehouse_id` and `rule_id`.
- Locations carry `warehouse_id` (computed from the view-location ancestor) so rule lookup can be warehouse-scoped.

### D3 — Source / technical / workflow logic
Flow of a pull need: `stock.rule.run(procurements)` → `_get_rule(product, location, values)` (location ancestor chain, route precedence, warehouse preference) → grouped by action → `_run_pull` → `stock.move.create` as superuser → `_action_confirm` C038 C040 C035.
Flow of a push: at `stock.move._action_done` the done moves go through `_push_apply` → `_get_push_rule` (+ `push_domain` exclusion loop) → `rule._run_push` (transparent = rewrite destination; manual = copy move waiting on the first) C030 C031 C033.
Change of steps: `warehouse.write` → `_update_location_reception/_delivery` → picking-type update values → `_create_or_update_route` (archive then re-activate/create rules) → `_create_or_update_global_routes_rules` (MTO rule) C019 C013 C014.
Generated routing per step (Routing = from, to, picking type, action):
- `one_step`: Vendors -> Stock (pull, IN) C003
- `two_steps`: Vendors -> Stock (pull, IN); Input -> Stock (push, STOR) C004
- `three_steps`: Vendors -> Stock (pull); Input -> Quality (push, QC); Quality -> Stock (push, STOR) C005
- `ship_only`: Stock -> Customers (pull, OUT) C006
- `pick_ship`: Stock -> Customers (pull, PICK); Output -> Customers (push, OUT) C007
- `pick_pack_ship`: Stock -> Customers (pull, PICK); Packing -> Output (push, PACK); Output -> Customers (push, OUT) C008
Supply methods: first rule make_to_stock, later rules make_to_order C009.

**Configuration state list (warehouse):**
- `active -> archived [write(active=False): only if no open moves and no foreign picking type uses its locations]` C048
- `archived -> active [write(active=True): re-writes depends fields so rules/locations/types are re-activated per steps]`

## CAP-U08-02 Transfer (picking) and movement state machine

**Function-ID(s):** FUNCTION MAPPING REQUIRED (no existing ID covers the generic state machine; GRV-F02/SDV-F02 cover validation only, see CAP-U08-04).

### D1 — Business purpose & process semantics
A transfer ("picking") is the header of one logistics operation (receipt, delivery, internal move, pick, pack, ...). The header status is never edited: it is computed from its moves C059 so that a user sees whether goods can be processed (Ready), are missing (Waiting), wait for another document (Waiting Another Operation), or are finished (Done/Cancelled) C056. The shipping policy of the operation type (`direct` as soon as possible / `one` when all products are ready) decides how partial availability maps to the header C070 C071.

### D2 — Architecture / data / object relationships
`stock.picking` 1—n `stock.move` (`picking_id`) 1—n `stock.move.line` (`move_id`, `picking_id`); moves are chained by `move_orig_ids`/`move_dest_ids` (many2many `stock_move_move_rel`); `stock.picking.type` gives sequence, defaults, reservation method, backorder policy, shipping policy; `stock.reference` (many2many `reference_ids`) groups moves of one origin and replaces the procurement group C076; `stock.picking.batch` groups pickings (`batch_id`) when stock_picking_batch is installed C095.

### D3 — Source / technical / workflow logic
Move state transitions (base `stock` + overrides noted):
- `draft -> confirmed [stock.move._action_confirm, no predecessor, MTS]` C076 C072
- `draft -> waiting [_action_confirm: move_orig_ids present or procure_method make_to_order]` C073 C074
- `draft -> confirmed (+ procurement) [rule.procure_method = mts_else_mto]` C075
- `confirmed|waiting|partially_available -> assigned [_action_assign reserved >= demand]` C082
- `confirmed|waiting -> partially_available [_action_assign reserved < demand]` C082
- `assigned|partially_available -> confirmed|waiting [_do_unreserve -> _recompute_state]` C084
- `assigned -> partially_available [demand raised on an open move: stock.move.write(product_uom_qty) at stock_move.py:864]`
- `open -> done [_action_done]` C092
- `open -> cancel [_action_cancel]` C094; `done -> cancel` is refused except for moves into an inventory-usage location (CAP-U08-06).
Picking state derivation:
- `no moves or any draft move -> draft` C061
- `all moves cancel -> cancel` C062
- `all moves cancel/done -> done (or cancel in the scrap special case)` C063
- `bypass-reservation source and all MTS -> assigned` C065
- `else -> relevant move state; partially_available -> assigned` C066 C067
Batch state: `draft -> in_progress [action_confirm]`; `-> cancel` / `-> done` computed C095 C096 (CAP-U08-09).

## CAP-U08-03 Reservation and availability

**Function-ID(s):** FUNCTION MAPPING REQUIRED (no existing ID; closest are GRV-F02/SDV-F02 which cover execution, not reservation).

### D1 — Business purpose & process semantics
Reservation binds stock to a move so it cannot be promised twice and so a picker is told the exact location/lot/package C165 C127. The timing is a per-operation-type policy C107; the shipping policy of the transfer decides whether partial reservation makes the header Ready C160. Bypass locations (vendor, customer, inventory loss, production) never touch stock levels C116.

### D2 — Architecture / data / object relationships

Removal strategy: `product.removal` (name, method) referenced from `stock.location.removal_strategy_id` and `product.category.removal_strategy_id` C136 C135. Hand-off to U09: this unit stops at the call of `stock.quant._get_reserve_quantity` / `_update_reserved_quantity`; quant creation, `reserved_quantity` bookkeeping and `in_date` are U09.

### D3 — Source / technical / workflow logic
Algorithm `stock.move._action_assign(force_qty=False)` (stock_move.py:2050):
1. Filter moves: not picked and state in confirmed/waiting/partially_available C113.
2. For each move compute missing quantity C114; if zero, mark assigned.
3. If bypass reservation -> create lines without quants C117; mark assigned; schedule putaway.
4. Else if no `move_orig_ids`: skip MTO moves C119; otherwise reserve from quants with `strict=False` C120; assigned vs partially_available.
5. Else (chained): compute availability from predecessor done lines minus siblings C121 C122 C123 C124 and reserve with `strict=True`.
6. Write states C161; check entire packs; apply putaway strategy to new lines.
Removal strategy resolution C129 C130 and ordering C131 C132 C133 C134 (+ FEFO when product_expiry is installed C138).
Triggers: confirm C110; done of an incoming/internal picking C146 C143; scheduler C147 C148; manual button `action_assign`.
Unreserve: C149 C150. Forced quantity at validation: C152 C153 C154.

**State list (move, reservation view):**

- `confirmed|partially_available -> assigned [_action_assign, full quantity]`

## CAP-U08-05 Returns and reverse transfers

## CAP-U08-06 Cancellation, unreserve, edit restrictions after done, and date/lead-time propagation

**Function-ID(s):** FUNCTION MAPPING REQUIRED (no existing ID; the cancel/return family is adjacent to GRV-F07/SDV-F06 but not identical).

### D1 — Business purpose & process semantics
