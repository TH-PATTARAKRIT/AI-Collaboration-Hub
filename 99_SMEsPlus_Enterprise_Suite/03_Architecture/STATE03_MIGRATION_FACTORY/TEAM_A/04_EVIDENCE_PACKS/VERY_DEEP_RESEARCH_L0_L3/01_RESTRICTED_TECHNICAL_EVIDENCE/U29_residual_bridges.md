## CAP-U29-01 Sales margin on bundled (kit) products - cost bridge

**Modules in scope:** `sale_mrp_margin`

**Function-ID(s):** FUNCTION MAPPING REQUIRED

**Claims:** VDR-U29-C001 to VDR-U29-C048

### D1 Business purpose and process semantics
Business purpose: show, on every sales order line and on the order total, a margin that reflects the true cost of what was delivered, including for products sold as a bundle (a kit sold as one line but delivered as several component items, no manufacturing order). Process semantics: the module `sale_mrp_margin` is a marker bridge whose manifest says it handles BoM prices to compute sale margin, but it contains no model, view, security or data file; the behavior is carried entirely by base and bridge modules that are present when it is installed (`sale_margin`, `sale_stock_margin`, `sale_mrp`, `mrp_account`, `stock_account`). Effective behavior is therefore stated as base + overrides in those modules; the bridge itself adds nothing at runtime (INFERENCE from the file inventory).

### D2 Architecture, data and object relationships
Objects: `sale.order.line` (`purchase_price` = Cost, `margin`, `margin_percent`, stored, group `base.group_user`) and `sale.order` (`margin`, `margin_percent`, stored) from `sale_margin`; `stock.move` valuation hooks (`_get_price_unit`, `_get_price_unit_dropshipped`, `_get_price_unit_delivery`, `_get_cogs_price_unit`, `_get_kit_price_unit`); `mrp.bom` (type phantom = kit) explosion; `account.move.line` COGS value (`_get_cogs_value`). Relationships: sale line -> stock moves (`move_ids`, `sale_line_id`); stock move -> BoM line (`bom_line_id`) for kit components; product category cost method decides which branch applies.

### D3 Source, technical and workflow logic
Control flow: (1) at line creation/change `sale_margin._compute_purchase_price` sets cost = product standard cost converted to line UoM and order currency; (2) when stock moves exist and the category cost method is not standard, `sale_stock_margin._compute_purchase_price` replaces the cost by a quantity-weighted blend of delivered cost (`_get_price_unit_delivery` on done moves) and standard cost for the not-yet-delivered quantity; (3) for kit lines the delivered cost comes from `sale_mrp` `StockMove._get_price_unit` -> `_get_kit_value_per_unit` -> `mrp_account` `_get_kit_price_unit` (explode BoM, component price x qty per kit / kit BoM quantity, dropshipped components use the dropship price); (4) on invoice posting the COGS unit amount for a kit line is the sum of storable component COGS prices x component qty / BoM quantity (`sale_mrp` `_get_cogs_price_unit`), reached from `stock_account` `account.move.line._get_cogs_value`. Triggers: `@api.depends('move_ids','move_ids.value','move_ids.picking_id.state')` on the cost recomputation.

State diagram:
- cost source: standard cost [no valued stock move: moves absent, draft or cancelled]
- standard cost -> delivered-weighted cost [valued move exists AND category cost method != standard]
- standard cost -> unchanged [valued move exists AND category cost method == standard; existing value is kept]
- delivered-weighted cost -> recomputed [move value or delivery state changes]

## CAP-U29-02 Expiry-aware stock forecast on sales order lines

**Modules in scope:** `sale_stock_product_expiry`

**Function-ID(s):** FUNCTION MAPPING REQUIRED

**Claims:** VDR-U29-C049 to VDR-U29-C074

### D1 Business purpose and process semantics
Business purpose: when a salesperson looks at the availability popover of a sales order line, products that expire must be shown as 'fresh' stock - stock that will still be sellable at the promised delivery date - rather than raw quantities that include lots about to be removed. Process semantics: the module changes only the information shown on an order line (forecast quantities and labels); it does not change reservation, removal strategy, lot selection or any stock movement. Those belong to `product_expiry` and `stock` (U08, U09).

### D2 Architecture, data and object relationships
Objects: `sale.order.line` (adds non-stored related `use_expiration_date` from the product) with the base forecast fields of `sale_stock` (`qty_available_today`, `free_qty_today`, `virtual_available_at_date`, `scheduled_date`, `forecast_expected_date`); `product.product` quantity computation `_compute_quantities_dict` (context keys `to_date`, `warehouse_id`, `with_expiration`, `fresh_qty_forecast`); `stock.quant.removal_date`. Client side: the order-line widget `qty_at_date_widget` and its popover component.

### D3 Source, technical and workflow logic
Control flow: `sale_stock` `_compute_qty_at_date` groups lines by (warehouse, scheduled date) and calls `_read_qties(date, wh)` which reads `qty_available`, `free_qty`, `virtual_available` of the products with context `to_date=date`, `warehouse_id=wh`. The module wraps `_read_qties`: it sets context `fresh_qty_forecast=True` for the super call; `product_expiry` sets `with_expiration=today` inside the quantity computation, and `stock` then uses `max_date = to_date` (when `fresh_qty_forecast` and `to_date` are set) else today to subtract expired unreserved quantity (`removal_date <= max_date`) from `free_qty` and `virtual_available`. Afterwards, if ANY line in the batch has an expiring product, `free_qty` of every product in the batch is overwritten with a fresh read under only the warehouse context (no `to_date`), i.e. 'fresh free quantity as of today'. The JS patch renames the popover labels to 'Fresh Forecasted Stock' and 'Fresh Available' and adds a 'Today' caption when the line's product uses expiration dates.

State diagram:
- no state machine: the forecast is a computed display value per line.
- popover label: standard labels -> fresh labels [line product has expiration tracking enabled]

|---|---|
| 1 Happy path | Salesperson opens an order line of an expiry-tracked storable product in draft/sent/sale: the popover shows 'Fresh Forecasted Stock' (forecast at the scheduled date minus quantities whose removal date is on or before that date) and 'Fresh Available' with a 'Today' caption (free quantity today, expired excluded). |
| 2 Reversal / negative path | NOT APPLICABLE - read-only informational computation; no document state is changed. |
| 3 Multi-company / data-scope | Quantities are read with the line's warehouse context; company scoping follows `stock.quant` multi-company rule (DB: rule 'stock_quant multi-company'). No company logic in the bridge. |
| 4 Side effects / cross-module | None beyond display. Relies on `product_expiry` quantity override and `stock` expiry subtraction; all lines in a batch share the free-quantity re-read (see D3). |
| 5 Configuration & optionality | Auto-installed when `sale_stock` and `product_expiry` are present; per-product activation via the 'use expiration date' product flag; the widget only appears for storable lines with quantity to deliver in draft/sent/sale. |
| 6 Validation & constraints | NOT APPLICABLE - no constraint or validation. |
| 7 Roles & permissions | No ACL, rule or group is declared (DB: 0 ACL, 0 rules from this module). Reading product quantities follows the user's stock/product access; the value is computed in the order-line compute (not sudo in this module). |
| 8 Scheduled / automated behavior | NOT APPLICABLE - no cron; recalculated on dependency changes of the base compute. |
| 9 Exception & failure behavior | If no line of the batch has expiring products the free-quantity re-read is skipped. The zip pairing of re-read results with super results assumes both iterate the same product recordset order (INFERENCE) - RT. |

## CAP-U29-03 Transport dispatch on batch transfers (vehicle, driver, dock, capacity)

**Modules in scope:** `stock_fleet`

**Function-ID(s):** FUNCTION MAPPING REQUIRED

**Claims:** VDR-U29-C075 to VDR-U29-C120

### D1 Business purpose and process semantics
Business purpose: let a warehouse organise outbound (and inbound) transfers into dispatch batches assigned to a vehicle or a third-party carrier, a driver and a dock location, see how full the vehicle is by weight and volume, and print the stop order (sequence by postal code). Process semantics: dispatch features are switched on per operation type ('Dispatch Management'); for those types the batch screen shows dock, vehicle, vehicle category and capacity bars, the operation overview offers transport views (list, dock gantt, route kanban, calendar, statistics), and putting transfers into a batch with a dock redirects the moves of those transfers to or from the dock location. Batch creation, auto-batching, validation and state changes remain in `stock_picking_batch` (U08/U22).

### D2 Architecture, data and object relationships
Objects: `stock.picking.type` (+`dispatch_management`, +`dock_ids` many2many to `stock.location`), `stock.picking` (+related `zip`, uses `batch_id`, `batch_sequence`), `stock.picking.batch` (+`vehicle_id` -> `fleet.vehicle`, `vehicle_category_id` -> `fleet.vehicle.model.category`, `dock_id`, `driver_id` -> `res.partner`, `end_date`, capacity percentages, related capacity fields), `fleet.vehicle.model.category` (+`weight_capacity`, +`volume_capacity`), `stock.warehouse` (picking-type update values), `stock.location` (view tweak). Reused base fields: `estimated_shipping_weight`, `estimated_shipping_volume` (batch), `shipping_weight`, `shipping_volume` (picking).

### D3 Source, technical and workflow logic
Control flow: (1) install hook `_enable_dispatch_management` sets the flag on in/out types always and on pack (3-step) or pick (2-step) types per warehouse delivery steps; later warehouse reconfiguration goes through `StockWarehouse._get_picking_type_update_values` which re-applies the flag and links the output location as dock of the out type for multi-step delivery. (2) Batch create -> `order_on_zip` (batch_sequence = position in zip-sorted pickings; empty zip sorts first) then, for batches that have a dock, `_set_moves_destination_to_dock`. (3) Batch write with `dock_id` -> same method. (4) Picking write with `batch_id` -> dock method when the batch has a dock, otherwise `_reset_location`. (5) `_set_moves_destination_to_dock`: no dock -> reset moves to the picking location; picking type code internal/incoming -> `move.location_dest_id = dock`; else -> `move.location_id = dock`. (6) Computes: vehicle -> category and driver; dock auto-selected when all pickings share one source location that is an allowed dock; category weight/volume capacity -> percentages; `end_date` = scheduled date + 1h when empty or before it. (7) merged batches keep vehicle and dock.

State diagram:
- picking type: dispatch off -> dispatch on [flag ticked, or install hook, or warehouse (re)configuration]
- batch dock: none -> set [user selects, or auto when all pickings share one dock-eligible source] -> cleared [picking type changes]
- move location: original -> dock [batch with dock; destination for internal/incoming, source for other types] -> original [dock cleared or picking removed from batch]
(batch life cycle draft/in progress/done/cancelled is in `stock_picking_batch`, unchanged here)

## CAP-U29-04 Visitor and event-attendee SMS contact bridges

**Modules in scope:** `website_sms`, `website_crm_sms`, `mass_mailing_event_sms`

**Function-ID(s):** FUNCTION MAPPING REQUIRED

**Claims:** VDR-U29-C121 to VDR-U29-C156

### D1 Business purpose and process semantics
Business purpose: let staff text a website visitor directly from the visitor screen when a mobile number is known (from the visitor's contact, or from a CRM lead when no contact exists), and let event organisers choose between email and SMS when mass-mailing event attendees or inviting contacts. Process semantics: `website_sms` adds an 'Send SMS' action to the visitor form, kanban card and list; `website_crm_sms` extends the eligibility and addressee to CRM leads; `mass_mailing_event_sms` swaps the mass-mailing form opened from an event for the one that lets the user pick mail or SMS. Sending itself is done by the SMS composer of `sms` (credits, gateway), outside this unit.
