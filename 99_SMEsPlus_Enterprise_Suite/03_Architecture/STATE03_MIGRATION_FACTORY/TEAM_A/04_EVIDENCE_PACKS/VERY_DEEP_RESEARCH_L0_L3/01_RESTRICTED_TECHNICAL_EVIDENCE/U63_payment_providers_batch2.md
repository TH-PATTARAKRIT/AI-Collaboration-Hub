## CAP-U63-01 Payment provider webhook architecture pattern

### D1 — Redirect-to-provider flow
All 16 providers follow a redirect flow: the transaction record creates a token or order on the provider API, the customer is redirected to the provider's hosted payment page, and on return the system processes the outcome via a GET or POST HTTP route registered with `@http.route`.

### D2 — Webhook / IPN channel
All 16 providers define a separate webhook/IPN route decorated with `csrf=False`. The webhook routes are POST-only and acknowledge with an empty string, 'OK', or a JSON empty response. CSRF exemption is required because these routes receive cross-origin server-to-server calls. All webhook handlers are flagged C1 in the claims table.

### D3 — Signature verification gate
Every provider that delivers server-to-server notifications performs signature verification before calling `_process()`. The verification pattern is: retrieve the received signature from the payload or a header; compute the expected signature using the provider's stored secret; compare with `hmac.compare_digest` or `consteq`; raise `werkzeug.exceptions.Forbidden` on mismatch.

### D4 — _process() choke point
After signature verification, all providers call `tx_sudo._process(provider_code, data)` on the sudoed transaction record. This is the single choke point defined in the base `payment` module that dispatches to `_apply_updates()`.

### D5 — State machine transitions
All providers map provider-specific status codes or strings to five Odoo transaction states via `_set_pending()`, `_set_authorized()`, `_set_done()`, `_set_canceled()`, `_set_error()`. The mapping is defined in `const.py` as `PAYMENT_STATUS_MAPPING`.

### D6 — Credential field access control
All providers protect secret credentials with `groups='base.group_system'`, restricting read access to the Administrator group. Public keys and merchant codes use default access.

### D7 — Tokenization support
Flutterwave, Mercado Pago, Razorpay, Stripe, and Xendit declare `support_tokenization = True` in `_compute_feature_support_fields`. DPO, ECPay, Iyzico, Mollie, Nuvei, Paymob, PayPal, PayU, Redsys, Toss Payments, and Worldline do not.

### D8 — Refund support
Razorpay (`support_refund='partial'`), Stripe (`support_refund='partial'`), and Worldline declare refund support. The others do not.

### D9 — Manual capture support
Razorpay (`support_manual_capture='full_only'`), Stripe (`support_manual_capture='full_only'`), and Worldline declare manual capture support.

### D10 — Proxy URL pattern
Stripe uses an Odoo-hosted proxy URL (`https://stripe.api.odoo.com/api/stripe/`) for some API calls. Mercado Pago uses a proxy URL (`https://mercadopago.api.odoo.com/api/mercado_pago`). This indirection allows Odoo to manage API versioning centrally.

| Dimension | Finding |
|---|---|
| 1. Provider credential fields | All 16 providers add `fields.Char` credentials; secrets use `groups='base.group_system'` |
| 2. API base URL | Each provider overrides `_build_request_url`; prod vs test URL selected from `self.state` |
| 3. Signature algorithm | SHA-256 HMAC (Flutterwave, Redsys, Worldline, Nuvei, Razorpay), SHA-512 HMAC (Paymob), 3DES+HMAC-SHA256 (Redsys key derivation), plain token compare (Toss, Xendit), API re-fetch (Mollie, DPO, Mercado Pago) |

| 6. Reference extraction | All providers override `_extract_reference`; key field varies: CompanyRef (DPO), MerchantTradeNo (ECPay), tx_ref (Flutterwave), merchant_order_id (Iyzico), external_reference (Mercado Pago), id (Mollie/Worldline), productId (Nuvei), orderId (Toss), orderId (Toss) |

| 8. Refund / capture | Stripe, Razorpay, Worldline have refund; Stripe, Razorpay, Worldline have manual capture |
| 9. Single-currency providers | ECPay (TWD only), Toss Payments (KRW only) enforce currency constraints at both DB and API layer |
| 10. Proxy pattern | Stripe and Mercado Pago route through Odoo-hosted proxy URLs |
