## CAP-U07-01 Receipt creation from a purchase order

**Function-ID(s):** GRV-F01 (receipt routing configuration), GRV-F02 (physical receipt execution - creation side only; validation engine is U08)

**Claims:** VDR-U07-C001 to VDR-U07-C066

### D1 Business purpose and process semantics
Business purpose: when a purchase order for goods is approved, the system must give the warehouse a receipt document with one planned move per goods line, linked to the order line, so that arrivals are executed against the order and tracked back to it. Process semantics: creation is bound to approval (state `purchase`), not to the buyer's `button_confirm`; orders waiting in `to approve` have no receipt (`purchase_stock/models/purchase_order.py:179-182`, `:379`; base `purchase/models/purchase_order.py:625-639`). Re-planning after approval is line-driven: adding/increasing a line adds moves to the open receipt or creates a new receipt when none is open and ordered > received (`purchase_stock/models/purchase_order_line.py:94-99,117-119,169-199`); decreasing produces a negative move that the transfer engine merges into an open move or turns into a planned return (`purchase_order_line.py:221-236`; `stock/models/stock_move.py:1377-1383,1746-1772`) with an activity warning (`purchase_order.py:94-107,298-325`). Prior IDs GRV-F01 (routing) and GRV-F02 (execution) map to the steps: route/steps are warehouse configuration, execution is the engine's validation (hand-off U08).

### D2 Architecture, data and object relationships
Objects and relations: `purchase.order` (picking_type_id required, picking_ids stored computed from `order_line.move_ids.picking_id`, reference_ids M2M `stock.reference`, receipt_status, effective_date, is_shipped, dest_address_id) -> `purchase.order.line` (move_ids One2many `stock.move.purchase_line_id`, move_dest_ids M2M downstream, orderpoint_id, location_final_id, propagate_cancel, qty_received_method) -> `stock.move` (purchase_line_id, created_purchase_line_ids) -> `stock.picking` (purchase_id related). `stock.reference` replaces the earlier procurement group in this revision (no `procurement.group` model is referenced by purchase_stock): the order's references are copied to picking and moves (`purchase_order.py:354-375`, `purchase_order_line.py:307`). Warehouse/route/rule: `stock.warehouse.buy_pull_id` + `reception_route_id` with push-only follow-on rules (`purchase_stock/models/stock.py:77-109`; `stock/models/stock_warehouse.py:793-807`). Picking type: `stock.picking.type` code incoming (or dropship) resolved by `_get_picking_type` (`purchase_order.py:345-352`).

### D3 Source, technical and workflow logic
Control flow: `button_confirm` (base) -> `_approval_allowed()` ? `button_approve` : state `to approve`; `button_approve` (purchase_stock override) = base approve + `_create_picking()`. `_create_picking` (for approved orders with a consu line): reuse open picking else `StockPicking.with_user(SUPERUSER_ID).create(_prepare_picking())` -> `order_line._create_stock_moves(picking)` -> `_action_confirm` -> sequence by date (step 5) -> `_action_assign` -> confirm following pickings of push rules -> drop empty new picking -> chatter origin note (`purchase_order.py:377-412`). `_prepare_stock_moves` splits quantity between moves attached to downstream demand and an extra free move (`purchase_order_line.py:206-237`); `_prepare_stock_move_vals` builds the move (date, price, locations, references, warehouse) after the orderpoint warehouse check (`:283-314`). Price derivation `_get_stock_move_price_unit` (`:239-262`). Inheritance chain for `button_approve`/`_create_picking`: purchase -> purchase_stock -> stock_dropshipping (`_create_picking` override for multi-sale-order dropship, `stock_dropshipping/models/purchase.py:43-77`). State diagram (order/receipt coupling):
- `draft -> sent` [print/send RFQ, base]
- `draft/sent -> to approve` [button_confirm when approval not allowed, base]
- `draft/sent -> purchase` [button_confirm when allowed, or button_approve by manager; purchase_stock then creates the receipt]
- `to approve -> purchase` [button_approve; receipt created now]
- `purchase -> purchase (receipt draft->confirmed/assigned)` [_create_picking]
- `purchase -> purchase (receipt extra move / new receipt)` [line added or quantity increased, line write/create]
- `purchase -> cancel` [button_cancel: open moves/pickings cancelled, done receipts kept with note]
- receipt_status: `False -> pending` [receipt exists] ; `pending -> partial` [any receipt done, not all finished] ; `partial/pending -> full` [all receipts done or cancelled] ; `* -> False` [all receipts cancelled]

## CAP-U07-02 Received quantity and purchase line status

**Function-ID(s):** GRV-F03 (partial receipt / backorder), PDT-F02 (per-receipt billing alignment, purchase), PDT-F04 (cross-shipment quantity/bill reconciliation)

**Claims:** VDR-U07-C067 to VDR-U07-C111

### D1 Business purpose and process semantics
Business purpose: one authoritative figure of what has arrived per order line, feeding progress and (under the received-quantity policy) the billable quantity. Semantics: goods lines compute `qty_received` from done moves, services stay manual; returns subtract only when refunded; backorders keep the line link so quantities accumulate across receipts (`purchase_order_line.py:25-80`; `stock_move.py:104-110`). PDT-F02/PDT-F04: bills attach to order lines (`purchase_line_id`) and the system links receipts to bills only through the line, not receipt-to-bill (`purchase/models/account_invoice.py:528`; `purchase_stock/models/account_move_line.py:32-33`); cumulative reconciliation is `qty_invoiced` summed over bill lines (`purchase/models/purchase_order_line.py:197-207`) - no shared bill reference field is enforced by these modules.

### D2 Architecture, data and object relationships
`purchase.order.line.qty_received_method` ('manual' | 'stock_moves') + stored computed `qty_received` (depends on `move_ids.state/product_uom/quantity`), `qty_received_manual`, `qty_invoiced`, `qty_to_invoice` (base), `product.template.purchase_method` ('purchase' | 'receive'). Moves: `purchase_line_id`, `origin_returned_move_id` (stock), `to_refund` (stock_account). `stock.picking` backorder via `backorder_id`/`create_backorder` on picking type. Order level: `receipt_status`, `invoice_status` (base).

### D3 Source, technical and workflow logic
`_compute_qty_received_method`: base -> manual for consu/service; purchase_stock sets consu -> stock_moves. `_prepare_qty_received` (purchase_stock, line 55-80): for stock_moves lines, iterate `_get_po_line_moves()` (same-product moves), skip non-done; purchase return (`_is_purchase_return`) -> subtract if no origin or `to_refund`; dropship-returned-to-stock edge -> ignore; return-of-return without `to_refund` or non-supplier/transit source -> ignore; else add; convert with HALF-UP; post chatter note. purchase_mrp overrides for phantom-BoM kits (`purchase_mrp/models/purchase.py:63-81`). Backorder: `button_validate` -> `_pre_action_done_hook` (ask wizard when type `ask`) -> `_action_done` -> `_create_backorder` splitting moves (`stock_picking.py:1420-1450,1555-1568`; `stock_move.py:2310-2338`). Extra received products: `_action_synch_order` creates a zero-qty PO line (`stock_move.py:61-93`). State diagram (line received status, derived):
- `qty_received 0 -> partial` [done move qty < product_qty]
- `partial -> complete` [sum of done moves >= product_qty]
- `complete -> over-received` [done quantity > product_qty, no cap]
- `any -> lower` [done return with to_refund / no origin]
- order `receipt_status pending -> partial -> full` [picking states, not quantities]

| Dimension | Finding |

| 6 Validation & constraints | No cap on received vs ordered; read-only field for goods lines in the UI (`views/purchase_views.xml:63-66`); hard stops only in `_sanity_check` (empty/zero/lots). |

## CAP-U07-03 Bill-before-receipt, over-receipt and under-receipt situations

**Function-ID(s):** PDT-F03 (bill-before-receipt anomaly) - verified against source; related GRV-F03

**Claims:** VDR-U07-C112 to VDR-U07-C137

### D1 Business purpose and process semantics
Business purpose: understand what the system prevents, permits or only flags when billed, ordered and received quantities diverge. Verified result: in the examined Community modules there is no code that blocks creating or posting a vendor bill before receipt, nor receiving more than ordered; the product's bill-control policy only changes the suggested billable quantity (`purchase/models/purchase_order_line.py:178-184`), the bill auto-complete copies every not-yet-billed PO line (`purchase/models/account_invoice.py:63-65,628-647`), and there is no 3-way-match module in the Community tree (`purchase/views/res_config_settings_views.xml:42-43`). The prior PDT-F03 premise (documentation implying a receipt gate) is therefore not supported by source: CONTRA flagged in the claims table.

### D2 Architecture, data and object relationships
`product.template.purchase_method` -> `purchase.order.line.qty_to_invoice`/`qty_invoiced`/`qty_received` -> `account.move.line.purchase_line_id` -> `account.move`; receipts: `stock.picking`/`stock.move` quantity vs `product_uom_qty`; warnings: `mail.activity` on bill (`purchase_stock/models/purchase_order_line.py:173-180`) and on receipts (`purchase_order.py:298-325`).

### D3 Source, technical and workflow logic
Bill creation: `_onchange_purchase_auto_complete` -> `_add_purchase_order_lines` -> `_prepare_account_move_line` uses `qty_to_invoice` (`purchase/models/account_invoice.py:33-65,201-212`; `purchase_order_line.py:628-647`). `action_create_invoice` builds invoices without a quantity precondition (`purchase_order.py:760-833`). Over/under-receipt: `_check_backorder` tests `picked < demand` only (`stock_picking.py:1555-1568`); `_action_done` cancels or backorders short moves; no excess check. State diagram (bill vs receipt):
- `order purchase, qty_received 0 -> bill created (qty 0 lines)` [receive policy; not blocked]
- `order purchase -> bill created (ordered qty)` [purchase policy; by design]
- `receipt done < ordered -> backorder` [type ask/always] ; `-> remainder cancelled` [type never / cancel_backorder]
- `receipt done > ordered -> qty_received > product_qty` [no cap]
- `product_qty < qty_invoiced -> warning activity on bill` [purchase_stock line write]

### Ten-dimension table

| Dimension | Finding |
|---|---|
| 1 Happy path | Receipt validated for the ordered quantity; `qty_received` = ordered; under received policy `qty_to_invoice` = ordered; bill created with that quantity. |
| 2 Reversal/cancel/negative path | Order qty cut below billed -> activity suggesting refund (`purchase_order_line.py:173-180`); return with refund -> negative `qty_to_invoice` (CAP-U07-04). |
| 3 Multi-company / data-scope | Not specific; company rules of `purchase`/`stock` apply. |
| 4 Side effects & cross-module triggers | Bill post re-values receipts (`stock_account/models/account_move.py:42`; `purchase_stock/models/stock_move.py:157-215`); receipt validation acknowledges the PO. |
| 5 Configuration & optionality | Product `purchase_method`; picking type backorder policy; optional 3-way-match extension not in Community. |
| 6 Validation & constraints | No over/under-receipt tolerance, no bill-vs-receipt constraint; validation stops only for empty/zero/lot errors (`stock_picking.py:1373-1415`). |
| 7 Roles & permissions | Purchase users create bills through account ACLs from `purchase` (hand-off U06); stock users cannot edit orders. |
| 8 Scheduled/automated behaviour | None. |
| 9 Exception & failure behaviour | UserError only for sanity-check failures; nothing for excess or bill-before-receipt. |
| 10 Accounting, stock, audit, security & compliance | Payable can be recognised before goods arrive (purchase policy or zero-quantity bills); over-receipt with received policy inflates billable quantity; control must be procedural or via the optional extension. |

Config only: no module row matching `3way` in the restored DB; `purchase_method` default is evaluated in code (`purchase/models/product.py:22-29`); no orders/bills exist, so no runtime anomaly can be reproduced from DB.

## CAP-U07-04 Returns of received goods and refund hand-off

**Function-ID(s):** GRV-F07 (reversal / return of received goods)

**Claims:** VDR-U07-C138 to VDR-U07-C162

### D1 Business purpose and process semantics
Business purpose: send received goods back to the vendor while keeping the receipt and correcting the order's received quantity and the payable (via credit note). Semantics: the return is a new picking from the receipt destination to the vendor (or return type's destination), each return line has `to_refund` (default True) that decides whether the order's received quantity decreases (`stock/wizard/stock_picking_return.py:25-45,142-159`; `stock_account/wizard/stock_picking_return.py:10-16`; `purchase_stock/models/purchase_order_line.py:65-67`). The credit note is produced by billing (hand-off U06): negative `qty_to_invoice` leads to a bill with negative total that is switched to a refund (`purchase/models/purchase_order.py:816`).

### D2 Architecture, data and object relationships
`stock.return.picking(.line)` wizard -> `stock.picking` (return_id) -> `stock.move` (origin_returned_move_id, to_refund, purchase_line_id, partner_id) -> `purchase.order.line.qty_received` -> `qty_to_invoice` -> `account.move` (in_refund) lines (purchase_line_id). Chain walk `_get_purchase_line_and_partner_from_chain` links return moves to the PO line (`purchase_stock/models/stock_move.py:140-151`).

### D3 Source, technical and workflow logic
`stock.return.picking._create_return`: copy picking with return values -> `_process_line` copies moves with `origin_returned_move_id` -> confirm/assign (`stock_picking_return.py:161-187`); purchase_stock `_prepare_move_default_values` sets purchase_line and partner for supplier destinations (`stock.py:125-131`), `_create_return` aligns picking partner (`:134-138`). Qty effect: `_prepare_qty_received` (`purchase_order_line.py:55-80`). Exchange: `action_create_exchanges` (`stock_picking_return.py:239-249,189-208`). State diagram:
- `receipt done -> return draft` [return wizard]
- `return draft -> confirmed/assigned` [action_confirm, action_assign]
- `return assigned -> done` [validate by stock user]
- `qty_received N -> N - r` [done return, to_refund true or no origin]
- `qty_received unchanged` [done return, to_refund false]
- `qty_to_invoice -> negative` [received policy, returned after billing]
- `bill total < 0 -> in_refund` [action_create_invoice step 4]

### Ten-dimension table

| Dimension | Finding |
|---|---|
| 1 Happy path | Return full/part of receipt with refund option -> done return -> `qty_received` decreases -> credit note via billing. |
| 2 Reversal/cancel/negative path | Return of return, exchange (independent receipt), cancel PO with done receipts (note only). |
| 3 Multi-company / data-scope | Intercompany transit recognised by `_is_purchase_return` (`stock_move.py:129-135`); company rules of stock. |
| 4 Side effects & cross-module triggers | Updates `qty_received`, `qty_to_invoice`, `invoice_status`; valuation of the outgoing move (U10); chatter on PO for qty change; stock reservation of destination moves unreserved (`stock_picking_return.py:163-164`). |
| 5 Configuration & optionality | Return picking type on the receipt type; `to_refund` per line (default on); product type consu; stock_account installed for `to_refund`. |
| 6 Validation & constraints | At least one non-zero return line (`stock_picking_return.py:182-183`); return of qty beyond received is not blocked here (RT). |
| 7 Roles & permissions | Return wizard is stock-side; purchase user can create pickings/moves (`ir.model.access.csv:6-7`); credit note requires account/purchase bill rights. |
| 8 Scheduled/automated behaviour | None. |
| 9 Exception & failure behaviour | UserError when no line quantity; chain walk can return no line (`stock_move.py:151`) leaving `purchase_line_id` empty (RT). |
| 10 Accounting, stock, audit, security & compliance | Return is an outgoing valued move (`stock_account/models/stock_move.py:683-689`); credit note adjusts payable; with `to_refund` off the order and stock diverge (INFERENCE flagged). |

### DB reconciliation (restored DB, configuration only)
Config only: restored DB has `stock_move.to_refund` column and return picking types (outgoing 1); stock_account wizard field exists in source; no pickings in DB.

## CAP-U07-05 Valuation and price-difference behaviour attributable to purchase_stock

**Function-ID(s):** GRV-F04 (inventory valuation at receipt), GRV-F05 (landed cost allocation)

**Claims:** VDR-U07-C163 to VDR-U07-C208

### D1 Business purpose and process semantics
Business purpose: value received goods promptly at the order price, refine to the real vendor bill, and record price differences and landed costs. Semantics (Community 19, valuation reworked: no valuation layer table): each incoming move carries `price_unit` (from the line) and a stored `value` computed by `_get_value_data` with priority manual -> bill -> production -> quotation -> returns -> standard price, plus extra (landed costs) (`stock_account/models/stock_move.py:363-448`). purchase_stock supplies the bill and quotation hooks (`purchase_stock/models/stock_move.py:157-243`). Price-difference journal lines on bill posting exist only for standard-cost products under anglo-saxon accounting (`purchase_stock/models/account_invoice.py:12-117`). Landed costs apply only to FIFO/average (`stock_landed_costs/models/stock_landed_cost.py:161`). Flag-OFF DB: periodic valuation, standard cost, anglo-saxon off, no location valuation accounts.

### D2 Architecture, data and object relationships
`stock.move` (price_unit, value, is_in/is_out/is_dropship/is_valued, purchase_line_id), `account.move.line` (purchase_line_id, display_type 'cogs'), `product.category` (property_valuation, property_cost_method, property_price_difference_account_id), `res.company` (inventory_valuation, anglo_saxon_accounting, cost_method), `stock.location.valuation_account_id`, `stock.landed.cost` (+ adjustment lines). Bill value: `aml.price_subtotal / aml.currency_rate`.

### D3 Source, technical and workflow logic
Receipt: `_get_stock_move_price_unit` (discount, taxes `total_void`, UoM, currency conversion, rounding) -> move price_unit -> at `_action_done`: `moves_in._set_value()` -> `_create_account_move` only if `valuation == 'real_time'` and a location valuation account exists (`stock_account/models/stock_move.py:177-218,659-667`).
