## Key Architecture Observations

- Membership has two layers: an explicit stored list per user and a computed effective list that adds every implied group (U235-C01, U235-C02). Editing the effective list from the group side can add explicit memberships but refuses to remove a membership that is still implied (U235-C03).
- Users cannot change their own group membership through ordinary profile edits; the list of fields a user may edit on their own record leaves it out (U235-C04).
- Group implication is a directed graph stored as direct links between groups. Transitive closures in both directions are computed from set definitions built over all groups rather than stored (U235-C05, U235-C06). Settings-driven switches add or remove direct links (U235-C07).
- Classification of groups moved to a privilege record that links a module category to groups; a stale comment in the base group data file still mentions a category field on groups (U235-C08, U235-C09). The web group widget reads one structured hierarchy field (U235-C10), and the exclusive flag on module categories only affects module installation (U235-C11).
- User types are three disjoint groups for employee, portal and public users, and a user may hold at most one of them (U235-C12, U235-C13). The external flag follows the absence of the employee group (U235-C14).
- The administrator role group implies the access-rights group, which implies the employee group (U235-C15); the administrator test is broader than the full system role (U235-C24).
- Companies: each user has one default company and a set of allowed companies, a validation ties them together, and the multi-company group is toggled automatically from the number of allowed companies (U235-C16, U235-C17, U235-C18).
- Credentials: password verification returns an identity mapping (U235-C19), hashing is slow and upgradeable (U235-C20), and API keys are random, stored only as hashes and limited in lifetime by group settings (U235-C21, U235-C22).
- The superuser identifier always runs with elevated rights (U235-C23).
- Defaults: new users start from the employee group plus configurable default groups (U235-C25); portal sign-up copies a template user named by a system parameter (U235-C26).

## Unknowns and Runtime-Dependent Items

- The group-level API key duration values and the configured default-access groups of a live database cannot be known from static reading (U235-C22, U235-C25).
- Which template user is configured for portal sign-up in a given database cannot be determined from source (U235-C26).
- Extension modules may add further user type groups or further exclusive pairs; only the three base type groups were found (U235-C12).
- Login throttling state is held per worker process; its behaviour across several workers was not exercised.
- The effect of the rule that blocks elevated-rights relational commands on user and group models is unknown for specific scenarios.
- No restored database was consulted for this unit, and every comparison with earlier versions is inference from prior knowledge because earlier source is not present in the tree.
