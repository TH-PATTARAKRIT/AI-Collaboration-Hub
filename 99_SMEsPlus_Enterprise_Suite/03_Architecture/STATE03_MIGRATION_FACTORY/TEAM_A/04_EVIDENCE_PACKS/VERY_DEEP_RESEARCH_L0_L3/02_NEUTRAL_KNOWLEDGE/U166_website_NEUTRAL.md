| C02 | Each website record enforces a unique domain | website model | HIGH | YES | HIGH | MEDIUM | No two website records in the same database may share the same domain address. This uniqueness is enforced at the database level, meaning domain collision is a hard constraint that migration scripts must respect when cloning or restructuring multi-website setups. |
| C03 | A company must be assigned to every website | website model | HIGH | YES | HIGH | HIGH | Every website is linked to one company record. This creates a binding between published web content and the legal entity it represents. When migrating to a multi-company environment, website-to-company assignments must be reviewed and mapped explicitly. |
| C04 | A website can publish content in multiple languages | website model | HIGH | YES | MEDIUM | MEDIUM | The list of enabled languages on a website is independently configurable per website record. A language enabled on one website need not be enabled on another. Migration of translatable content must account for which languages are active per website, not just globally. |
| C05 | The active website is resolved from session, context, domain, or first fallback | website model | HIGH | YES | HIGH | HIGH | When an incoming web request arrives, the system determines which website record governs it by checking, in order: an administrator-forced session override, an explicit context value, the domain name in the request, and finally the first available website if no match is found. This resolution chain means domain configuration directly controls website selection in production. |
| C06 | Multiple websites per database require a configuration toggle | settings model | HIGH | YES | HIGH | LOW | The ability to manage multiple websites through the backend interface is protected by a settings group. When only one website exists, this group is inactive and the interface simplifies accordingly. Creating a second website automatically activates the group. This is a feature present in Community, not Enterprise-exclusive. |
| C07 | Each website maintains its own URL routing map | ir_http model | HIGH | YES | HIGH | HIGH | URL dispatching is keyed per website identifier so that two websites can have different URL-to-controller mappings at the same path. This means URL rewrite rules, redirect rules, and route availability can differ between websites in the same database. Migration must transfer rewrite tables website by website. |
| C08 | CMS pages are served through a dedicated lookup before controller fallback | ir_http model | HIGH | YES | MEDIUM | MEDIUM | When a request arrives for a path that has no controller route, the system first looks up the path in the catalogue of published website pages. If a matching page is found, its stored template is rendered and returned. If not, redirects are checked. This two-stage lookup is core to how static CMS pages work. |
| C09 | URL rewrite rules are applied per website during route generation | ir_http model | HIGH | YES | HIGH | HIGH | When generating the routing table for a website, the system reads that website's active rewrite rules and incorporates them. A 308 rewrite adds the new URL as a valid endpoint and marks the old URL as a redirect. A 404 rewrite suppresses a URL entirely. Each website has its own independent set of active rewrites. |
| C10 | A website page delegates its template storage to the view system | website.page model | HIGH | YES | LOW | LOW | The page record itself stores only navigation metadata such as URL, publish date, and visibility flags. The actual page template and content architecture is stored in a linked view record. This delegation means page content is subject to the same versioning and inheritance rules as all other QWeb views. |
| C11 | Pages have a URL and an indexing flag controlling search engine visibility | website.page model | HIGH | YES | LOW | LOW | Each published page has a required URL path and a boolean flag indicating whether the page should appear in search engine sitemaps. Pages with the indexing flag disabled are still served to visitors but excluded from the sitemap. |
| C12 | A page can be set to become visible only on or after a scheduled date | website.page model | HIGH | YES | LOW | LOW | In addition to the published flag, a page has an optional publish date field. If this date is set to a future time, the page will be served as unpublished until the date passes, even if the published flag is true. This enables scheduled content release without manual intervention. |
| C13 | A field on the SEO metadata allows overriding the URL slug | mixins model | HIGH | YES | LOW | LOW | Every record that participates in website publishing can carry a custom SEO name that replaces its database name in URL generation. When this field has a value, it is used to build the path segment rather than the record's standard display name. This allows human-readable URLs independent of internal record names. |
| C14 | Page title, description, and keywords are translatable per record | mixins model | HIGH | YES | LOW | LOW | The three standard search-engine metadata fields — title, description, and keywords — are stored on each record and support translation. This means different language visitors see translated metadata in search results. An optimisation flag is automatically derived when all three fields are populated. |
| C15 | The navigation menu is stored as a tree structure with group-based visibility | website.menu model | HIGH | YES | MEDIUM | MEDIUM | Navigation entries form a hierarchical tree. Each entry may restrict its visibility to specific user groups, allowing menu items to appear differently for logged-in users versus the public. The tree is stored using a path-based index enabling efficient subtree queries. |
| C16 | Mega menus store rich HTML content without automatic sanitisation | website.menu model | HIGH | YES | LOW | LOW | When a menu entry is configured as a mega menu, its dropdown content is an HTML block stored without server-side sanitisation. This content is designed to be authored by trusted designers. Migration of mega menu content must preserve raw HTML as-is. |
| C17 | Anonymous visitor identity is derived from connection characteristics, not cookies | website.visitor model | HIGH | YES | LOW | LOW | For users who are not logged in, the system creates a stable identifier by combining the visitor's network address, browser identification string, and session token into a cryptographic hash. This hash is consistent within a session but does not persist across different devices or browsers of the same person. |
| C18 | Visitor tracking fires only on successful, non-automated requests | ir_http model | HIGH | YES | LOW | LOW | Page visit records are only created when a request results in a normal successful response and the requesting client has not been identified as an automated crawler. Error responses, redirects, and bot traffic do not generate visitor tracking records. |
| C19 | Repeat visits to the same page within thirty minutes do not create duplicate tracking records | website.visitor model | HIGH | YES | LOW | LOW | The tracking system checks for a recent visit record to the same page before writing a new one. If the same visitor has already been recorded visiting the same page within the past thirty minutes, no additional record is written. This prevents page refreshes and navigation loops from inflating visit counts. |
| C20 | Whether a record appears published depends on which website is currently active | mixins model | HIGH | YES | HIGH | HIGH | A record with the published flag set to true is only shown as visible on the website that matches its assigned website scope. If a record is scoped to a specific website, it will not appear as published when viewed in the context of a different website, even though its published flag is true at the database level. This contextual nature of publication state is critical during multi-website migrations. |
| C21 | Social media channel links are stored per website, defaulting from the main company | website model | HIGH | YES | LOW | LOW | Each website record carries its own set of social media profile links. | C22 | A CDN can be configured per website with regex-based URL filters | website model | HIGH | YES | LOW | LOW | Each website has independent CDN settings including a base URL and a set of URL pattern filters.
