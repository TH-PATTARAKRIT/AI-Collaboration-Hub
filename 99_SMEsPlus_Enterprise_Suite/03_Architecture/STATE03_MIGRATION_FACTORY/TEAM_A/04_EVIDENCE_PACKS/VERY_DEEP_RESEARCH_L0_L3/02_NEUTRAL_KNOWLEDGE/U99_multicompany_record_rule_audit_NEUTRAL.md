# U99 Neutral Knowledge — Multi-Company Record Rule Audit
> NEUTRAL LAYER — no source paths, no class/method names, no file extensions, no snake_case, no backticks

| NR-ID | Statement |
|---|---|
| NR-U99-001 | The record rule model in Odoo 19 is configured to disallow sudo commands on rule records themselves, preventing privilege escalation through the rule management interface. |
| NR-U99-002 | The domain evaluation context for record rules injects three variables at evaluation time: the current user object, the list of currently active company identifiers, and the identifier of the primary active company. |
| NR-U99-003 | The list of active company identifiers injected into rule domain evaluation is derived from the environment's active company set, which is in turn sourced from a context key representing the user's active company selection. |
| NR-U99-004 | The cached domain computation for record rules includes the active company selection context key as part of its cache key; changing the active companies invalidates the cached domain and forces recomputation. |
| NR-U99-005 | When an environment operates in superuser mode, the rule retrieval step returns zero rules for any model and any access mode. This is an unconditional early exit — no rule of any kind, including company isolation rules, is applied under superuser mode. |
| NR-U99-006 | The single guard condition that implements the total superuser bypass of all record rules is a two-line early return: check superuser flag, return empty. This is the definitive mechanism for all record rule bypass in Odoo 19. |
| NR-U99-007 | The computed domain for record rules is cached separately for superuser and non-superuser environments (the superuser flag is included in the cache key), ensuring the superuser bypass does not pollute the domain cache used by regular users. |
| NR-U99-008 | The superuser elevation method on a recordset creates a new recordset bound to an environment with the superuser flag set to true. The official documentation for this method explicitly warns that it may cause data access to cross the boundaries of company isolation rules. |
| NR-U99-009 | The official documentation for the superuser elevation method states: using it could cause data access to cross the boundaries of record rules, possibly mixing records that are meant to be isolated, including records from different companies in multi-company environments. |
| NR-U99-010 | The environment property that returns the current company reads the active company list from the context key; in superuser mode it skips validation against the user's permitted company set, allowing access to any company's data. |
| NR-U99-011 | The validation that prevents a user from accessing an unauthorized company is guarded by a non-superuser check; in superuser mode this guard is never reached and any company identifier in context is accepted without verification. |
| NR-U99-012 | The environment property that returns the full set of active companies also skips unauthorized-company validation in superuser mode, applying the same bypass as the single-company property. |
| NR-U99-013 | When the active company context key is absent from the environment context, both the current company and current companies properties fall back to the user's own configured company set as retrieved from the user record directly. |
| NR-U99-014 | The partner record isolation rule uses a hierarchical company operator (parent-of) rather than a strict membership check, making partners visible to users of child companies within the company hierarchy; partners with no assigned company are universally visible. |
| NR-U99-015 | Bank account records and currency rate records follow the same hierarchical isolation pattern as partners: a parent-of operator allows child companies to see parent-company records, and null-company records are visible to all. |
| NR-U99-016 | Company records themselves are isolated using strict membership rules for portal, employee, and public users, but users with the ERP manager group have an unrestricted domain permitting visibility of all company records. |
| NR-U99-017 | Journal entries (accounting moves) are isolated using a strict membership domain: only records whose company field exactly matches one of the currently active company identifiers are visible. No hierarchical parent-of relaxation is applied to journal entries. |
| NR-U99-018 | Journal entry lines inherit the same strict membership isolation as their parent journal entries; the company field on the line must match an active company identifier exactly. |
| NR-U99-019 | Accounting journals use the hierarchical parent-of operator, making journals belonging to parent companies visible to users working in a child company — a deliberate relaxation to support multi-entity chart-of-accounts sharing. |
| NR-U99-020 | The chart-of-accounts record uses a many-to-many company relationship field (not a single company field); its isolation rule applies the parent-of operator to this multi-company field, supporting shared account structures across company hierarchies. |
| NR-U99-021 | Payment records use strict membership isolation identical to journal entries — only payments from currently active companies are visible, with no hierarchical relaxation. |
| NR-U99-022 | Several record types (bank statements, stock lots, stock locations, purchase-bill union views) use an extended membership domain that appends a null-company sentinel to the active company list, ensuring that records with no assigned company remain universally visible. |
| NR-U99-023 | Stock transfer (picking) records use strict membership isolation: only transfers belonging to a currently active company are visible; no null-company extension is applied to this rule. |
| NR-U99-024 | Lot and serial number records extend the company membership domain with a null-company sentinel, allowing lot records without a company assignment to be visible across all companies. |
| NR-U99-025 | Purchase orders use strict membership isolation: only orders belonging to a currently active company are visible to the current user session. |
| NR-U99-026 | The purchase-bills union analytical view uses the extended membership pattern including a null-company sentinel; this accommodates records in the view that may not carry a company assignment. |
| NR-U99-027 | Sales orders and sales order lines use the same strict company membership isolation pattern as purchase orders; the pattern is consistent across the three operational transaction models. |
| NR-U99-028 | An intercompany payment module is present in Odoo 19 Community under a lesser general public license; it enables automated reconciliation of invoices and payments belonging to different companies within the same database. |
| NR-U99-029 | The intercompany payment posting logic intentionally elevates to superuser mode before filtering moves eligible for intercompany clearing; this is a documented pattern of deliberate company isolation bypass for cross-company automation. |
| NR-U99-030 | Cross-company clearing journal entries are created using an explicit company context switch method in addition to superuser elevation; both the access-rights bypass (superuser) and the company context switch are required to create entries in a different company. |
| NR-U99-031 | Three configuration fields are added to the company record to support intercompany clearing: a clearing journal, a clearing payable account, and a clearing receivable account — all must be configured per company before intercompany reconciliation can activate. |
| NR-U99-032 | The core journal entry model contains at least one explicit superuser elevation assignment within its standard methods, indicating that certain accounting operations are deliberately designed to bypass company record rules for internal consistency. |
| NR-U99-033 | The inalterability hash-chaining feature for journal entries uses superuser elevation when searching and fetching entries to compute chain integrity; this bypass is required because hash computation must span all entries in a sequence regardless of the caller's active company selection. |
| NR-U99-034 | The superuser flag is stored as a boolean attribute on the environment object at construction time; it is immutable for any given environment instance and can only be changed by creating a new environment binding. |
| NR-U99-035 | When generating an access-denied error message, the record rule engine inspects whether any failing rule's domain contains a company field reference; if so, it appends a multi-company switch suggestion and, where possible, identifies the specific company the user needs to activate to access the record. |
