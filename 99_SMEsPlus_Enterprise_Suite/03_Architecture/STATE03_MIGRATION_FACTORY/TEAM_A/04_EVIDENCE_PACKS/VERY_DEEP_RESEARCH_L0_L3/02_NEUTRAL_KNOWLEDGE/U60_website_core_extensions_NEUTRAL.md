[N-U60-001] The website module extends the core view rendering system so that each view record can be associated with a specific website. When a designer edits a shared generic view while working in the context of a particular website, the system automatically creates a private copy for that website rather than modifying the shared original. This copy-on-write behaviour ensures that changes made on one website do not affect any other website that shares the same underlying template.

[N-U60-002] Each view record can carry a flag indicating whether visits to the page it represents should be recorded in the visitor tracking log. This allows operators to selectively enable detailed visitor history only on pages where that information has value.

[N-U60-003] Website views can have one of four visibility settings: fully public, visible only to signed-in users, restricted to a designated access group, or accessible only after entering a password. The password is stored in protected encrypted form and verified at the time a visitor requests the page. A website designer always sees all views regardless of their visibility setting.

[N-U60-004] When a generic view is deleted in the context of a particular website, the system first creates website-specific copies for every other website so those websites retain the view. This copy-on-unlink behaviour is a companion to copy-on-write. A special flag can be passed to bypass both mechanisms when the system itself needs to perform low-level view management without triggering copies.

[N-U60-005] An anonymous website visitor is identified by a short token derived from the visitor's network address, browser agent, and session identifier. A visitor who logs in is instead identified by their contact record. The token is stored in the visitor table with a uniqueness constraint. The visitor's detected timezone is stored separately and updated using a locking strategy that avoids conflicts when multiple requests arrive simultaneously.

[N-U60-006] The visitor record is created or updated atomically using a database upsert operation. A running count of visits is incremented only when a gap of more than eight hours has elapsed since the last recorded connection. Individual page visits are recorded in a separate tracking table that links the visitor to the page and the precise address visited. A short deduplication window of thirty minutes prevents the same visitor from generating duplicate track entries for the same page within a single browsing session.

[N-U60-007] When an anonymous visitor logs in, any tracking history accumulated during the anonymous session is transferred to the visitor record associated with their partner account, and the anonymous record is removed. Visitor records that have no associated partner and have not connected within a configurable number of days (defaulting to sixty) are periodically removed by a background job.

[N-U60-008] The website supports four types of URL rules for controlling how addresses are handled. A block rule causes a specific address to return a not-found response. Permanent and temporary redirect rules forward visitors to a different address, with the difference recorded in the response code so browsers can decide whether to cache the destination. A rewrite rule creates an alias so that both the old and new address reach the same content. Changes to block or rewrite rules immediately refresh the routing table used by the server to match incoming requests.

[N-U60-009] Website menus are stored in a hierarchy that supports at most two levels of nesting. A mega menu is a special leaf menu that displays a rich content panel rather than sub-links; it cannot be placed inside another menu or have children of its own. When a new menu entry is created without being tied to a specific website, the system automatically creates a matching entry on every active website. The system ensures that the website designer group is always included whenever access-restricted menu visibility is configured.

[N-U60-010] A public form submission controller accepts data for any record type that has been explicitly enabled for website form access. The controller validates field types and coerces values accordingly before creating a record. Custom fields that are not mapped to known model fields are collected into a single free-text note. Files attached through the form are saved as document attachments linked to the created record. An optional configuration flag causes the visitor's network address, browser, and language to be appended to the record for compliance or diagnostic purposes.

[N-U60-011] The blog system provides a channel for publishing articles. Each article belongs to a blog, and blogs can span multiple websites. Articles carry a publication date that controls when they become visible to the public; a designer can view drafts and future-dated posts that are hidden from regular visitors. When an article is published, a notification is sent to followers of the parent blog. Replies to those notifications are quietly demoted to internal notes to prevent follower inboxes being flooded. Each article has a computed summary that takes the first two hundred characters of the content text unless the author has supplied a custom teaser. Articles are tagged and include full open-graph social metadata including article type, publication time, modification time, and cover image. A running view counter records how many times the article has been opened.

[N-U60-012] Blog tags are grouped into categories and carry a usage-frequency count per blog that is computed through a database aggregation query with a configurable minimum threshold. This allows the website to surface only the most commonly used tags rather than every tag ever created.

[N-U60-013] When a visitor submits a contact or enquiry form that creates a sales lead, the system automatically links the visitor record to the newly created lead. The submission is pre-processed to normalise telephone numbers to international format using the visitor's detected country or the company's country as the reference. The geographic state detected from the visitor's network location is also written to the lead when the form did not supply one. A default sales team and salesperson can be configured per website to receive all leads submitted through that website's contact form. The marketing channel on the lead is set to a value representing the website when no channel was supplied in the form. Visitors who have at least one associated lead are permanently protected from the periodic cleanup that would otherwise remove old anonymous visitor records.

[N-U60-014] An IAP-powered company identification feature inspects the network addresses of anonymous visitors to determine whether they belong to known companies. Rules define which pages and which geographic regions should be monitored, with optional filtering by company size, industry, and employee role. When a monitored page is served to a public visitor, the visitor's address is noted against the matching rule, unless the visitor already has a sales lead on record. A background job periodically sends batches of at most twenty-five collected addresses to a cloud identification service. When the service recognises a company, a sales lead is created and the identifying information is attached as an internal note. Addresses for which the service finds no match within a configurable period are discarded. A cookie on the visitor's browser records which rules have already been triggered to avoid recording the same visit multiple times.

[N-U60-015] When the live chat module is active alongside the CRM module, each sales lead displays a count of live chat sessions held with its associated visitors. When a chatbot conversation results in a new lead, the lead is named after the visitor and the visitor is linked to the lead. When a chat operator uses the command that converts a conversation to a lead, the visitor is also linked to the lead and the visitor's detected country is copied to the lead if the lead does not already carry a country.

[N-U60-016] The partner assignment module allows certified partner companies to be found and assigned to sales leads based on geographic proximity. Each partner carries a numerical weight that influences how often they receive new leads when multiple partners match the same location. Partner assignment uses a progressive search that starts with a small geographic area and expands in stages up to the entire country, with a final fallback to the nearest partner by straight-line distance. Portal users who are associated with an assigned partner company can view, accept, and decline the leads sent to them, update contact details and expected outcomes, and submit new opportunities on behalf of their company. Leads and opportunities are accessible at dedicated portal addresses and support sorting and date-range filtering.

[N-U60-017] When a visitor has no linked partner but does have associated sales leads, the short message composer that would normally target the partner can instead target the lead whose phone number matches the visitor's recorded mobile number. The most relevant lead is selected by a confidence score.

[N-U60-018] The customer showcase allows published partner customers to be displayed on a public directory page. Customers must be marked as published and must have an assigned implementation partner to appear. The list can be filtered by industry, country, and custom tags. Each tag carries a colour designation drawn from a standard set of five Bootstrap style names and is itself published by default. A sitemap generator provides search engines with addresses for each industry and country combination. The directory is paginated at twenty results per page and can display a map overlay when a Google Maps key is configured.
