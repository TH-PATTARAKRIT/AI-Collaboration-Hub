[N-U53-001] A thin bridge module links the conversational assistant feature to the human resources area. It activates itself automatically whenever both the messaging assistant and the human resources modules are installed at the same time. Its sole purpose is to extend the user profile screen with assistant-related status information from the human resources perspective. It contributes no business logic of its own.

[N-U53-002] A mail plugin module allows users of external email clients such as Outlook and Gmail to connect their mailboxes to the business database. It depends on the contacts module, the web layer, and the in-app purchase service. It enables looking up contact information, logging email messages against records, and creating new contacts without leaving the email client interface.

[N-U53-003] The authentication flow for the email plugin uses a two-step exchange. First, an internal user authorises the plugin through a browser confirmation page, which produces a short-lived temporary code valid for three minutes. The plugin then exchanges this temporary code for a persistent access token stored as an API key. The token lifetime is thirty days by default and can be adjusted through a system parameter. Only users classified as internal employees can initiate this flow. Each authenticated request carries the token in a standard authorisation header, which the server validates against the stored key.

[N-U53-004] Once authenticated, the email plugin can look up contacts by email address, name, or internal reference. If the contact is not found, the system automatically attempts to enrich and create a matching company record using an external data enrichment service. Public email provider domains such as those used by personal webmail are excluded from enrichment. The enrichment service returns structured company information including address, phone, website, and logo. If the service cannot find data or credits are insufficient, a typed error response is returned to the plugin. Users can also log the content of an email message as an internal note against a record, restricted to a permitted list of record types that can be extended by other modules.

[N-U53-005] Enrichment data returned from the external service is cached in a dedicated supporting table linked to the contact record. This table is kept separate from the main contact table to avoid adding a large field to a frequently accessed record. Each contact may have at most one enrichment cache entry. The cache stores both the raw enrichment response as a text string and the search key used to retrieve it. When a contact is removed the cache entry is also removed automatically.

[N-U53-006] A work order represents one step of a manufacturing order executed at a specific machine or workstation. Work orders are ordered by their sequence, their scheduled slot, and their start date. Each work order carries a barcode derived from the manufacturing order reference. The status of a work order progresses through blocked, to-do, in-progress, finished, and cancelled states. Scheduling is based on calendar slots reserved for the workstation. The start and end dates are computed from the reserved slot rather than stored directly. A progress percentage is derived from actual time recorded relative to expected duration. The costs per hour are captured at the moment the work order is marked finished so that later changes to the workstation rate do not affect historical cost.

[N-U53-007] Work orders support a dependency model where one work order can be blocked until predecessor work orders have produced a sufficient quantity. When a work order is started, a time-tracking entry is opened on the workstation. Pausing the work order closes the current time entry without marking the order complete. Finishing the work order closes all open time entries, stamps the completion date, and records the hourly cost. If the workstation is blocked due to a productivity issue, the work order cannot be started until the blockage is resolved. The scheduling planner considers the primary workstation and any configured alternatives, picks the earliest available slot across them all, and creates the slot reservation. Planning recurses through predecessor work orders to ensure correct ordering. A raw database query is used to detect overlapping slots on the same workstation.

[N-U53-008] A workstation is a physical or logical machine resource with an associated working calendar. Its real-time status is derived from open time-tracking entries: productive or reduced-speed entries indicate active use, other entries indicate a blockage, and the absence of any open entry indicates normal idle state. Overall equipment effectiveness is computed as productive time divided by total recorded time over the preceding month. A performance metric compares expected duration to actual duration for completed work orders. The workstation holds per-product capacity records that control how many units can be processed in parallel and override setup and cleanup times for specific products. The scheduling algorithm searches forward or backward through calendar intervals in blocks of fourteen days up to a configurable maximum horizon.

[N-U53-009] A routing operation is the definition of one step in a bill of materials, specifying which workstation performs it and how long it takes. The duration can be set as a fixed value or computed automatically from the average of the most recent completed work orders for that operation. The number of historical work orders used for this average is configurable. Operations can be restricted to specific product variants so that certain steps apply only when a particular combination of attributes is being produced. Operations can declare dependencies on other operations in the same bill of materials to enforce sequencing, and the system prevents circular dependencies. Creating or modifying an operation marks all active manufacturing orders using that bill of materials as having an outdated configuration.

[N-U53-010] An unbuild order reverses a completed manufacturing order by returning the finished product to raw components. It can be linked to the original manufacturing order, in which case component quantities and lot traceability are derived from the original production records. Without a linked order, component quantities are derived from the bill of materials. The system prevents unbuilding against an order that has not yet been completed. Serial-number-tracked products are handled one unit at a time. Previously unbuilt lots are tracked to prevent returning the same component twice. When the unbuild is confirmed, a note is posted on the original manufacturing order. A database constraint enforces a positive unbuild quantity. Completed unbuild orders cannot be deleted.

[N-U53-011] Several wizard flows support manufacturing operations. A quantity change wizard adjusts all component and finished product movements proportionally when the target production quantity is revised, and also adjusts the expected duration of all associated work orders. A backorder wizard lets the operator decide per manufacturing order whether to create a backorder for incomplete quantities or simply close the order. A split wizard divides a manufacturing order into smaller batches, optionally driven by a maximum batch size defined on the bill of materials. A serial number wizard assigns or generates serial numbers for tracked finished products, and can split the order into one sub-order per serial number. A consumption deviation wizard alerts the operator when actual component usage differs from the bill of materials quantities under warning or strict consumption policies, and offers both confirmation and quantity correction options.

[N-U53-012] When a manufacturing order is marked as complete and any of the component lots used have passed their expiry date, the system presents a confirmation dialog before proceeding. The dialog names the expired product and lot when only one is involved, and shows a general warning when multiple expired lots are present. The operator may confirm to proceed or cancel. The same expiry check applies when a work order step records its production. A context flag is used to skip the expiry check after the operator has already confirmed once, preventing the dialog from appearing twice.

[N-U53-013] When landed costs such as freight or customs duties are applied to receipts that originate from subcontracting orders, the cost allocation is redirected from the receipt movement to the upstream supply movements that actually delivered the components to the subcontractor. This ensures that the landed cost is charged to the correct layer of the supply chain. Non-subcontracting receipts are handled without any redirection. This module activates automatically whenever both the landed costs feature and the subcontracting feature are installed.

[N-U53-014] A bridge module connects the subcontracting feature to the repair order feature. It activates automatically when both features are installed. The module itself contains no business logic in the current revision; its purpose is to ensure that the two features are installed together and can coexist correctly. Any integration behaviour is expected to be delivered through configuration data or views rather than programmatic overrides.
