# U94 Neutral Knowledge — Payment Provider Webhook
> NEUTRAL LAYER — no source paths, no class/method names, no file extensions, no snake_case, no backticks

| NR-ID | Statement |
|---|---|
| NR-U94-001 | A payment transaction record carries a status field with six possible values: draft (initial), pending (submitted to provider but not yet confirmed), authorised (funds reserved but not captured), confirmed (payment complete), cancelled, and error. The default value at creation is draft. |
| NR-U94-002 | The status field on a payment transaction is read-only and cannot be copied; all status changes must be made through the framework-provided state-transition helpers, not by direct field assignment. |
| NR-U94-003 | A single framework method acts as the unified entry point for all incoming payment data from any provider. It orchestrates finding the transaction, validating the amount, applying provider-specific updates, and optionally creating a reusable payment token. |
| NR-U94-004 | When payment data arrives without a bound transaction record, the framework looks up the matching transaction from the database using the provider code and the merchant reference embedded in the payment data. |
| NR-U94-005 | Before any status change is applied, the framework validates that the amount and currency reported by the provider match the values stored on the transaction. Validation-type transactions are skipped. |
| NR-U94-006 | Provider modules must override the "apply updates" hook to translate provider-specific status strings into the framework's status transitions. The hook is called after amount validation passes. |
| NR-U94-007 | The transition to "pending" status is allowed only from "draft". Transition helpers always log a human-readable message on linked documents after updating the status. |
| NR-U94-008 | The transition to "authorised" status is allowed from "draft" or "pending". It indicates that funds have been reserved and are awaiting capture. |
| NR-U94-009 | The transition to "confirmed" (done) status is allowed from draft, pending, authorised, or error. After confirming, the framework also evaluates whether any parent transaction should be marked as complete. |
| NR-U94-010 | When a child partial-capture or void transaction reaches a final status, the framework checks whether all sibling transactions of the same operation type have also finalised; if so, it updates the parent transaction status accordingly. |
| NR-U94-011 | The transition to "cancelled" status is allowed from draft, pending, or authorised. It also triggers the parent-transaction state recalculation. |
| NR-U94-012 | The transition to "error" status is allowed from draft, pending, or authorised. Extra allowed source states can be passed as an optional argument to handle unusual scenarios (such as a failed refund). |
| NR-U94-013 | The internal state-update routine writes the new status, a status message, the current timestamp, and resets the post-processed flag in a single database write. Transactions already in the target state are silently skipped; transactions in an illegal source state generate a warning. |
| NR-U94-014 | In the core payment module, the post-processing step only marks the transaction as having been post-processed. All substantive accounting work is injected by the accounting integration module. |
| NR-U94-015 | A scheduled background job picks up all transactions that have not yet been post-processed within the last four days and calls the post-processing routine for each one, committing after each success and rolling back after each failure. |
| NR-U94-016 | The accounting integration module extends the payment transaction model by adding a link to an accounting payment record and a list of linked invoice documents. |
| NR-U94-017 | The link from a payment transaction to the corresponding accounting payment is a one-to-one read-only field that is set only after the accounting payment has been created during post-processing. |
| NR-U94-018 | Payment transactions are associated with invoices through a many-to-many relationship using a dedicated join table. Only moves of type customer invoice, customer credit note, vendor bill, or vendor refund are eligible. |
| NR-U94-019 | The accounting integration module's post-processing override iterates over confirmed transactions, validates any draft invoices linked to them, and then creates missing accounting payments. |
| NR-U94-020 | An accounting payment is created only if the transaction is confirmed, its operation is not a validation, no accounting payment already exists for it, and no child transactions have reached a final state. |
| NR-U94-021 | The payment-creation routine assembles the accounting payment from the transaction's amount, currency, partner, journal, payment method line, optional token reference, and memo; it also appends early-payment-discount write-off lines when applicable. |
| NR-U94-022 | The accounting payment record is created through the standard ORM create mechanism, which internally generates the underlying journal entry (account move) in the provider's configured journal. |
| NR-U94-023 | Immediately after creation, the accounting payment is posted, which confirms the journal entry and makes the accounting entries effective in the general ledger. |
| NR-U94-024 | After posting, the transaction's accounting-payment link field is set to the newly created payment, establishing the traceability from the payment transaction to the accounting record. |
| NR-U94-025 | When the transaction has associated invoices, the routine reconciles the payment's journal entry lines with the invoice's outstanding lines by matching on the destination account and calling the reconciliation routine on the combined line set. |
| NR-U94-026 | The Stripe connector registers a webhook endpoint at a provider-specific URL path. Stripe sends event notifications to this URL for events such as payment intent succeeded, payment intent failed, refund created, and refund updated. |
| NR-U94-027 | The Stripe webhook handler deserialises the incoming JSON event, locates the matching transaction by merchant reference, verifies the HMAC signature using a stored webhook secret and a time-window tolerance of ten minutes, and then delegates to the core processing entry point. |
| NR-U94-028 | Stripe's status strings are mapped to the framework's status values through a configuration constant: "succeeded" maps to confirmed, "requires capture" maps to authorised, "processing" and "pending" map to pending, "canceled" maps to cancelled, and "requires payment method" or "failed" map to error. |
| NR-U94-029 | The PayPal connector registers a separate webhook endpoint. Before processing, it verifies the notification origin by calling the PayPal webhook-signature verification API using transmission headers supplied by PayPal. |
| NR-U94-030 | PayPal payment data undergoes normalisation before processing because the structure of data from the capture-request response differs from the structure of webhook event payloads. |
| NR-U94-031 | PayPal's status strings are mapped to the framework status values through a provider-specific mapping constant: the "COMPLETED" status maps to confirmed, "PENDING" maps to pending, and "VOIDED" maps to cancelled. |
| NR-U94-032 | A browser-side polling endpoint triggers post-processing immediately after the customer is redirected back from the provider, providing a fast path that runs in parallel to the background scheduled job. The post-processing result — including the final status and the landing route — is returned to the browser as JSON. |
| NR-U94-033 | For refund transactions processed via webhook, the accounting post-processing cron is triggered immediately after the transaction is set to confirmed, because the browser-side polling path is not available for server-to-server webhook flows. |
