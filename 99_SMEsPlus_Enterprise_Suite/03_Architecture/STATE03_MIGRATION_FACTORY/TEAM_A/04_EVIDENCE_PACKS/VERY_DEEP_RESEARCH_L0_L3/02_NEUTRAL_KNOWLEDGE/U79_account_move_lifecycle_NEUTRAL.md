# U79 Neutral Knowledge — account.move Lifecycle
> NEUTRAL LAYER — no source paths, no class/method names, no file extensions, no snake_case, no backticks

| NR-ID | Statement |
|---|---|
| NR-U79-001 | A journal entry document in the accounting module has exactly three lifecycle states: Draft (initial editable state), Posted (validated and locked for accounting), and Cancelled. These are the only workflow states; there is no separate "confirmed" or "approved" state. |
| NR-U79-002 | Invoice and bill documents carry an additional computed payment state that is separate from the workflow state. The payment state can be: Not Paid, In Payment, Paid, Partially Paid, Reversed, Blocked, or an invoicing-only legacy state. Payment state is derived from reconciliation data, not manually set. |
| NR-U79-003 | Posting a journal entry is initiated via a public posting action that checks for anomalous amounts or dates and may open a confirmation dialog before delegating to the core posting logic. The action accepts only draft documents. |
| NR-U79-004 | The core posting logic validates: user has invoicing permission, the document is in draft state, at least one real journal line exists, the journal is active, the currency is active, all accounts are active, and the accounts belong to the correct company. Failures raise a validation error before any state change occurs. |
| NR-U79-005 | During posting, if the document date falls within a locked fiscal period, the date is automatically advanced to the day after the lock date rather than raising an error. This date adjustment occurs before the state is changed to Posted. |
| NR-U79-006 | When the document transitions to Posted, the system sets the document state to Posted and also records that this document has been posted before (a flag that is never reset thereafter), in the same write operation. |
| NR-U79-007 | The hash chain computation is triggered automatically by the write operation that sets the state to Posted, not directly by the posting function itself. The hash is computed and stored immediately after the state transition is flushed to the database. |
| NR-U79-008 | After all documents are marked Posted, the posting logic calls the reversal reconciliation routine for any documents that are reversals of already-posted originals, and also processes any import-marked reconciliations on the resulting lines. |
| NR-U79-009 | Resetting a journal entry to Draft requires the document to currently be in Posted or Cancelled state. If the document is associated with a government cancellation workflow, a cancellation request must be submitted instead of a direct draft reset. |
| NR-U79-010 | Three categories of posted documents can never be reset to Draft regardless of other conditions: exchange difference entries, tax cash basis entries, and any entry that has had the inalterability hash set. The hash lock is permanent and irreversible. |
| NR-U79-011 | Cancelling a Posted document is a two-step process: the document is first reset to Draft (invoking all draft-reset guards including the hash check), then cancelled. Cancellation removes all reconciliation links, cancels associated payments, and sets the workflow state to Cancelled. |
| NR-U79-012 | The fiscal lock date check examines three separate lock dates on the company: the standard user lock date (for all entries), the accounting officer lock date (stricter), and a hard lock date. The check parameters vary depending on whether the journal is a sales journal, purchase journal, or general journal. |
| NR-U79-013 | The tax lock date check is a separate mechanism from the fiscal lock date check. It applies only to lines that affect the tax report and uses the company tax lock date. Both checks can be triggered independently by the same write operation. |
| NR-U79-014 | The fiscal lock date check is triggered in three scenarios: when a Posted document's name or date is changed in a write operation; when a write operation attempts to change the document state away from Posted; and after any write that changes date or state, re-checked on all resulting Posted documents. |
| NR-U79-015 | The fields protected by lock date enforcement fall into three groups: tax-sensitive fields (balance, tax line, tax identifiers, tax tags); fiscal fields (tax fields plus account, journal, foreign amount, currency, partner); and reconciliation-sensitive fields (account, date, balance, foreign amount, currency). |
| NR-U79-016 | The inalterability hash is a chained hash stored on each secured journal entry. The default hash version is 4. In version 4, the hash is stored prefixed with the version number. Older versions stored a plain hexadecimal hash string. |
| NR-U79-017 | Hash computation covers the journal entry header fields (name, date, journal, company for version 4) and all line fields from the integrity field list. All field values are serialized to a JSON string and combined with the previous entry's hash before computing the SHA-256 digest. The hash chain is ordered by the document sequence number within a journal and sequence prefix. |
| NR-U79-018 | Hash computation only occurs for journals where the inalterability restrict mode is enabled. Journals without this setting are not subject to automatic hash chaining, even after posting. The hash can also be applied manually (forced) regardless of journal setting. |
| NR-U79-019 | The hash computation requires a gap-free sequence in the journal prefix. If a sequence gap is detected, or if there are unreconciled bank statement lines in the chain, the hashing operation raises an error and refuses to proceed. |
| NR-U79-020 | Once the inalterability hash is set on a document, any attempt to modify the integrity hash fields or the hash field itself via the normal write operation raises an error. The hash lock is enforced at the ORM layer and cannot be bypassed by normal user actions. |
| NR-U79-021 | The "posted before" flag is a one-way latch: set at the moment of first posting and never cleared in any subsequent operation including reset to Draft, cancellation, or reversal. It permanently records that the document has been through the Posted state at least once. |
| NR-U79-022 | A partial reconciliation record represents a single debit-credit match between two journal entry lines. Each record stores the matched amounts in company currency and both foreign currencies, plus a reference to a full reconciliation record if the match completes a full reconciliation. |
| NR-U79-023 | A full reconciliation record is created automatically when all lines in a reconciliation group reach zero residual balance. The full reconciliation record links back to all involved partial reconciliation records and all involved journal entry lines. |
| NR-U79-024 | The reconciled status on a journal entry line is a stored computed field derived from the residual amount. A line is considered fully reconciled when both its company-currency residual and foreign-currency residual are zero within rounding tolerance. This is computed from the matched debit and credit partial reconciliation records on that line. |
| NR-U79-025 | There is no reconciliation state on the journal entry document itself. Reconciliation state exists only at the line level. The invoice payment state (Paid, Partial, etc.) is the document-level signal derived from reconciliation, computed separately. |
| NR-U79-026 | The reconcile operation on a group of journal entry lines creates partial reconciliation records for each debit-credit pair, creates exchange difference entries if foreign currency rates differ, creates tax cash basis entries if applicable, and creates a full reconciliation record if the group is fully reconciled. All of this occurs within a balanced-check context. |
| NR-U79-027 | Removing a reconciliation (unreconcile) cascades: the partial records are deleted, the full reconciliation record is deleted, any exchange difference journal entries are reversed, any tax cash basis entries are reversed, and the invoice payment state is recalculated. |
| NR-U79-028 | Payment state computation on an invoice uses a SQL query on partial reconciliation records to identify which payments are matched, whether those payments are fully matched against bank statements, and whether the counterpart move types represent a reversal pattern. This determines the Not Paid, In Payment, Paid, or Reversed outcome. |
| NR-U79-029 | The reversal mechanism creates a copy of the original document with the type-reversed document type (customer invoice becomes credit note, vendor bill becomes vendor credit note, journal entry remains a journal entry) and all journal line balances negated. The copied document has a link back to the original via the reversal-of reference. |
| NR-U79-030 | When a reversal is created with the cancel flag active, it is immediately posted, and the original and reversal lines are reconciled together to neutralize the original. When created without the cancel flag, the reversal remains in Draft and auto-reconciles when it is posted later. |
| NR-U79-031 | The reversal-of link on a document (pointing to the original) and the reverse-documents link (a collection pointing to all reversals) are two sides of the same relationship. Neither is cleared when a reversal is reset to draft or cancelled. |
| NR-U79-032 | Editing a Posted document is restricted to specific operations: the invoice lines, date, partner, payment terms, currency, fiscal position, and cash rounding cannot be modified. Some contextual operations may bypass this check using a skip flag. |
| NR-U79-033 | Changing the journal of a document that has been posted before is blocked unless the document's sequence name is simultaneously cleared or set to a placeholder. This protects sequence integrity. |
| NR-U79-034 | For future-dated documents, posting in soft mode (the normal user-facing action) defers the actual posting: the auto-post setting is changed to "at date" and the document will be posted automatically by the scheduler on the accounting date. Posting in hard mode (used internally) posts future-dated documents immediately. |
| NR-U79-035 | Under strict audit trail mode (a company setting), journal entries that have been posted at least once cannot be permanently deleted. They can only be cancelled. The system enforces this at the record deletion level. |
