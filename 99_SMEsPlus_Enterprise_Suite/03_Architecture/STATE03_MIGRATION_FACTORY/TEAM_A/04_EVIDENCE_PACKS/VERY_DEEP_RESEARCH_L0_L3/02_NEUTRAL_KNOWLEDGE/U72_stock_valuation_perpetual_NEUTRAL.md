# U72 Neutral Knowledge — Stock Valuation Perpetual
> NEUTRAL LAYER — no source paths, no class/method names, no file extensions, no snake case, no backticks

| NR-ID | Statement |
|---|---|
| NR-U72-001 | In Odoo 19 Community the stock valuation layer concept previously represented as a dedicated model no longer exists; inventory costing history is instead recorded through a product value history model that tracks standard price changes, lot-level price updates, and manual move value adjustments |
| NR-U72-002 | Each product value history record may be linked to a specific stock movement; when a link is present the record represents a manual override of that movement's valuation amount rather than a product-wide price change |
| NR-U72-003 | The monetary amount stored in a product value history record represents either a unit price (for product-level price changes) or the total value of the associated movement (for movement-level overrides) |
| NR-U72-004 | Creating a product value history record linked to a movement automatically triggers recalculation of that movement's monetary value field |
| NR-U72-005 | Each stock movement carries a monetary value field in the company currency representing its current inventory valuation amount; this field is populated during movement validation and is the primary source for downstream accounting |
| NR-U72-006 | Each stock movement may be linked to a single accounting journal entry generated during perpetual valuation; this link is maintained for audit and traceability purposes |
| NR-U72-007 | When a stock movement is validated, the costing engine first values outgoing movements (to capture the current cost stack state), then calls the base validation logic, then values incoming movements, and finally generates accounting entries |
| NR-U72-008 | Outgoing movements are valued before base movement validation completes because the FIFO cost stack must reflect quantities present before any same-batch receipts are added |
| NR-U72-009 | The accounting entry generation step runs on all movements in a validation batch; only movements meeting the perpetual gate check actually produce journal entries |
| NR-U72-010 | A single accounting journal entry is created for an entire validation batch; individual movement lines are collected and posted in one journal entry using the inventory stock journal configured at company level |
| NR-U72-011 | The gate check for accounting entry creation requires: product is a storable good, the movement has a non-zero valued quantity, either the source or destination location carries a valuation account assignment, and the product category or company is configured for perpetual (real-time) valuation |
| NR-U72-012 | Perpetual valuation is the setting described as real-time or at invoicing in the inventory configuration; periodic (at closing) valuation suppresses automatic entry generation during movement validation and instead relies on a manual closing process |
| NR-U72-013 | The journal used for inventory valuation entries is configured at company level and applies to all perpetual stock movements for that company |
| NR-U72-014 | The accounting entry for a stock movement uses the location valuation account and the stock valuation account as the two sides; the direction (which is debit, which is credit) depends on whether the source or destination location carries the valuation account |
| NR-U72-015 | For outgoing movements under FIFO costing, the movement value is determined by consuming the oldest-first incoming cost layers built from historical receipt movements ordered by date; the cost of each receipt is stored directly on the receipt movement record |
| NR-U72-016 | For outgoing movements under standard-price or weighted-average costing, the movement value is the current standard price multiplied by the moved quantity at the time of validation |
| NR-U72-017 | For incoming movements, value is determined in priority order: a manual product value override if present, then the linked vendor bill amount, then the purchase order line price, then product standard price |
| NR-U72-018 | The FIFO cost stack is rebuilt on demand by searching incoming movement records ordered from newest to oldest, reversing the list to produce oldest-first order, and walking forward until the on-hand quantity is consumed |
| NR-U72-019 | After movement validation, the product standard price is updated: for weighted-average products a weighted recalculation is performed; for FIFO products the standard price is set to total inventory value divided by on-hand quantity |
| NR-U72-020 | When an incoming movement arrives in a batch with no outgoing movements, a fast-path weighted-average update formula is used: new average equals previous quantity times old standard price plus added value, divided by new total quantity |
| NR-U72-021 | For FIFO products with no remaining on-hand stock, the standard price falls back to the unit price of the most recent incoming movement |
| NR-U72-022 | The costing method (standard price, weighted average, or FIFO) is configured as a company-dependent property on the product category; a company-level default is used when the category carries no override |
| NR-U72-023 | The valuation mode (periodic or perpetual) is configured as a company-dependent property on the product category; the company carries a default valuation mode, which defaults to periodic |
| NR-U72-024 | When a customer invoice is posted for a perpetual storable product, two additional journal lines are automatically created: one debiting the cost-of-goods-sold expense account and one crediting the stock valuation account, transferring the inventory value to expense at the point of sale recognition |
| NR-U72-025 | For customer sales, the COGS credit to the stock valuation account uses the weighted-average or FIFO unit cost of the delivery movement linked to the invoice line |
| NR-U72-026 | When a vendor bill is posted for a perpetual storable product, the purchase invoice line's general-ledger account is automatically set to the stock valuation account instead of the usual purchase expense account; this debits inventory value directly from the bill |
| NR-U72-027 | The bill-to-inventory reconciliation (purchase receipt to vendor bill matching) is accomplished without an intermediate stock-input transit account in Odoo 19 Community; the vendor bill debit goes directly to the stock valuation account |
| NR-U72-028 | For products valued at standard price, an additional price-difference journal line is generated on the vendor bill when the billed price differs from the standard cost; this difference is posted to the price-difference account configured on the product category |
| NR-U72-029 | When a purchase order receipt has not yet been billed, the movement value falls back to the purchase order line price converted to company currency at the movement date |
| NR-U72-030 | Return movements derive their value proportionally from the original outgoing movement value; exact cost reversal is performed using the ratio of returned quantity to original valued quantity |
| NR-U72-031 | Changing the costing method on a product category does not raise a blocking error even when historical movements exist; the engine immediately recomputes standard prices for all affected products under the new method |
| NR-U72-032 | The company-level stock valuation account serves as a fallback when the product category carries no specific valuation account; the category-level account takes precedence over the company default |
| NR-U72-033 | For periodic valuation, a manual closing action generates a batch of accounting entries reconciling inventory book value against the general-ledger stock account balance; this can be triggered manually or scheduled at daily or monthly frequency |
| NR-U72-034 | The stock valuation account carries a linked stock variation account; this variation account is used for continental perpetual adjustments and periodic closing entries to post inventory movement through profit and loss |
| NR-U72-035 | A valuation account may be configured directly on a stock location; when present, movements involving that location generate additional reclassification entries between the location valuation account and the product valuation account during the manual closing process or perpetual movement |
| NR-U72-036 | The product-level average cost and total inventory value are computed on demand by replaying all historical incoming and outgoing movements in chronological order; a manual price-history checkpoint can seed the calculation from a specific date to avoid scanning the full movement history |
| NR-U72-037 | FIFO cost queries use an arbitrary batch limit when fetching incoming movements and will fetch additional batches if the on-hand quantity requires more history than the initial fetch provides; this prevents memory exhaustion on products with long movement histories |
| NR-U72-038 | The product value history model also supports lot-level valuation; when a product has lot valuation enabled, each lot carries its own standard price and the product-level price reflects the weighted average across lots |
