# U75 Neutral Knowledge — Period Cutoff / Accrued Orders
> NEUTRAL LAYER — no source paths, no class/method names, no file extensions, no snake_case, no backticks

| NR-ID | Statement |
|---|---|
| NR-U75-001 | An accrued-orders wizard exists as a transient model in the accounting module. It handles both purchase and sales order accruals. The wizard is triggered manually by a user action, not by any scheduled job. |
| NR-U75-002 | The wizard carries a reversal date field. When the wizard is first opened, the reversal date is automatically set to one day after the accrual entry date. |
| NR-U75-003 | The system enforces that the reversal date must be strictly later than the accrual entry date. If the user enters an earlier or equal date, the wizard rejects the submission before creating any entries. |
| NR-U75-004 | For purchase-side accruals, the counterpart account must be of the current liability type. For sales-side accruals, it must be of the current asset type. The domain restriction is applied automatically based on the order type in context. |
| NR-U75-005 | Each order line's accrual amount is posted to the product's income or expense account, applying any active fiscal position mapping. Purchase lines use the expense account; sales lines use the income account. |
| NR-U75-006 | When a purchase order line involves a storable product under perpetual inventory valuation, the line-level account shifts from the expense account to the stock variation account, capturing the accrual on the balance sheet rather than directly in profit and loss. |
| NR-U75-007 | The wizard produces a single balanced counterpart journal item summarising the total accrual across all selected orders. This item is only generated when the net balance is non-zero after company-currency rounding. |
| NR-U75-008 | When the user confirms the wizard, the system creates the accrual entry and posts it immediately. It then creates the reversal entry and posts that immediately as well, in the same database transaction. Both entries exist in posted state from the moment the wizard completes. |
| NR-U75-009 | The reversal entry carries a reference indicating it is the reversal of the original accrual, and its accounting date is the user-supplied reversal date. The reversal is not a draft waiting for manual posting; it is posted automatically. |
| NR-U75-010 | A hard validation prevents the wizard from proceeding when the reversal date is on or before the accrual entry date. This is checked before any database write. |
| NR-U75-011 | For purchase lines where more quantity has been billed than received at the accrual date, the wizard recalculates the unit price from posted invoice lines and received quantities to arrive at an accurate over-billing amount. |
| NR-U75-012 | The wizard's base implementation returns no expense or stock-variation accounts for line-level lookup. A module extending inventory accounting is expected to override this to supply the correct accounts for perpetual-valuation products. |
| NR-U75-013 | The accounting module adds a Global Lock Date field to the company configuration. Any journal entry dated on or before this date is postponed to a later date or blocked, depending on the journal sequence settings. |
| NR-U75-014 | A Hard Lock Date field also exists on company configuration. Unlike the soft lock dates, the hard lock date cannot be bypassed by granting exceptions to individual users. It is intended as a permanent, irreversible close boundary. |
| NR-U75-015 | Separate soft lock dates exist for sales journals and purchase journals, enabling the finance team to close purchases and sales independently from the global lock. |
| NR-U75-016 | Lock date enforcement runs on every write and post operation for journal entries. The system inspects the applicable lock dates based on the journal type and raises an error with the name and value of the violated lock date. |
| NR-U75-017 | The lock date check is scoped per journal type: the global lock and hard lock are always checked; the sales lock applies only to sales journals; the purchase lock applies only to purchase journals; the tax lock is not checked during the standard write or post guard. |
| NR-U75-018 | A dedicated month-end inventory valuation close action exists on the company record. It collects all valuation adjustments needed, creates a single journal entry summarising them, and can post that entry immediately when called from automation. |
| NR-U75-019 | The inventory close logic has three sub-calculations: a location reclassification step, a stock-versus-accounting delta reconciliation, and a continental perpetual variation step. Results from all three are combined into one closing journal entry. |
| NR-U75-020 | A scheduled action handles automatic inventory close. It runs daily. On the last calendar day of each month it additionally performs a monthly close. It processes only companies configured for daily or monthly automatic closing; companies set to manual are skipped. |
| NR-U75-021 | The scheduled action for inventory valuation close is defined in the module's data layer as a daily job active by default, operating at the company level. It is the only stock-valuation-related scheduled action in the module. |
| NR-U75-022 | The system tracks the last closing entry by storing up to ten closing entry identifiers in a system parameter keyed by company. This allows the next close to calculate only the delta since the previous close, rather than reprocessing all history. |
| NR-U75-023 | The close action prevents back-dated closings. If the requested close date is earlier than the date of the most recent existing closing entry, the system raises an error instructing the user to cancel the later closing first. |
| NR-U75-024 | For customer invoices of perpetual-valuation products, two additional journal items (cost-of-goods-sold lines) are injected at invoice posting time: one credits the stock valuation account and one debits the cost-of-goods-sold account for the same amount. |
| NR-U75-025 | The invoice posting routine is extended in the inventory accounting module to inject these cost-of-goods-sold lines before the base posting logic runs. This injection is the real-time perpetual valuation trigger for outgoing goods. |
| NR-U75-026 | For vendor bills, a price-difference adjustment mechanism exists but is gated behind an anglo-saxon accounting flag on the company. When active and the product uses standard costing, it creates price-difference correction lines debiting a dedicated account and crediting the bill line account. |
| NR-U75-027 | In the standard continental accounting setup (the default in Community), the anglo-saxon flag is off, so no price-difference or goods-receipt-invoice-receipt clearing lines are generated on vendor bills. The stock valuation account and the vendor payable account are not connected through an interim clearing account in this setup. |
| NR-U75-028 | An optional valuation account field exists on stock locations. When populated, it causes inventory movements into or from that location to generate reclassification entries, either at closing time (periodic) or immediately at movement confirmation (real-time). |
| NR-U75-029 | When a stock location has a valuation account set, incoming movements credit that location account and debit the stock valuation account; outgoing movements do the reverse. This location-based mechanism is how transit and non-standard locations are handled in the valuation chain. |
| NR-U75-030 | A separate period-close wizard exists in the accounting module for cryptographically securing journal entry chains. It identifies all unhashed posted entries up to a selected date and applies a hash chain to them, making later tampering detectable. This is the Community mechanism for immutable period close beyond lock dates. |
| NR-U75-031 | The accounting module has one daily scheduled action that posts draft entries whose auto-post date has passed. There is no scheduled action for period close, accrual creation, or lock date advancement in the accounting module itself. |
| NR-U75-032 | There is no period model in Odoo 19 Community accounting. All period control is implemented through lock date fields on the company record. There are four soft lock dates and one hard lock date. Exceptions to soft locks can be granted per user. |
| NR-U75-033 | For companies using continental perpetual valuation, the closing routine calculates the net change in stock accounting value over the current fiscal year and posts that net change between a variation account and a stock expense account, ensuring the period variation is captured in profit and loss. |
| NR-U75-034 | The automatic closing period for inventory valuation is configured per company with three options: manual, daily, and monthly. Only companies with daily or monthly settings participate in the scheduled automatic close. |
