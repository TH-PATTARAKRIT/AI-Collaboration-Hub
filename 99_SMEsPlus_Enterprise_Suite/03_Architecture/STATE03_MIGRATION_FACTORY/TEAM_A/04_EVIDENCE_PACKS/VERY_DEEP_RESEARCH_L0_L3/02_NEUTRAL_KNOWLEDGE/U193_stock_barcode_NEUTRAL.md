## Key Design Patterns

1. **Single-call state serialization** — `get_barcode_view_state()` delivers the complete working state in one RPC, minimizing latency for warehouse workers on mobile devices.
2. **Client-side cache + lazy fetch** — product and location barcodes are preloaded into JavaScript dictionaries; unknown barcodes trigger targeted RPC lookups.
3. **Step-state machine** — scan steps are stateful and mode-aware, allowing the same abstract action to handle receipts, deliveries, inventories, and internal transfers with different bypass rules.
4. **Immediate-transfer default** — new pickings created by scanning a picking type barcode from the main menu are immediate transfers, meaning no demand reservation step is required.
5. **Lot creation deferred to validation** — when a picking type is set to create-only, lot names are stored as strings and the lot record is only persisted on `button_validate`, avoiding orphan lots from abandoned operations.
6. **Split-on-partial** — both destination location and destination package assignment trigger automatic line splitting to preserve unreserved quantities.

## Migration Relevance Notes

- `stock_barcode` depends on `barcodes` module for the `barcode_events_mixin` — this mixin must exist in the target Odoo version.
- `stock.inventory` is used as a separate model; in Odoo 16+, physical inventory was merged into `stock.quant`. Migration of the inventory client action requires adapting to `stock.quant` or the `stock.inventory` compatibility shim.
- `immediate_transfer` field on `stock.picking` may have changed semantics in v16+.
- `product_packaging` barcode support is wired through `on_barcode_scanned` — any changes to packaging model structure require updating this path.
- `lot_name` (string) vs `lot_id` (M2O) dual lot handling in `validate_lot()` must be preserved in any port.
