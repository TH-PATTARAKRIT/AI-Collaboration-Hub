## 0. The canonical question, answered

The directive requires each of these to be **determined independently**:

> PAYMENT STATE ≠ ACCOUNTING POSTING STATE ≠ BANK CONFIRMATION STATE ≠ RECONCILIATION STATE

**Finding PSM-F-00 — In the reference implementation they are NOT four independent states. They are two stored states, one derived boolean, and one absent concept.**

| Required state | What actually exists | Independent? |
|---|---|---|
| Payment state | `account.payment.state` — 5 values, **computed and stored**, `readonly=False` | **No.** Its compute reads the *reconciliation* of the liquidity line and the *payment status of linked invoices*. |
| Accounting posting state | `account.move.state` — the journal entry's own state | **No.** In v18 the payment's `write()` generates and posts the move; state drives the move, not the reverse. |
| Bank confirmation state | **No such field exists.** The nearest proxy is `account.payment.is_matched`. | **No.** `is_matched` is set `True` by configuration alone in two branches (PSM-F-04). |
| Reconciliation state | `account.bank.statement.line.is_reconciled` + `account.payment.is_reconciled` | **Partially.** Both are computed; the statement-line one has a default-true terminal branch. |

**Consequence, stated plainly:** a design that assumes it can read four independent facts from the reference model will be reading two facts and two derivations of them. **Every one of the four must be re-authored as a first-class, separately-written state in the target design.** This is the single most important structural output of P06.

## 1. `account.payment.state` — the payment state

**PSM-F-01 — Five values, no `posted` and no `cancel`.**
`$V18E/account/models/account_payment.py:38-51`:
```
('draft', "Draft"), ('in_process', "In Process"), ('paid', "Paid"),
('canceled', "Canceled"), ('rejected', "Rejected"),
```
declared `required=True, default='draft', compute='_compute_state', store=True, readonly=False, tracking=True, copy=False`.
**DENOMINATOR:** POPULATION: the single `state` field definition on that model. PATH SET: that file. UNIT: selection value. **COUNT = 5.**

**PSM-F-02 — `readonly=False` on a stored compute means the state is directly writable.**
Any code path — or any user with write access through a view — can set `state` without passing through an action method. The compute then runs only on its declared dependencies. This is not a state *machine*; it is a state *field with an opinion*.

**PSM-F-03 — The compute promotes `in_process → paid` by two different mechanisms, and they mean different things.**
`$V18E/account/models/account_payment.py:411-425`:
```
@api.depends('invoice_ids.payment_state', 'move_id.line_ids.amount_residual')
...
payment.state = ('paid' if move.company_currency_id.is_zero(sum(liquidity.mapped('amount_residual')))
    or not liquidity.account_id.reconcile else 'in_process')
...
if payment.state == 'in_process' and payment.invoice_ids and all(invoice.payment_state == 'paid' for invoice in payment.invoice_ids):
    payment.state = 'paid'
```
Mechanism 1: the **liquidity line is fully reconciled** — i.e. the bank leg has been matched. That is close to "the bank confirmed it".
Mechanism 2: **all linked invoices report `paid`** — which says nothing about the bank at all.
Mechanism 3 (the `or` clause): **the liquidity account is not reconcilable** — in which case `paid` is asserted with no matching of any kind.

**Therefore `state == 'paid'` is ambiguous by construction.** Three distinct real-world situations produce the identical value, and nothing on the record distinguishes them. For a treasury process this is the defining defect: *the system cannot tell you why it thinks a payment is paid.*

**PSM-F-03a — The dependency is mutually recursive.**
`account.payment._compute_state` depends on `invoice_ids.payment_state`; `account.move._compute_payment_state` depends on `matched_payment_ids.state`. Two computed stored fields each depending on the other. Recomputation order is an ORM implementation detail, not a business rule.

**PSM-F-03b — The compute never demotes to `draft`.** Only forward transitions are expressed.

## 2. State drives the move — the v18 inversion

**PSM-F-05 — `action_post` does not post anything. The journal entry is generated by the `write()` hook.**
`$V18E/account/models/account_payment.py:1067-1070`:
```
self.filtered(lambda pay: pay.outstanding_account_id.account_type == 'asset_cash').state = 'paid'
self.filtered(lambda pay: pay.state in {False, 'draft', 'in_process'}).state = 'in_process'
```
`$V18E/account/models/account_payment.py:910-913`:
```
def write(self, vals):
    if vals.get('state') in ('in_process', 'paid') and not vals.get('move_id'):
        self.filtered(lambda p: not p.move_id)._generate_journal_entry()
        self.move_id.filtered(lambda m: m.state == 'draft').action_post()
```
**This is the central v18 change: state drives the move, not the move driving state.** Any P06 design carried over from an earlier generation — where posting the entry set the payment state — is modelling a system that no longer exists.

**PSM-F-05a — A cash-type outstanding account jumps straight to `paid`.** First line above. No intermediate state, no bank event, no reconciliation. For a Thai SME operating a cash journal this is the normal path, and it produces `paid` with zero bank evidence.

**PSM-F-06 — The remaining state actions are single assignments.**
`$V18E/account/models/account_payment.py:1072-1089` — `action_validate` sets `paid`; `action_reject` sets `rejected`; `action_cancel` sets `canceled` then `draft_moves.unlink()` and `button_cancel()` on the rest; `action_draft` sets `draft` and `button_draft()`.
**There is no transition table, no guard on which transitions are legal, and no reason recorded for `rejected` vs `canceled`.** For a treasury process, "the bank refused this" and "we changed our mind" are different facts with different accounting consequences; here they are two adjacent one-line methods with identical structure.

**PSM-F-07 — A payment can legally exist with no journal entry.**
`$V18E/account/models/account_payment.py:837-845` — the ValidationError fires only when an outstanding account is set:
```
if (payment.state not in ('draft', 'canceled') and not payment.move_id
    and payment.outstanding_account_id):
    raise ValidationError(...)
```
and `_generate_journal_entry` (`:1001-1002`) acts only on `not p.move_id and p.outstanding_account_id`.
**Consequence:** with no outstanding account configured, a payment reaches `paid` with **no accounting entry whatsoever**. Combined with PSM-F-13 below (a move-less payment can drive an invoice to `paid` with a non-zero residual), this is a complete settlement path that touches no ledger.

## 3. Bank confirmation state — the absent concept

**PSM-F-04 — `is_matched` is not a bank-confirmation fact. It is true by configuration in two branches.**
`$V18E/account/models/account_payment.py:436-455`:
```
if not pay.outstanding_account_id:
    pay.is_reconciled = False
    pay.is_matched = pay.state == 'paid'
...
if pay.journal_id.default_account_id and pay.journal_id.default_account_id in liquidity_lines.account_id:
    pay.is_matched = True
```
Branch A (`:438`): with no outstanding account, `is_matched` is simply a copy of `state == 'paid'` — **circular**, since `state` was itself derived from matching.
Branch B (`:450`): when the payment posts directly to the bank account rather than to an outstanding account, `is_matched = True` **unconditionally, with no bank statement in existence**. The in-code comment states the intent: to let a user manage payments without statement lines.
Branch C (`:444`): a zero-amount payment is declared both `is_reconciled` and `is_matched` true.
Branch D (`:441`): with no currency, id or move, `is_matched = False`.
Branch E (`:452`): the only site that tests liquidity-line reconciliation.

> **COUNT CORRECTED at the supplemental round (REV-E-11): four top-level branches, five assignment sites.** An earlier state of this finding named three. See `25_` §3.

**The field's own label is "Is Matched With a Bank Statement" (`:54`). In two of its three branches it is true when no bank statement exists.** This is the evidence for cross-process blocker `P06-B-06`: **the system has no field whose meaning is "the bank confirmed this."**

**PSM-F-04a — And `is_matched` is load-bearing.** `account.move._compute_payment_state` reads it through SQL (`$V18E/account/models/account_move.py:1159-1160`):
```
COALESCE(BOOL_AND(COALESCE(pay.is_matched, FALSE)) FILTER (WHERE counterpart_move.origin_payment_id IS NOT NULL), TRUE)
```
so `in_payment` versus `paid` on the customer-facing invoice turns on this configuration-dependent boolean. **A configuration choice about outstanding accounts silently changes what the business sees as the payment status of its invoices.**

## 4. Invoice-side state — `account.move.payment_state`

**PSM-F-08 — Seven values.**
`$V18E/account/models/account_move.py:48-56` — `not_paid, in_payment, paid, partial, reversed, blocked, invoicing_legacy`. **DENOMINATOR:** POPULATION: the `PAYMENT_STATE_SELECTION` constant. UNIT: selection value. **COUNT = 7.**

**PSM-F-09 — Two of the seven are sticky and never recomputed.**
`$V18E/account/models/account_move.py:1132-1140` partitions into four groups; `invoicing_legacy` and `blocked` are excluded from computation, and everything that is not a posted invoice is forced to `not_paid`.

**PSM-F-10 — `blocked` is a manual toggle, not a computed fact.**
`$V18E/account/models/account_move.py:5376-5384` — `action_toggle_block_payment`, refusing only to block an already `paid`/`in_payment` invoice.

**PSM-F-11 — `in_payment` exists only when the Accounting layer is installed.**
`$V18E/account/models/account_move.py:6236-6241` returns `'paid'`; the override at `$V18E/accountant/models/account_move.py:7-9` (a nine-line file) returns `'in_payment'`.
**DENOMINATOR:** PATTERN `_get_invoice_in_payment_state` over `$V18E`, `--include=*.py`: 25 hits, of which exactly **2** are definitions in `models/`. **Class A within that scope.**
**Consequence:** the meaning of "paid" on an invoice changes with the installed edition. In one configuration `paid` means *bank-matched*; in the other it means *residual is zero*. **The same word carries two different assurance levels depending on a module install.** Any P06 control expressed as "invoice is paid" is undefined until the edition is fixed.

**PSM-F-12 — `in_payment` ⇔ residual zero but at least one counterpart payment is not matched.** From PSM-F-04a's SQL. This is the only place in the model where "money left us but the bank has not confirmed" is expressed — and it rests entirely on the configuration-dependent `is_matched`.

**PSM-F-13 — A move-less payment can drive an invoice to `in_payment`/`paid` with a NON-ZERO residual.**
**Precondition (added by AAS1-C-02):** the branch is conditioned on `not p.move_id`, i.e. a payment with no journal entry, reachable only where no outstanding account is configured (PSM-F-07). The accurate statement is therefore: *in a configuration where payments generate no accounting, invoice settlement status is driven by the payment record alone.*
`$V18E/account/models/account_move.py:1213-1218`:
```
elif invoice.matched_payment_ids.filtered(lambda p: not p.move_id and p.state == 'in_process'):
    new_pmt_state = invoice._get_invoice_in_payment_state()
elif reconciliation_vals:
    new_pmt_state = 'partial'
elif invoice.matched_payment_ids.filtered(lambda p: not p.move_id and p.state == 'paid'):
    new_pmt_state = invoice._get_invoice_in_payment_state()
```
**Settlement is asserted on the invoice while the ledger still carries the full receivable.** The customer-facing status and the general ledger disagree, by design, and nothing reconciles them. This is the highest-severity finding of this file.

**PSM-F-14 — `status_in_payment` exists and merges two state machines into one display field.**
`$V18E/account/models/account_move.py:550-557` and `:1221-1224` — non-stored, `PAYMENT_STATE_SELECTION + [('draft',...), ('cancel',...)]`, nine possible values, returning `move.state` when draft/cancelled and `payment_state` otherwise. Useful for a screen; **unusable as a control state**, because it conflates document lifecycle with settlement.

**PSM-F-15 — Two distinct payment↔invoice relations.**
`$V18E/account/models/account_move.py:207-221` — `origin_payment_id` (this entry *is* the payment's journal entry) versus `matched_payment_ids` (m2m, payments linked to this invoice). The reverse `invoice_ids` on the payment carries the in-code comment (`$V18E/account/models/account_payment.py:142-149`): *"contains the invoice even if they don't have a journal entry and are not reconciled"*. **The link is asserted before, and independently of, any accounting fact.**

## 5. Duplicate reference detection — advisory, and inconsistent between its two call sites

**PSM-F-16 — `_fetch_duplicate_reference` matches on five columns plus a state filter.**
`$V18E/account/models/account_payment.py:753`, join predicate `:788-806`: `partner_id`, `company_id`, `date`, `payment_type`, `amount`, and `duplicate_payment.state IN %(matching_states)s` with default `('draft', 'in_process')`.
**DENOMINATOR:** POPULATION: the JOIN predicate of that single query. UNIT: matched column. **COUNT = 5**, plus 1 state filter.

**PSM-F-17 — The record filters itself out when `in_process`.**
`$V18E/account/models/account_payment.py:763` — `payments = self.filtered(lambda p: p.partner_id and p.amount and p.state != 'in_process')`.

**PSM-F-18 — The docstring describes conditions that are not in the query.**
`:754-761` claims duplicates "are not reconciled … represent a credit in the same account receivable … are in the suspense account". None of those conditions appear in the SQL at `:788-806`. **The documentation is stale relative to the implementation.** Recorded because a designer reading the docstring would build the wrong control.

**PSM-F-19 — The register wizard passes a state value absent from the v18 `account.payment.state` selection.** *(Class A within the declared scope: the selection at `$V18E/account/models/account_payment.py:38-51`.)*
`$V18E/account/wizard/account_payment_register.py:889` — `def _fetch_duplicate_reference(self, matching_states=('draft', 'posted')):`
`'posted'` is **not** among the five values at `account_payment.py:38-51`. **The wizard's duplicate query can therefore only ever match `draft` payments** — `in_process` duplicates, which are precisely the dangerous ones, are invisible to it.
**Classification: CONFIRMED DEFECT** (two verbatim quotes, cross-file, no interpretation required).

**PSM-F-20 — The double-pay guard is advisory and never consulted.**
`$V18E/account/wizard/account_payment_register.py:566-577` builds `actionable_errors['unpaid_matched_payments']` with the message *"There are payments in progress. Make sure you don't pay twice."* — `actionable_errors` is a `fields.Json` display field (`:162`) and is **never read** in `_create_payments` (`:1194-1258`).
**There is no blocking check preventing a second payment against an invoice already fully covered by an in-flight payment.** Carried into the Duplicate/Match Attack file as attack A3.

## 7. Move ↔ payment synchronisation

**PSM-F-25 — `_synchronize_to_moves` rewrites the move in place, gated on ten fields.**
`$V18E/account/models/account_payment.py:949-955`, trigger list `:996-999`: `date, amount, payment_type, partner_type, payment_reference, currency_id, partner_id, destination_account_id, partner_bank_id, journal_id`. **UNIT: field name. COUNT = 10.**
It **drops all existing write-off lines** (`:976-977`) and rewrites with `'name': '/'` to permit renumbering (`:985`).
**Consequence:** editing any of ten fields on a payment silently destroys and re-creates the counterpart lines of its posted journal entry, including any manual write-off, and re-opens the entry's name for renumbering. That is a mutation of posted accounting driven by a field edit.

**PSM-F-26 — `unlink` force-drafts and deletes the move.**
`$V18E/account/models/account_payment.py:920-927` — `self.move_id.filtered(lambda m: m.state != 'draft').button_draft()` then `self.move_id.unlink()`.

**PSM-F-27 — `_seek_for_lines` classification is heuristic, with a salvage branch.**
`$V18E/account/models/account_payment.py:244-258` — lines are sorted into liquidity/counterpart/writeoff by account membership and account type, treating `company.transfer_account_id` as a counterpart; and when neither liquidity nor counterpart is identified, a lone write-off line is reassigned into the empty slot (`:254-258`). **The structural meaning of a posted entry is re-derived by inspection each time it is read**, rather than being recorded.

## 8. Employee payment — a second, divergent settlement model

`$V18E/hr_expense/models/hr_expense_sheet.py:746-773` — the move is created **first**, then injected as `move_id` into the payment vals, then the payment is created. This is the reverse of PSM-F-05.

`$V18E/hr_expense/models/account_payment.py:13-18` replaces `outstanding_account_id` with the expense destination account. **The account-determination chain documented in the Event-to-GL Matrix does not hold on this path.**

**PSM-F-30 — Expense-linked payments are frozen, and the freeze list contains a defect.**

**Consequence: `journal_id` and `ref` are NOT in the protected set.** The journal of an expense-linked payment can be changed without hitting the guard. **UNIT: intended field names 12; actual set members 11, one malformed.**
**Classification: CONFIRMED DEFECT** — directly observable from the source, no interpretation required. Whether it is known upstream is undetermined (no changelog in the evidence root).

**PSM-F-31 — Payroll widens the valid counterpart account types by context flag.**

**Consequence:** the set of accounts a payment may settle against is **context-dependent**, and the context is supplied by a button in a view. `_seek_for_lines` classification (PSM-F-27) therefore differs by entry point.
**DENOMINATOR:** PATTERN `hr_payroll_payment_register` over `$V18E`, py+xml, excluding `/i18n/`. **RESULT = 5** — 2 tests, 2 consumers, 1 view producer.

**PSM-F-32 — Payslip `paid` is set on a whole-move residual test.**

## 9. Target-design requirements arising from this file

| ID | Requirement | Arises from |
|---|---|---|
| PSM-R-01 | The four states must be **four separately written fields**, each with a recorded writer and timestamp. None may be computed from another. | PSM-F-00 |
| PSM-R-02 | A `paid` state must carry the **reason** it became paid (bank-matched / invoice-derived / non-reconcilable account). | PSM-F-03 |
| PSM-R-03 | A first-class **bank confirmation** fact must exist, settable only by an ingested bank event, never by configuration. | PSM-F-04, PSM-F-04a |
| PSM-R-04 | An explicit **transition table** with guards; `rejected` and `canceled` must carry distinct, recorded causes. | PSM-F-06 |
| PSM-R-05 | Settlement must never be asserted on a document while its ledger residual is non-zero. | PSM-F-13 |
| PSM-R-06 | Duplicate-payment detection must be **blocking**, must cover in-flight payments, and must use one consistent state set at every call site. | PSM-F-19, PSM-F-20 |
| PSM-R-07 | Internal transfer must be a **paired object** with a proof that both legs are captured and the transit account nets to zero. | PSM-F-24 |
| PSM-R-08 | Editing a settled payment must not silently rewrite its posted counterpart lines. | PSM-F-25 |
| PSM-R-09 | Account determination must not be overridable by module or by view context. | PSM-F-29, PSM-F-31 |
| PSM-R-10 | The meaning of "paid" must be **edition-independent**. | PSM-F-11 |
