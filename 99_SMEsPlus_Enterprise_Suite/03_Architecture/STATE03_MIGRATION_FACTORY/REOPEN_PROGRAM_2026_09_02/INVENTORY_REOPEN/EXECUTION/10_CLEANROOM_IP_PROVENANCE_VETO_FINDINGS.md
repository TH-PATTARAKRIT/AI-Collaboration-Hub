## 1. Mandate and Method

Track 08 (Clean-Room / IP / Provenance VETO) does not evaluate whether Inventory's functional-design conclusions are substantively correct, nor whether the wider evidence chain is properly governed and traceable — those are other tracks' mandates. Track 08's own mandate is narrower and specific: **clean-room boundary, source boundary, license/IP, contamination, and provenance** — whether source ERP (Odoo-family) models, routes, workflows, or literal code have leaked into SMEsPlus target semantics; whether the Boss-ordered `bh_*`/`bhpro_*` source-learning exclusion is being honored; whether vendor-specific features are being treated as universal business truth; whether source field/model identity is leaking into canonical SMEsPlus semantics; and whether raw source and customer data are being handled and preserved correctly.

Two bodies executed this identical mandate in parallel, independently, per the Council Charter's Anti-Groupthink Rule:

- **Council (challenge)** — treated every prior "clean-room: intact" self-certification as a hypothesis to re-test, not a fact to inherit, via three independent passes: (1) a content-level `git grep` for `bh_`/`bhpro_` across all six branch tips from CORR-005 through CORR-007B, restricted on a second pass to each round's own newly-authored files only, to isolate whether *new* work reintroduced excluded content; (2) a line-by-line read of the highest clean-room-risk technical documents — the N-A12-01 proof package, the Route/Procurement/Replenishment evidence (A6), the Product/UOM classification evidence (A5), the Database/Dump Forensic Register (A2), and the Clean-Room Classification and Quarantine Register (A17); (3) an independent `git merge-base --is-ancestor` check against canonical `origin/SMEsPlus` for CORR-006, CORR-007A, and CORR-007B, rather than accepting a prior round's non-merge claim at face value.
- **Special Team (investigation)** — ran its own independent `git grep` sweep for `bh_`/`bhpro_` across the 28 files newly added across CORR-006, CORR-007A, and CORR-007B, plus a `diff` of the A17 quarantine register between DR-002/CORR-005 and the CORR-007B tip; and — beyond the `bh_`/`bhpro_` question — a signature-based sweep for Odoo Python idioms (`@api.depends(`, `def _compute_`, `fields.Selection(`, `class ProductCategory`, literal `return self.product_id.` expressions) combined with a fenced-code-block presence check, run across every distinct-content branch tip from DR-002 through CORR-007B.

Neither body had access to the other's output while working. This document is the first point at which the two are read side by side.

### 2.3 Where the two bodies diverge — and why this is a real conflict, not just asymmetric coverage

Both bodies also independently identify the **same artifact** — CORR-007B's N-A12-01 Account-led Inventory Period Close / Product Category Valuation proof package, files `08_CORR007B_N_A12_01_ACCOUNT_LED_INVENTORY_PERIOD_CLOSE_FUNCTIONAL_DESIGN_PROOF.md` and `09_CORR007B_PRODUCT_CATEGORY_VALUATION_FUNCTIONAL_DESIGN_REVIEW.md` — as the single highest clean-room-risk material in the entire chain, and both agree CORR-007B's own dedicated Clean-Room Compliance Review (`12_CORR007B_CLEAN_ROOM_COMPLIANCE_REVIEW.md`) failed to catch what each of them separately found there (see §3.3). That much is genuine, independent corroboration — including both bodies independently quoting file 12's own self-description of N-A12-01 as *"high-risk for clean-room drift."* What is **not** corroborated is what, specifically, is wrong with files 08 and 09, or how serious it is.

**Council's finding is about language.** Reading file 09 §7, file 08 §12, and file 08 line 325, Council found phrasing that drifts from descriptive ("this is what the reference system does") toward prescriptive ("SMEsPlus must do this") — most pointedly file 09 §7's line: *"SMEsPlus functional design must use the location-based model actually present in source, not the category-based Input/Output model from the screenshot."* Council also flags file 08 §12's table, titled "Accounting x Inventory Close Contract," as describing Odoo's own module-ownership boundaries under a target-sounding name without an explicit reference-only qualifier in the heading itself, and file 08 line 325's phrase "whether SMEsPlus's reference source supports..." as linguistically conflating target and reference. Council's own verdict on this finding is that it is a **material caution**: correctable by rewriting or re-qualifying the specific lines as descriptive fact, recommended as a **named precondition on a future Team B kickoff**, but not itself grounds to hold the chain today, since nothing has merged and Team B has not yet read it.

**Special Team's finding is about literal code.** Reading a different set of sections in the same two files — file 08 §17 and file 09 §2–3 — Special Team found verbatim, fenced-code-block reproductions of actual Odoo Python source: the full body and decorator of `_compute_valuation()`, the complete `property_valuation` field declaration including its exact Selection values (`'periodic'`/`'real_time'`) and multi-line help-text docstring, and the full boolean return expression of `_should_create_account_move()` (`stock_account/models/stock_move.py:630-635`). Special Team's own verdict on this finding is that it is a **regression against the project's own written standard** — A17, authored in DR-002 on 2026-08-31 and self-scored `VERIFIED`, states in its own text: *"No vendor source code body, ORM class definition, or schema DDL was copied verbatim into any A0-A20 deliverable — every citation is `file path -- Class.field_or_method_name`, not a code block reproduction."* Special Team independently confirmed that standard is in fact honored in A3, A4, A5, A7, and A9 (zero fenced code blocks anywhere in those files, checked directly) and in the other 26 files newly added across CORR-006, CORR-007A, and CORR-007B. Files 08 and 09 are, on Special Team's sweep, the **only two files anywhere in the nine-branch chain** where the standard is not honored. On this basis, Special Team's verdict is `HOLD`: files 08 and 09 must be remediated to the project's own citation-only standard **before** Team B or Team C are authorized to read this evidence for any N-A12-01 design work.

These two findings are not a factual contradiction. Council's narrative never asserts there are no fenced code blocks in files 08/09, and Special Team's narrative never asserts there is no prescriptive language there either — each body cites different section numbers and never engages with the other's specific citation. Read one at a time, each looks like a single, containable finding. **Read together, they describe more risk in the same two files than either finding shows on its own:** a document that both drifts toward prescriptive framing of the reference system's structure *and* separately reproduces that system's literal source code is a more serious clean-room exposure than either defect alone. The fact that Council's own dedicated read of these exact two files did not surface the code-block issue — and Special Team's did not independently confirm or rule out the language issue — is itself the reason this document treats the disagreement as real rather than as one body simply being more thorough. This is precisely the scenario the dual-review, anti-groupthink structure exists to surface, and precisely why this document does not adjudicate which reading is dispositive on its own authority.

**This document does not determine which finding is "more correct."** Doing so would require an independent third re-read of files 08 and 09 against both claims, which is outside this document's own method — a convergence of two existing findings sets, not a fresh forensic pass. What this document does instead is what it is required to do: state the conflict explicitly, and reconcile the track verdict to **`HOLD`** rather than to either `CONTINUE_WITH_NOTES` or a freestanding `HOLD` selected without acknowledging the disagreement. §7 recommends a specific tie-breaking action.

## 3. Detailed Findings

### 3.1 Provenance hygiene: a shared-worktree collision pattern — Council finding, not addressed by Special Team's Track 08 pass

Council located a disclosed (not discovered) incident in CORR-007B's own session-closure record: the branch's git working directory was shared with a concurrent Accounting/WHT session, and two collisions resulted. First, a foreign Accounting/WHT commit briefly landed on the Inventory branch by race condition; it was corrected via cherry-pick to its correct branch before either side pushed. Second, two concurrent sessions independently used overlapping file numbers for their own addendum-5 responses; this was resolved transparently via a renumbering and cross-reference index (file 16), with no file deleted. Both incidents were self-disclosed rather than discovered by Council's own review, and neither altered any evidentiary finding or disposition.

Council frames this explicitly as adjacent to, rather than squarely inside, this track's core clean-room boundary — it is a **provenance-integrity** finding, not a source-contamination one — which is presumably why Special Team's own Track 08 pass, focused more tightly on the `bh_`/`bhpro_` exclusion and the technical evidence base, did not independently surface or address it. Nothing in Special Team's material disputes this finding; it simply is not covered there. Council's own recommendation is that the underlying pattern — concurrent AI sessions sharing insufficiently isolated git working directories — should prompt a standing instruction for isolated worktrees/branches across Inventory, Accounting, and Joint reopen sessions going forward, rather than relying on after-the-fact self-correction each time it recurs.

### 3.2 Source field identity firewalling: `purchase_request_id` — Special Team finding, not addressed by Council's Track 08 pass

Special Team examined `01_CORR007B_GRPA_M15_PURCHASE_ORDER_LINE_DRIFT_PROOF.md` and found a clean example of source field identity being correctly firewalled from canonical SMEsPlus semantics rather than adopted by default: the legacy `purchase_order_line.purchase_request_id` column is explicitly and correctly recommended **not** to be carried forward as an active SMEsPlus business field. The document's own §4.4 disposition — *"Do not carry `purchase_order_line.purchase_request_id` forward as an active SMEsPlus business field... Controlled carry-forward (not a blocker)"* — treats the column as a migration/legacy-data fact only, never as target schema.

Council's item-classification list does not separately address this specific field, and its key findings do not mention `GRPA-M15` by name. This is not a contradiction — nothing in Council's material disputes the finding — it is simply outside what Council's own pass happened to examine in this level of detail; it is carried forward here at full weight on Special Team's evidence alone, consistent with how this document treats every single-body finding in this track.

### 3.3 The clean-room self-review control gap — both bodies converge, independently

Both bodies conclude that CORR-007B's own internal clean-room control mechanisms were not adequate to catch what this convergence pass, reading the two bodies together, now surfaces. File 12 (`CORR007B_CLEAN_ROOM_COMPLIANCE_REVIEW.md`) correctly names N-A12-01 as "high-risk for clean-room drift" in the abstract and correctly concludes the package is not yet clean-room functional-design-closed — but, as file 16 §3 itself concedes in language both bodies independently quote, file 12 "does not check specific citations in files 01-09/14/15 against those principles." In other words, CORR-007B produced a clean-room **policy restatement** of its own four governing principles, posed as abstract challenge questions, rather than a clean-room **audit** that walks the actual technical citations in files 08 and 09 against those principles line by line. Special Team adds that the round's own internal challenge brief (`11_CORR007B_9_SPECIAL_TEAM_CHALLENGE_REPORT.md`) names a "Lead Code & UI Architect — clean-room boundary" role among its nine challenge capacities but never discharges it as its own separate, independently-reported deliverable; its output folded into the same principle-level file 12 instead.

Both bodies independently recommend the same fix: a future round's self-declared clean-room compliance review should be paired with a mechanical, citation-level sweep — not principle-restatement alone. This convergence document's own §2.3 is, in effect, the first time such a citation-level pass has actually been run against files 08 and 09 specifically for fenced-code-block content, and it was Special Team's method, not file 12's own self-review, that caught it.

### 3.4 A plausible mechanism for the N-A12-01 regression — Special Team's own hypothesis, not independently confirmed by Council

Special Team offers a specific, evidence-grounded explanation for why the citation discipline that held everywhere else in the chain did not hold in files 08 and 09: both documents were produced under direct, repeated pressure. File 09 itself opens by noting that Boss's addendum rejected the prior N-A12-01 proof as "still insufficient," and CORR-007B's own text records Boss personally challenging the N-A12-01 disposition across five rounds before a final "HIGH FUNCTIONAL DESIGN GAP — REOPENED" label was set. Special Team's reading is that, under pressure to produce maximally granular, irrefutable mechanism proof, the citation-only discipline that held in every other document in the chain broke down into literal excerpting specifically in the two files addressing the most contested item. This is offered as a plausible mechanical explanation, not as an independently re-confirmed fact — Council's own material does not address or dispute this causal account, having focused on the language dimension rather than the code-block dimension of the same two files.

### 3.5 Canonical exposure — zero, confirmed independently by both

Both bodies ran `git merge-base --is-ancestor` directly against a freshly-checked `origin/SMEsPlus`, rather than accepting a prior round's summary, and both confirm CORR-006, CORR-007A, and CORR-007B are each `NOT-MERGED`. Canonical's own `bh_`/`bhpro_` hits are limited to prompt files quoting the Boss ruling itself, plus baseline module-scan CSVs unchanged since before any corrective round — no drift beyond the original DR-002/CORR-005 baseline, confirmed by Council. Team B (Inventory Design) is explicitly and repeatedly stated as not authorized throughout the chain, most recently and explicitly in CORR-007B's own file 13.

## 4. Clean-Room Impact Statement

**Clean-room impact: MIXED — NOT YET PRODUCT-CONTAMINATING, BUT ACTIVE AND UNRESOLVED AT THE EVIDENCE LAYER.**

On this track's own owned checklist item — the Boss `bh_*`/`bhpro_*` source-learning exclusion — clean-room impact is **none**. Both bodies independently and rigorously confirm zero violation, with unusually strong corroboration: near-identical file universes, checked independently, by different methods, returning the identical zero-hit result. Elsewhere in the reference-evidence base — the Odoo stock-routing/procurement engine (A6), the product-classification gate (A5/A17), and raw source/customer data handling (A2) — clean-room impact is also **none**: evidence throughout is properly source-vs-target labeled, and no vendor logic, schema, or row-level customer data has been adopted, retained, or transmitted as if it were SMEsPlus's own.

At the specific N-A12-01 package (CORR-007B files 08 and 09), clean-room impact is **not zero and not resolved**. Council's read finds boundary-adjacent prescriptive language drifting toward treating the reference system's own structural choices as SMEsPlus design directives. Special Team's read finds literal, verbatim Odoo Python source-code reproduction — full method bodies, decorators, and a complete field declaration with its exact enum values and docstring — that breaches the project's own explicit, previously self-verified citation-only standard (A17, DR-002, self-scored `VERIFIED`). Both bodies agree this has **not** propagated to the actual SMEsPlus product or design: Team B and Team C remain unauthorized, nothing has merged to canonical, and no SMEsPlus schema or design document exists yet that could have inherited anything from either defect. There is no confirmed downstream contamination today.

But the evidence-layer exposure is real, it sits directly in the path a future Team B author will read first once N-A12-01 unblocks, and the two reviewing bodies disagree — not on the facts each cites, but on how serious the combined picture is and what must happen before that reading takes place. Because of that unresolved disagreement over the highest-risk artifact in the entire chain, this document cannot honestly report "clean-room impact: none" for Track 08 as a whole, the way it can for every other item examined. The accurate statement is: clean-room impact is contained to the evidence corpus, not the product, but is specifically unresolved between Council and Special Team — which is precisely why the reconciled Track 08 verdict is `HOLD` rather than `CONTINUE_WITH_NOTES`.
