## 1. Mandate and Method

Track 09 (AI Control / Automation / Human Oversight VETO) does not evaluate whether Inventory's technical or functional-design conclusions are correct — that is the province of other tracks (Track 02/TBRAC for Thai business fitness, Track 03/06 for functional design and the standing `N-A12-01` HOLD, Track 01/Audit for evidence and governance currency). Track 09's own mandate is narrower and forward-looking: **AI authority, the deterministic-control boundary, explainability, escalation, and human override** — given that SMEsPlus's own migration execution will be AI-orchestrated, which decisions may an AI agent infer or propose, and which stock, provenance, and reconciliation controls must instead be fixed, replayable, and human-approved rather than left to a model's judgment at run time.

Both bodies that produced the inputs to this document independently confirm this mandate is **genuinely new to this reopen**. `INV-DELTA-08` states plainly that "AI Control, Security and Clean-room are now independent Veto mandates," and both bodies checked this empirically rather than taking the delta trigger's word for it: DR-002's own Amendment Section 4/5 mandatory-coverage checklist — the twenty-two-domain table inside `A15_MATERIAL_UNKNOWN_EXHAUSTION_REPORT.md` — contains no AI-authority or deterministic-control-boundary domain anywhere in it. Every round from DR-002 through CORR-007B answers "what does the Odoo reference system do," never "what will SMEsPlus's own AI-orchestrated migration and reconciliation pipeline guarantee deterministically, and where is AI permitted to infer." Nothing in the prior nine-round evidence chain should be read as having already closed this track's question; on the evidence available to both bodies, it was never asked before this reopen.

**This document itself does not re-run that git/source forensic work.** The Council (challenge) and Special Team (investigation) findings converged here were each already-completed, independent passes — the Council's against a specific set of branch tips (`audit/inventory-core-corr007b-3high-closure-010` and its ancestors: DR-002 `b31597fa`, CORR-005 `d69da790`, IDR-007 `ed26918a`, CORR-006 `46a84837`, CORR-007A `deceb733`, CORR-007B `0eb78c68`), the Special Team's as independent primary-source verification of the same underlying evidence base, including its own direct re-extraction of the `N-A13-02` conditions from CORR-005's own text and its own full-tree repository search confirming no migration/ETL code exists anywhere. This document holds both sets of claims faithfully, attributes each to "Council" or "Special Team" as reported, cross-checks them against each other for agreement and disagreement, and — for a small number of load-bearing facts (the RACI matrix's actual version/status header, the STATE02 escalation document's filename, `MIGRATION_PLAN_v0.1.md`'s existence and placeholder status) — spot-confirms them directly against the files present in this worktree. It does not independently re-derive either body's underlying git forensics from scratch.

### 2.2 Is this a factual contradiction, or a difference in how the same facts were weighed?

A mismatched verdict label is not by itself proof of a substantive disagreement — two blind reviewers can reach different headline labels while agreeing on every fact examined, or they can genuinely contradict each other on a specific claim. This document checked which is true here before reconciling, the same two-level way Track 01's convergence did for its own (matching) verdicts.

**Level 1 — did the two bodies contradict each other on any specific claim they both examined?** No instance was found. Reading the two findings sets item by item (§3, §5): both independently conclude the source reference system has no unified idempotency-key mechanism (near-identical wording, both citing DR-002's own "PARTIALLY SUPPORTED not VERIFIED" rating); both independently re-extract the identical `N-A13-02` tenant-isolation conditions from CORR-005's own text, down to the same "16-model company-scoped rule table" and the same unaudited ORM-vs-`sudo()` residual; both independently reach the same conclusion about the AI Skill RACI Matrix (unapproved draft, no Migration Factory role) and the STATE02 escalation ladder (sound, but not built for per-record AI decision-routing); both independently credit the same two positive process precedents (DR-002's honest sandbox-block disclosure; CORR-007B file 14's honest single-session-not-independent-panel disclosure); and both independently — without prompting from each other — raise the identical concern about whether this very reopen's own 9-Council/9-Special-Team structure is genuinely parallel or a re-run of the same single-session pattern. Nowhere does one body assert a fact the other body's own evidence contradicts.

**Level 2 — did the two bodies cover the same ground?** Not fully, and the asymmetry is real, though additive rather than adversarial (detailed in §3 and carried at full weight into §5 and §6):

- **Council alone** identified that Product Category, not product or company, is the source system's actual valuation-policy owner (CORR-007B file 09), and that this makes AI-driven category assignment at migration time a high-stakes, non-cosmetic control decision with no governance gate defined anywhere — Council's own text calls this "a new synthesis, not previously drawn anywhere in the chain."
- **Special Team alone** identified `G-5` (the migration-cutover first opening balance) as having no reference mechanism in the source system at all, and named it "the single highest AI-fabrication-risk point in the whole Inventory scope."
- **Special Team alone** ran a full-text search of the entire CORR-006/CORR-007A/CORR-007B closure package for the words "idempotency" and "replay" and reports zero hits despite `INV-DELTA-07` naming exactly this question as a reopen trigger — a specific, reproducible verification Council's own narrative describes in substance but does not report having executed as a literal search.
- **Special Team alone** verified by full-repository search that no migration/ETL/transformation code exists anywhere in the repository and that `MIGRATION_PLAN_v0.1.md` is an explicit, unauthored placeholder — a fact this document independently spot-confirmed (§1) and that reframes every other finding as a specification gap for a system that does not yet exist, not an audit of a running system's misbehavior.
- **Special Team alone** surfaces that the source system's `combo` (kit/bundle) product type has no obvious home in Boss's own proposed three-way Stockable/Consumable/Service target-routing hypothesis — a concrete edge case inside a question Council also treats as open but does not itself name at this level of specificity.
- **Council alone** frames the mandate's overall answer as "entirely unanswered," a stronger and more categorical statement than Special Team's "the skeleton does not yet exist," even though both are describing the same underlying absence of a target-side AI-governance design.

None of these six items contradicts anything in the other body's material. This is coverage asymmetry, not contradicted fact — structurally the same finding Track 01's own convergence reached about its own (matching) verdicts, and the same conclusion this document reaches about Track 09's (mismatched) ones.

### 2.3 Why the reconciled verdict is `HOLD`

Because no specific factual contradiction was found, the two bodies' underlying evidence and even their own recommended next actions converge almost completely — both want the same gaps (idempotency, provenance, tenant-isolation residual, UOM rounding, generalized exception-escalation procedure, AI-execution clean-room control) named as explicit, evidence-cited **preconditions** rather than closed by omission or left as background hardening work. Read charitably, the verdict-label difference looks less like a factual dispute and more like a difference in how urgently to phrase the same underlying gap: Council's `HOLD` attaches to any Team B design authorization that would touch AI-assisted migration mapping, classification, or reconciliation; Special Team's `CONTINUE_WITH_NOTES` attaches to the investigation itself continuing, while its own preconditions bind at the point of "any future authorization of AI-orchestrated migration execution" — a later gate than Team B design.

That reading would be enough to reconcile toward `CONTINUE_WITH_NOTES` on its own. But the instruction governing this document is explicit and is treated as binding here: **when two independently-produced verdicts conflict, this document must say so and mark the track `HOLD` rather than arbitrarily picking one.** That rule exists precisely for situations like this one, where a plausible interpretive bridge between the two labels exists but the labels themselves still disagree — the bridge is an inference this document is making after the fact, not something either body itself asserted, and Boss should see the raw disagreement rather than only this document's smoothed-over reading of it. Accordingly, the reconciled Track 09 verdict is **`HOLD`**, on the strength of the stated reconciliation rule and independently reinforced by the substance: seventeen paired AI-authority and deterministic-control items (§3, §5), only a small number of which either body classifies as closed, sit against a system that — by Special Team's own independently-verified fact — does not yet have a single line of migration code or a completed migration plan to design those controls into. This is not a verdict on the reopen's substantive technical progress, which is Track 03/06's territory; it is a verdict that Track 09's own specific material question is not yet answered by either body's own account, and the fact that the two bodies chose different words to say so is itself part of what Boss is being shown, not a discrepancy this document is entitled to erase.

## 3. Detailed Findings

### 3.1 The design context: an already-decided AI-orchestrated Migration Factory, and a specification that does not yet exist

Special Team's investigation adds a framing point Council's own material is consistent with but does not state as directly: Boss has already committed the target migration architecture to an **AI-orchestrated Migration Factory** (`INV-DELTA-07`; the parallel Joint-reopen prompt's own instruction to "deeply investigate the desired AI-orchestrated Migration Factory at the joint boundary"). Track 09's question is therefore not whether AI should be used in migration — that is already decided — but exactly where the deterministic line sits inside a process that will be AI-orchestrated by design. The Council 09 charter's own operative invariant, quoted in Special Team's narrative, states the target relationship precisely: *"AI may assist, detect, recommend, challenge and explain; deterministic controls must not rely solely on probabilistic AI."*

Against that already-decided target, Special Team independently verified — by full-repository search on both canonical `origin/SMEsPlus` and the controlling CORR-007B branch — that **zero migration, ETL, or transformation code exists anywhere**, and that `99_SMEsPlus_Enterprise_Suite/01_SaaS_Foundation/SDS/MIGRATION_PLAN_v0.1.md` is an explicit, unauthored placeholder. This document independently spot-confirmed the file exists at that path in this worktree. Council's own material is consistent with this — it separately notes "no EXPERT_IDTM execution has ever run against Inventory (only the charter/decision doc exist)" — without reporting the same literal full-repository grep. Every finding in §3.2–§3.4 below is therefore a forward-looking control-boundary specification for a system that has not yet been built, not an audit of a running system's observed misbehavior. Both bodies are explicit that this absence of code is itself a clean negative finding, not a defect in either track's own research.

### 3.2 The A13 Register and the missing EXPERT_IDTM execution: evidenced candidates, zero ratified controls

Council identifies `A13_CROSS_DOMAIN_INVARIANT_CANDIDATE_REGISTER.md` as the closest existing artifact to a deterministic-control specification, and both bodies draw on it extensively — while both are careful to preserve its own explicit self-limitation: it is headed "research candidates... not proven SMEsPlus invariants and not executed tests," reserving formal test-matrix execution for `EXPERT_IDTM`. Ten candidates are named there, spanning almost exactly Track 09's own checklist: quantity conservation, unauthorized-mutation prevention, replay/duplicate protection, on-hand consistency, tenant isolation, lot/serial consistency, valid state transitions, cross-domain provenance, and Inventory-to-Accounting reconciliation identity.

Council's independent verification — consistent with, though not identically phrased by, Special Team — is that every one of these ten candidates remains **unenforced at the database layer** in the reference system, and **none has been converted into a ratified, tested target-side SMEsPlus control**. No `EXPERT_IDTM` execution folder exists anywhere in git history for Inventory; only the charter and a Boss appointment decision exist. The register is exactly what it says it is: a list of candidates, not a list of controls. This status — real, evidenced, honestly self-labeled, and unchanged since it was written — is itself the foundation for nearly every deterministic-control finding in §3.4 below.

### 3.3 The eight AI-use surfaces

Both bodies independently organized their investigation around the same eight decision surfaces where an AI-orchestrated migration would have to act: source classification, product-type/category mapping, warehouse/location mapping, lot/serial/package mapping, exception classification, duplicate/anomaly detection, migration transformation, and reconciliation explanation. Read together, a consistent pattern holds across nearly all eight: the **source-side facts are well-evidenced** (both bodies cite the same primary artifacts — `A5`, `A12`, `A17` — for what the reference system actually does), but **no target-side AI-governance design exists for any of them** — no approval gate, no confidence threshold, no escalation rule. Both bodies treat that absence as genuine white space rather than a defect in prior rounds, consistent with §3.1: nothing has been built yet for the gates to attach to.

**Source classification.** Both bodies confirm the source's product-classification mechanism is a compound, partly-mutable two-field gate — `product.template.type` (`consu`/`service`/`combo`) plus a computed-but-overridable `is_storable` boolean, forced `False` whenever `type != 'consu'` (`A5` Section 4) — not a clean three-value tag. Council frames the open question as whether an AI migration agent may freely infer the target classification per legacy record or must apply a locked, human-approved rule table; Special Team frames the same open question as a boundary requirement for a not-yet-built classification engine, with an explicit worked constraint: classifying a real customer row must be a proposal against a deterministic rule table with mandatory human review, never a live per-row model call at migration run time.

**Product type / Product Category mapping — where the two bodies' coverage diverges most, and most productively.** This single heading covers two distinct, high-stakes findings, one from each body, neither disputed by the other:

- **Council's finding**, explicitly labeled a new synthesis not previously drawn anywhere in the evidence chain: CORR-007B's own file 09 proves — via a fully-cited compute method with explicit precedence (a company-dependent `property_valuation`/`property_cost_method`, category value wins if set, else company default) — that **Product Category, not product and not company, is the source system's true owner of costing method and valuation policy**. An AI-driven migration's category-assignment decision for each legacy product is therefore not cosmetic data mapping; it silently determines every future GL posting for that item — Standard, FIFO, or AVCO costing; Periodic or Perpetual valuation — for the life of the record. No rule-bound, human-reviewable gate for that specific migration decision exists anywhere in the evidence produced so far.
- **Special Team's finding**: Boss's own proposed three-way Stockable/Consumable/Service target-routing hypothesis does not have an obvious home for the source's `combo` type (kits and bundles) — a bundle is not itself a stock-holding item, but its components may be, and none of the three named target buckets cleanly fits it. This is a concrete, previously-unflagged edge case inside a question (`INV-FP-13`) both bodies otherwise agree remains genuinely open and unproven against Thai business reality, with its own designated deliverable (`12_STOCKABLE_CONSUMABLE_SERVICE_DEEP_PROOF.md`) confirmed by Council not to exist anywhere in git history yet.

Read together, these are two different failure modes on the same underlying field: one is a **silent-misclassification risk** (an AI agent picks a plausible-looking category and gets valuation policy wrong without anyone noticing), the other is an **undefined-target risk** (an AI agent has no correct bucket to put a `combo` product in at all). Both belong in the same control design.

**Warehouse/location mapping.** Both bodies confirm warehouse configuration in the source system is a route-graph *generator*, not static data (`A12` Section 2; Special Team additionally cites `SAAS-04` and the two-branch-concept company/tenant resolution problem from `A10`) — a migration must either regenerate the route graph in target terms or explicitly map all seven `stock.location.usage` values (`A5` Section 1). Both conclude no target design or AI-authority rule for making that choice exists yet; Special Team adds the specific requirement that any AI-proposed location/route mapping be published as a reviewable, versioned rule set approved once by a human, then applied deterministically thereafter — never regenerated by inference per tenant.

**Lot/serial/package traceability mapping.** Both bodies confirm package history is a separate, frozen, append-only snapshot distinct from a possibly-reused live package row (`A12` Section 3), and that expiration and consignment handling remain explicitly unresearched. Special Team adds a specific citation Council's material does not name directly: `A13` candidate #6 (a tracked product's move-line lot/serial should match the product's own tracking setting) is a plausible invariant that is not database-enforced and has never been tested against real dump data — exactly the kind of field where AI fill-in risk is highest, requiring a hard reject/quarantine rule rather than a best-guess fill.

**Exception classification.** Both bodies point to the same single detailed worked example: `GRPA-M15` (`purchase_request_id`, CORR-007B file 01), triangulated across a dump foreign-key constraint, the module registry, and a fresh full-tree source grep, with its unresolved residual honestly handed to a named downstream owner rather than silently resolved by inference. Both agree this is genuinely good practice and genuinely singular — nothing in the evidence generalizes it into a decision procedure for the much larger volume of ambiguous fields a real Migration Factory run will encounter, and no materiality or reversibility threshold is defined anywhere for when an exception may be auto-resolved versus must halt for human review.

**Duplicate/anomaly detection.** Both bodies cite the same underlying facts (`A13` candidates #3 and #10: no unified idempotency-key mechanism; no DB-level enforcement against negative quantities, over-fulfillment, or duplicate quant bins). Special Team adds a positive existing precedent Council's material does not develop in the same terms: the source system's own deduplication mechanism, `_merge_quants()`, is deterministic code, not inference — and recommends the target design follow the same shape, where AI may flag *candidate* duplicates or anomalies for review, but the merge or resolution action actually applied to stock data must be deterministic, rule-following code with a full pre/post audit log, never an autonomously AI-executed merge.

**Migration transformation (general).** Both bodies point to the same foundational absence: `A12` Section 10 states the source provides no external-ID or provenance field on any `stock.move`, `stock.quant`, or `stock.picking` record — "a migration will need to introduce its own provenance/external-ID mapping layer." Special Team independently corroborates the *system-level* absence of any transformation logic at all (§3.1); Council's finding is the more specific one that even the *design* for this particular foundational layer does not exist, not even as a placeholder sketch — and this layer is precisely the infrastructure idempotency, replay protection, and reconciliation identity would need to be built on top of.

**Reconciliation explanation.** Both bodies point to `A13` candidate #9 (Inventory-to-Accounting reconciliation identity, registered as Cross-Proof Lane C scenario 10, a "mandatory future test" never executed because database restore was blocked throughout this chain). Special Team's independent contribution here is the sharper and more specific one: `G-5`, the migration-cutover *first opening balance*, is source-confirmed to have **no reference mechanism at all** — "not covered by any mechanism... not found in source; genuinely absent." Special Team names this "the single highest AI-fabrication-risk point in the whole Inventory scope" — an AI asked to explain why a migrated opening balance reconciles would have zero source ground truth to explain from, and would necessarily be arguing from a policy SMEsPlus itself must originate. This item does not appear under this name anywhere in Council's own material; it is carried forward here at full weight as a Special-Team-only finding, consistent with §2.2.

### 3.4 The deterministic-control checklist

Both bodies independently evaluated the same eight named deterministic-control requirements against the source system's own evidenced behavior. The pattern across all eight is close to uniform: a real, well-evidenced source-side mechanism exists (usually application-layer only), no equivalent target-side, database-enforced guarantee has been designed, and an AI-orchestrated bulk migration extracting via direct SQL or bulk APIs would bypass the source's own application-layer guardrails entirely and inherit exactly the gaps described below, unless SMEsPlus's own target schema closes them independently.

| Control | Source-side status (both bodies agree) | Target-side status (both bodies agree) |
|---|---|---|
| Quantity conservation | Single choke point, `_synchronize_quant()`; formula well-defined at 5-key bin granularity (product, location, lot, package, owner) | No DB CHECK constraint or trigger enforces it anywhere; not yet a database-guaranteed invariant in any target design |
| Source/target record counts | `_merge_moves()` can combine multiple originating moves into one record — cardinality is **not** guaranteed 1:1 | No documented, versioned expected-cardinality-transform table exists; a naive count-parity check would produce false-fail noise |
| Referential integrity | `stock_move_line.move_id` is `ON DELETE SET NULL`, not cascading/restricting; no CHECK constraints anywhere in the Inventory schema | No target-side referential-integrity migration-validation rule specified; direct-SQL extraction will encounter orphaned rows the application layer itself never produces |
| Tenant/company isolation | ORM-layer `ir.rule` enforcement confirmed comprehensive (16-model company-scoped rule table, `stock/security/stock_security.xml`) | Explicit, named, never-audited residual: whether every code path actually routes through the ORM versus a `sudo()`-equivalent bypass (ties to `SAAS-03`, no DB-layer backstop found anywhere) |
| UOM conversions | No `uom.category` model; convertibility inferred structurally via a self-referential `relative_uom_id` tree; rounding precision is global, not per-UOM | Filed only as a structural note for future design; never elevated to an owned, verifiable conversion-rule requirement |
| Idempotency / replay protection | "No single unified idempotency-key mechanism exists" (DR-002's own words); only quantity-remaining-based merge/no-op guards, rated PARTIALLY SUPPORTED not VERIFIED even for the source's own ordinary operation | No design exists for the migration pipeline; a full-text search of the entire CORR-006/CORR-007A/CORR-007B closure package for "idempotency" or "replay" returns zero hits |
| Source/target checksums | N/A — no migration-data checksum concept exists yet | No design exists for migration row/batch integrity specifically; the project's own SHA-256 evidence-manifest discipline (a fixed `shasum -a 256` command, not an AI-estimated value) is a directly reusable, already-working precedent both bodies recommend extending rather than replacing |
| Reconciliation identities | `A13` candidate #9 well-formed but never independently tested against real data (DB restore blocked); `G-5` opening balance has no reference mechanism at all (Special Team) | Must be defined as explicit, human-approved formulas before migration, computed deterministically and logged verbatim; AI's role limited to narrating an already-computed result, never computing or asserting the reconciliation itself |

Two items deserve individual emphasis beyond the table, because both bodies converge on them as the two highest-priority gaps in this entire checklist.

**Idempotency is the most acute, most strongly corroborated gap in the whole track.** DR-002's own words, unchanged through five corrective rounds, are that "no single unified idempotency-key mechanism exists." `INV-DELTA-07` — written for this exact reopen — names AI-orchestrated migration idempotency as a new, material trigger for reopening Inventory at all. Special Team's specific contribution is the reproducible verification that closes the loop: a full-text search of the entire CORR-006/CORR-007A/CORR-007B closure package for "idempotency" and "replay" returns **zero hits** in either round, despite five rounds of otherwise-detailed Boss challenge on other named items having passed through the same evidence. Council's independent narrative reaches the identical substantive conclusion — "carried unchanged through IDR-007/CORR-006/CORR-007A/CORR-007B without ever being re-tested, elevated, or resolved" — by a different route (comparing the finding's status across rounds rather than a literal grep). Both bodies treat "AI-orchestrated rapid migration implies retries, partial-batch reruns, and session restarts as normal operating conditions" as the reason this cannot be deferred: SMEsPlus needs a first-class, deterministic migration idempotency key checked before every write, independent of any model's judgment, so a retried operation can never double-apply a stock movement.

**Tenant isolation's `sudo()`-bypass residual is the other headline convergence, verified near-verbatim by both bodies independently re-reading the same source text.** `N-A13-02` is "VERIFIED WITH CONDITIONS" in CORR-005 for the *source* system only. Both bodies independently located and quote the identical condition directly from CORR-005's Five-High Reconciliation Matrix: ORM-layer `ir.rule` enforcement is comprehensive and closed, but whether every code path in `stock_account`/`sale_stock`/`purchase_stock`/`mrp` that touches company-scoped models actually routes through the standard ORM — versus using `sudo()` internally — was explicitly never audited, and there is no database-layer backstop at all if that trust is ever violated (`SAAS-03`). Both bodies draw the identical inference, independently: an AI-orchestrated bulk migration load is precisely the kind of operation that plausibly needs a privileged, `sudo()`-equivalent write path to seed cross-company data during initial load — which makes this specific, already-named, never-audited residual directly relevant to AI-authority design, not a peripheral security footnote. Both recommend the target design add a database-layer tenant boundary (not ORM-trust alone) plus a mandatory, automated post-write cross-tenant leakage audit.

### 3.5 Governance frameworks assessed: the RACI matrix and the STATE02 escalation ladder

Both bodies independently checked whether any pre-existing, project-wide AI-authority framework already governs this problem, and reached the same conclusion about the same two candidate documents. `SMEsPlus_AI_SKILL_RACI_MATRIX_v0.1.1` — spot-confirmed in this worktree at `99_SMEsPlus_Enterprise_Suite/00_Project_Governance/SMEsPlus_AI_SKILL_RACI_MATRIX_v0.1.md`, internal document version `v0.1.1`, header status `CLAUDE SKILL ARCHITECT CONTROLLER ADDED / CHATGPT L99 REVIEW REQUIRED / NOT APPROVED / NOT AUTOMATED YET` — is an unapproved draft scoped to Claude Skill-package governance (FDS drafting, review-prep packages, UAT generation) and contains no role at all for Migration Factory bulk-execution activity. `STATE02_ESCALATION_AND_REPLACEMENT_RULE_v1.0` — spot-confirmed at `99_SMEsPlus_Enterprise_Suite/00_Project_Governance/State_02_Governance/Step_04_Ownerless_Execution_Control/` — is, both bodies agree, a genuinely sound general escalation ladder (P0/P1/P2 clocks, Boss-only non-delegable Level 5 authority, an explicit anti-pattern list including "using owner inactivity to bypass Boss approval on non-delegable decisions"), but it is built for slow, human-owner-inactivity escalation on minute/hour/day clocks — not for a per-record AI decision-routing rule inside a bulk data pipeline that could process thousands of records in a single run. Neither document has been adapted to the actual shape of this problem, and both bodies are explicit that this is a finding about a real, current gap, not a criticism of either document for what it was designed to do.

### 3.6 Self-assessment: has the AI-driven evidence chain itself honored these controls?

## 4. Clean-Room Impact Statement

**No clean-room violation was found by either body in evidence produced to date.** Both bodies are explicit that their own review activity — reading already-committed evidence files and existing governance documents — introduced no source code, schema, or vendor architecture into any target artifact, and both ground their recommendations in business-fact and source-behavior citations already gathered under `A17`'s quarantine discipline ("evidence of business semantics only, never adoption of vendor schema/field/method names"), which this track reused rather than re-deriving. Every control this track recommends — an idempotency key, database-layer tenant isolation, a migration-data checksum discipline extending the project's existing SHA-256 manifest habit, human-approval gates on classification and reconciliation decisions, a deterministic UOM conversion table — is original SMEsPlus target-design guidance, not a port of Odoo mechanics; several explicitly reject copying the reference system's own gaps (its ORM-only tenant enforcement, its absent idempotency mechanism) rather than inheriting them.

**Both bodies independently surface the same forward-looking clean-room risk vector, one no other track's mandate is positioned to see, and both are explicit it is a risk to control for, not a violation that has occurred.** Clean-room discipline to date has rested entirely on human-supervised research: Team A analysts reading Odoo source and re-describing business facts in their own words, then re-verified independently. An AI-orchestrated Migration Factory executing bulk field-mapping and classification at run time is a fundamentally different risk surface. An AI agent inferring that a legacy structure "needs the same five-key quant-bin structure," "the same route-generation-on-write pattern," or "the same append-only package-history split" the reference system uses would be reproducing source **architecture** under cover of "necessary business-fact migration" — precisely what the project's Clean-Room Principles (Reference Only; No Copy/No Clone/No Reuse; Migrate Business Facts + Semantics Only; Target Design Must Be Original) forbid. No control of any kind — an automated pattern-match check, a mandatory human design review, or an explicit prohibition — has yet been specified to catch this specific failure mode at the point an AI migration agent actually proposes target structures, as distinct from the point a human researcher writes a citation-backed Markdown file.

The two bodies frame this identically-substantive risk with slightly different emphasis, worth preserving rather than flattening into one voice: Council calls it "a genuinely open clean-room gap... it should be a named requirement before any Team B design work that involves AI-assisted schema or mapping generation begins." Special Team frames it as "a forward-looking caution for Team B/C, not a finding of an existing violation," and adds a specific, actionable proposal: if the eventual Migration Factory's transformation logic is ever built by prompting a model with the reference system's own source code as context, the same quarantine discipline `A17` already applies to research documents must be extended to migration code itself — business semantics learned from source and target implementation code must stay in separate custody, with no source snippet, method name, or file structure crossing directly into generated SMEsPlus code. Both framings describe the same gap; this document preserves both rather than picking one, and both agree it should be a named requirement before Team B design work involving AI-assisted schema or mapping generation begins — not a finding that blocks anything that has already happened.
