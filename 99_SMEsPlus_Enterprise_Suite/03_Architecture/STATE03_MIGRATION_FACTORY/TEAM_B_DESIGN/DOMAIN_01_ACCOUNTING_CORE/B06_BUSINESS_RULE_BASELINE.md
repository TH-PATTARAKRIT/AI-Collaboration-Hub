# B06 — Business Rule Baseline

| Field | Value |
|---|---|
| Domain | DOMAIN_01 — Accounting Core |
| Phase | B6 — Business Rule Baseline |
| Method | Operationalizes B02–B05's capability/lifecycle/invariant design into checkable rules; starts from Team A's GR-01..13 but restates each against this domain's own design vocabulary (Entry, Posting, Consumption, Correction) rather than the reference system's |
| Vendor terminology | None below — every rule is stated in this domain's own conceptual vocabulary (B03 §2) |

## Rule Register

| Rule ID | Rule | Trigger | Precondition | Validation | Expected Outcome | Exception | Accounting Consequence | Audit Consequence | Evidence |
|---|---|---|---|---|---|---|---|---|---|
| BR-01 | A proposed Entry's total debit must equal its total credit before it can become COMMITTED | Posting attempted (CAP-02) | Entry is in DRAFT with at least one line | Σdebit(lines) = Σcredit(lines) | Posting proceeds to next check | Refused, with reason; entry stays DRAFT | Trial balance stays internally consistent | Refusal itself is a logged attempt (Audit Evidence) even though nothing committed | BINV-01, GR-01 |
| BR-02 | A Line carries a debit amount or a credit amount, never both | Line is written | Line is being added to a proposed Entry | credit × debit = 0 | Write succeeds | None — this is a structural constraint on Lines, not a business exception | Prevents nonsensical postings | N/A (pre-commitment) | GR-02 |
| BR-03 | A Line's functional-currency amount and transaction-currency amount must agree in sign | Line is written | Line carries a non-functional currency amount | sign(functional amount) = sign(transaction amount), or both zero | Write succeeds | None | Currency-consistency correctness (BINV-04a) | N/A (pre-commitment) | GR-03, BINV-04 |
| BR-04 | A financial (non-presentation) Line must reference an active account | Line is written | Line is not a presentation-only line | account reference present and account is active per CAP-01 | Write succeeds | Presentation-only lines are exempt | Traceability to the chart of accounts (CAP-01) | N/A (pre-commitment) | GR-04 |
| BR-05 | A transaction dated within an already-closed period must not be committed without an authorized, recorded override | Posting attempted | Entry date falls within a period CAP-04 reports closed | CAP-04's single authoritative answer is consulted | Refused unless an authorized override is separately recorded (B09) | Authorized, time-boxed, recorded override only — no code-level or configuration-level bypass path exists in this design | Period cutoff integrity (BINV-02) | Both the refusal and any override are logged | GR-05, BINV-02, ADV-03 |
| BR-06 | Correcting a COMMITTED Entry means posting a new Entry linked to the original; the original's content is never rewritten | Correction requested | Referenced Entry is COMMITTED | Correction Entry itself passes BR-01 through BR-05 like any other Entry | Two entries exist: original (now SUPERSEDED, B04 §2) and correction, permanently linked | None — this is the only correction path for a consumed Entry (see BR-07) | Strongest available audit-trail pattern (BINV-05) | Correction event logged; link is queryable in both directions | GR-06, BINV-05, ADV-04 |
| BR-07 | A COMMITTED Entry that has been consumed (B04 §4) must not be returned to an editable state or altered in place | Amendment or reopen requested | Entry is COMMITTED and CAP-08's Audit Evidence shows a Consumed event against it | Consumption status is checked, not assumed | Refused; BR-06 (Correction) is the only available path | An unconsumed COMMITTED Entry may still receive a logged in-place Amendment (BR-14) — this exception is deliberately narrow and closes the moment consumption is recorded | Prevents the domain's central identified weakness (BINV-06, CF-06) from recurring by design | The refusal itself, and every Amendment that occurred before consumption, are logged | GR-07, BINV-06, ADV-04, ADV-07 |
| BR-08 | An account's accounting category is fixed once the account has been referenced by any COMMITTED Entry | Category-change requested | Account has at least one COMMITTED Entry line | Usage check against the Ledger | Refused; a new account is required for reclassification going forward | Category may still be set/changed freely before first use | Prevents silent retroactive misstatement of prior statement placement (BINV-09) | Refusal logged | GR-08, BINV-09 |
| BR-09 | A foreign-currency transaction is recognised at the spot rate on its date; the resulting monetary balance is remeasured to functional currency at each reporting date | (a) Line written with non-functional currency; (b) reporting-date trigger fires | (a) valid rate available for the date; (b) balance exists in a non-functional currency | (a) rate applied at recognition; (b) CAP-06 remeasurement runs | (a) recognised amount recorded; (b) a Remeasured Entry is committed (B04 §3) through the normal Posting gate | No exception to (b) — this design does not treat remeasurement as optional or configuration-dependent, unlike the reference system's unevidenced status (ADV-08) | IAS 21 compliance (BINV-04b, RG-05) | Remeasurement is itself a committed, audited Entry | GR-09, BINV-04, RG-05 |
| BR-10 | Monetary values are represented with exact decimal precision at every step from recognition through remeasurement and reporting | Any monetary value is written | — | No binary floating-point representation is used at any point in the value's lifecycle | Values reconcile exactly to their components | None | Reliable financial totals (BF-02) | N/A (representation-level, not an audited business event) | GR-10, disagreement-02 (correctly scoped as a computing norm, not overclaimed as an accounting standard) |
| BR-11 | A financial fact tagged as belonging to a regulated document class (CAP-07) automatically carries that class's integrity/numbering guarantee — coverage is a property of the class, not an administrator setting | Entry is tagged with a regulated document class at Posting | Document class is one this domain has evidence for (currently: Thai e-Tax invoice/receipt, Thai tax invoice — RG-03/RG-04 only) | Class-appropriate integrity/numbering mechanism engages automatically | Coverage cannot be silently absent for an in-scope class | This rule does **not** extend to document classes or to the general ledger beyond what RG-03/RG-04 actually evidence (OQ-01) — no broader claim is made | Regulatory compliance for the specifically evidenced document classes (AO-02) | Tagging and coverage are both logged | GR-11, GR-12, CAP-07, AO-02 |
| BR-12 | A statutorily numbered document (currently: Thai tax invoice, RG-04) carries a genuinely sequential number without gaps | Entry tagged as a statutorily numbered document class is committed | — | Sequence assignment is atomic with commitment, not a separate step that could be skipped | Numbering is provably gapless for that class | None for the evidenced class; this rule is not extended to classes without evidence | Avoids audit flags for the evidenced class; makes no claim beyond it | Sequence assignment logged | GR-12, RG-04 |
| BR-13 | An account marked inactive/deprecated must not accept new activity through **any** posting path | Deprecation requested, or posting attempted against a deprecated account | — | Deprecation check applies uniformly, not scoped to one usage type | Deprecation blocked while any active reference exists; posting to an already-deprecated account is refused regardless of path | None — this rule is a deliberate correction of the reference system's partial-guard weakness (Team A: guarded only against tax-repartition usage, not general posting) | Configuration integrity; prevents orphaned or contradictory chart-of-accounts state | Both deprecation attempts and posting refusals are logged | GR-13 — **strengthened, not merely inherited**, per this domain's advancement mandate |
| BR-14 | An in-place Amendment to an unconsumed COMMITTED Entry is permitted but is always a logged, before/after event | Amendment requested | Entry is COMMITTED and not yet consumed (checked per BR-07) | Amendment still passes BR-01 through BR-05 as if newly posted | Entry content changes; a permanent `Amended` event records the prior value | None beyond the consumption boundary itself (BR-07 governs what happens after) | Keeps the pre-consumption correction path lightweight without sacrificing traceability | `Amended` event is mandatory, not optional — this is what distinguishes this rule from the reference system's uncontrolled reset-to-draft (CF-06) | B04 §3/§4 (new, Team B design) |
| BR-15 | A Consumption trigger (B04 §4), once recorded against an Entry, is permanent | Any of the four consumption trigger conditions fires | Entry is COMMITTED | Trigger condition matched against B04 §4's list | `Consumed` event recorded in Audit Evidence | None — there is no operation in this design that clears a recorded Consumed event | Enforces BINV-06/BINV-07 as an operational rule, not only a stated invariant | The event itself is the audit consequence | B04 §3/§4, BINV-07 (new, Team B design) |

## Coverage Note

BR-01 through BR-13 correspond one-to-one with Team A's GR-01 through GR-13, restated in this
domain's own vocabulary and, where Team A identified a weakness (BR-05's bypass path, BR-07's
mutability gap, BR-13's partial guard), restated as the **fixed** design rather than the
observed gap. BR-14 and BR-15 are new — they exist only because B04 introduced Amendment and
Consumption as first-class concepts the reference system's neutral observation had no
occasion to name.
