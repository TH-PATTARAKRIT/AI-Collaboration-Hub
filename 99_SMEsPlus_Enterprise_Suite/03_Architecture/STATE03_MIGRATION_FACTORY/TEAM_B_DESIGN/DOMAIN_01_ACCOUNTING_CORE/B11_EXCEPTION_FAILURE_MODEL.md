| 13 | Unauthorized correction | A correction performed by someone not entitled to perform corrections specifically (a narrower authorization than general posting, per CO-06's tiering) | Refused; correction-specific authorization is checked distinctly from ordinary posting authorization | Refusal logged | Escalate per platform authorization policy | Same as #12 |
| 14 | Repeated reversal | Ambiguous chains from reversing a reversal | **Resolved by design (B04 §6, B07 §3):** each Correction Link is independent and equally valid; a correction of a correction is not a special case — the relationship, not the Entry's "distance" from an original, carries meaning | Every link in the chain is independently logged and queryable | Follow the chain; there is no ambiguity to recover from by design | None — resolved, not merely observed as previously ambiguous (Team A GAP-D01-23) |
| 15 | Missing reference | An Entry with no traceable connection to why it exists | **New requirement:** every Entry must carry an origin reference — either a cross-domain reference back to the originating business event (B03 §3), or, for manual entries, a required actor + reason. CAP-02 refuses commitment of an Entry with neither. | The origin reference is a permanent, immutable property of the Entry (Team A: this scenario was previously deferred/unanalysed) | Correct the proposed Entry to include an origin reference and resubmit | None — resolved as a new requirement this phase, not left deferred |
| 16 | Migration imbalance | A migrated entry appears balanced in the source but is not, independently | Governed entirely by [B10](B10_CANONICAL_MIGRATION_REQUIREMENTS.md) MG-C10/MG-C12 — routed to the migration exception queue, blocking only that fact | Exception-queue entry with the specific validation failure | Human-resolved per MG-C12, never auto-forced to balance | Extent of actual source-data imbalance remains a data-level unknown until migration is attempted (GAP-D01-11) |
| 17 | Concurrency | Two simultaneous actions on the same Entry silently produce a lost update | **New design principle (was GAP-D01-21, out of scope for Team A's read-only pass):** any state-changing action on an Entry must be evaluated against that Entry's current, latest committed state at the moment of the action. If that state changed between when the action was initiated and when it would take effect, the later action fails cleanly and must be re-evaluated against the new state — it never silently overwrites. This is stated as a required property, not a specific mechanism (no implementation named). | The failed, stale-state action is itself logged | Re-submit the action against current state | The specific technique that guarantees this property is an implementation decision properly deferred past this domain-design phase |
| 18 | Partial failure | An Entry commits but its Audit Event does not (or vice versa), leaving evidence out of sync with fact | **New design principle:** Entry commitment (or any B04 §3 state change) and its corresponding Audit Event production are treated as a single indivisible unit — there is no reachable state where one exists without the other. | The indivisibility guarantee is itself the evidence requirement — a system that could reach a split state would fail BINV-08 by construction | If a split state is ever observed, it indicates a defect in the indivisibility guarantee itself, requiring investigation outside this domain's business-rule scope | The specific mechanism guaranteeing indivisibility is an implementation decision properly deferred past this domain-design phase |

## Pattern Note

Six of the eighteen scenarios (6, 9, 11, 15, 17, 18) required this phase to go beyond
restating Team A's evidence, because Team A either correctly declined to analyze them
(concurrency, security/authorization depth — out of scope for a read-only forensic pass) or
found the reference system's own answer genuinely absent or unproven (future posting,
duplicate detection effectiveness, missing-reference traceability). Multi-tenant isolation
(6) was never in scope for Team A's evidence at all, since the reference system was not
evaluated as a multi-tenant SaaS platform. This is exactly the kind of gap Team B's clean-room
design mandate exists to close independently, not merely inherit as still-open.
