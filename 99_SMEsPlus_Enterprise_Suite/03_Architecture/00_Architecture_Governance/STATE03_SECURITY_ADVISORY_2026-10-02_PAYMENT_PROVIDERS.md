## 1. HIGH — Toss Payments: a forged webhook chain could confirm a payment (`W-01`)

**Finding**: Toss's webhook handler skips signature verification for messages reporting status `EXPIRED` or `ABORTED` (`VDR-U20-C146`, `C147`), and `_apply_updates` overwrites the transaction's stored per-payment secret from **any** incoming message regardless of status (`C148`). Messages with a status other than `DONE`/`EXPIRED`/partial-cancellation fall through to `error` (`C149`). The engine's own `_set_done` allows the transition from `error` (`C150`, confirmed against the shared `payment` state-machine claims `C089`/`C090`). Chained: an attacker sends an `ABORTED` message (secret=X, correct reference) — skips verification, overwrites the stored secret to X — then a `DONE` message with the same secret X and the transaction's own amount — which now compares correctly (`C151`'s `hmac.compare_digest` only compares the message secret against whatever is currently stored, which the first message just set). DeepSeek itself flags the full chain `INFERENCE`/`RUNTIME-REQUIRED` — it has not executed it. **Classification: `RUNTIME/AWT_REQUIRED`** — the individual code facts (`C146`–`C151`) are internally consistent and `ACCEPTED`; the end-to-end exploit needs execution against a live/sandboxed Toss integration to confirm, which is Korea/KRW-only and likely not in SMEsPlus's current deployment footprint — queued to the AWT backlog, not a correction request to DeepSeek (nothing more can be learned from further static reading).

## 2. HIGH — Mercado Pago: direct-payment route trusts a browser-supplied amount (`W-02`)

**Finding**: the public, token-less direct-payment route overwrites the server-side payload's amount with a browser-supplied `transaction_amount` field (`VDR-U20-C057`, confirmed against the matching front-end JS line `C058`), while the later amount-extraction step reads an echoed `unit_price` from `additional_info.items` rather than the charged `transaction_amount` (`C059`) — DeepSeek flags as `INFERENCE`: whether the gateway's own server independently prices the charge from the echoed item (closing the gap) or trusts the client figure (leaving it open) is unconfirmed without a live call. **Classification: `RUNTIME/AWT_REQUIRED`** for the same reason as `W-01` — static evidence is `ACCEPTED` and internally consistent; closing the question needs an actual Mercado Pago sandbox call, not more source reading. Latin-American gateway; not Thailand-relevant for this deployment's own market, but still a genuine finding if this gateway were ever enabled.

## 3. HIGH for production use — the demo gateway is live, published, and able to confirm orders (`W-12`)

**Finding**: unlike the 23 real gateways (all `disabled`), the `demo` provider is **enabled in `test` state and `is_published = true`** in the studied DB (`VDR-U20-C309`, `C314`), with its payment method active (`support_tokenization = true`) and no transactions/tokens on it yet. The engine shows published providers to non-internal (portal/public) users regardless of production intent (`C315`). Its public `demo_simulate_payment` route accepts arbitrary client-supplied data and passes it straight to `_process` (`C312`), and `_apply_updates` reads the simulated outcome (`pending`/`done`/`cancel`/else `error`) directly from that client-supplied `simulated_state` (`C310`) — i.e. **any anonymous visitor who can reach the storefront/portal with this provider published can self-confirm a simulated payment and the order flow that depends on it**. **Classification: `ACCEPTED`** — this is a direct DB/code observation, not an inference, and needs no further research to confirm the mechanism; what remains open is purely a deployment-configuration question (is `payment_demo` reachable/published on any environment that matters), which is `RUNTIME/AWT_REQUIRED` only for *that* question, not for the mechanism itself. **Recommended immediate action for whoever owns a live environment: confirm `payment_demo` is unpublished/disabled wherever a real storefront or portal is reachable.**

## 5. What is NOT currently exposed (reduces real-world severity today)

All 23 real-gateway provider rows are `disabled` in the studied configuration — none is reachable by a customer today. The only **reachable** payment surfaces in this snapshot are the demo gateway (§3, published) and the Cash-on-Delivery/offline custom provider (enabled, no online-gateway attack surface). The gateway-specific findings above (`W-01`–`W-11`, `W-14`) describe code-level weaknesses that would matter **if and when** a given gateway is enabled for a live deployment — they are not describing a currently-live exposure on this studied snapshot, with the explicit exception of `W-12` (demo) and `W-13` (offline/demo routes), which concern providers that already are reachable.
